두 러너 모두 DD one-way latency가 같은 셀에서 0.4 ms와 900 ms 사이를 오간다(C `ws` 64B 78.5 ms vs 256B 1.8 ms, C++ `tls`
1024B 645 ms vs 256B 0.6 ms). DD는 백프레셔까지 제출하므로 one-way latency는 샘플 시점의 큐 깊이이고 러너·언어와 무관하게 bimodal이다.
따라서 이 표의 latency 비율(before의 `tls` 6.23x 포함)은 binding 비용을 나타내지 않으며 판정에 쓰지 않는다. **DD multi의 latency
metric 정의(큐 깊이 대신 admission→수신 시간 등)는 정책 검토 항목으로 남긴다(사용자 결정).**

## 판정

- 세 transport 모두 64~256B에서 66~75%로 tcp DD(pass 2 뒤 90.8%)와 같은 "작은 메시지 고정 비용" 형태이며, binding SEND 경로는
  transport를 모른다(같은 `send_operations.cpp` 경로). 이 pattern의 자체 pass 1(`86b897abf7`)과 Sol 리뷰 pass 2(`e6dd88fbc6`, 후보
  9개 중 3개 채택·6개 no-go)는 tcp 측정으로 이미 수행했고 남은 후보는 모두 public contract 변경(기각 목록)이다.
- §7.5: 두 pass 뒤 공개 contract를 유지한 효과 있는 후보가 없으면 `보류`. → `MULTI_DEALER_DEALER` `tls` **`보류(79.3%)`**, `ws`
  **`보류(85.3%)`**, `wss` **`보류(91.1%)`**(완화 목표 90%를 tls/ws/wss에도 적용할지는 사용자 결정; 적용 시 `wss`는 `통과`).
