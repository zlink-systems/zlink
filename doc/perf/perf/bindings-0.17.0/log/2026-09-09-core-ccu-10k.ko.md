## 원인과 오류 전달

**접속 대기 10초가 부족한 문제가 아니라 Core의 pipe 최소 예약 거부다.**
공식 0.17.4의 5,000 접속 재현에서 raw Asio connect callback은 5,000/5,000 성공했다.
`zlink_socket_monitor_recv()`도 성공하여 `ZLINK_EVENT_ACCEPT_FAILED`(64),
`event.value=ENOBUFS`(105)를 반환했다. 서버는 `ready=3517 expected=5000 monitor_error=105`로
barrier를 중단했다. 이후 러너가 서버 종료를 확인하고 client stdin에 `STOP`을 쓴다.
클라이언트는 `wait_for_start_from_stdin()`에서 `false`, `errno=ECANCELED`(125)를 받고
`run_case().pass=false` → `run()`의 exit 2로 끝난다.

```text
[multi-stream-server] connection-ready barrier failed ready=3517 expected=5000 monitor_error=105
perf_stream_client: START wait failed errno=125 connected=5000 expected=5000
```

위 두 줄과 5,000 connect 성공 callback은 ccu10k-baseline-client-errno (`/home/hep7/.cache/zlink/ccu10k/results/multi/report/perf_c_multi_linux_20260909_092406_ccu10k-baseline-client-errno.txt`)에 보존했다.
Client가 사용하는 connect는 raw Asio API이며 Core monitor recv나 ZMP handshake를 호출하지 않는다.
STREAM의 ZMP handshake 없음은 `core/doc/spec/core/socket/08-stream.ko.md:282`에 명시돼 있다.

원인 경로의 줄 번호는 수정 전 Core 0.17.4 기준이다.

Balanced STREAM 최소 예약은 방향당 64 KiB, 연결당 128 KiB다. 초기 고정 cap 512 MiB만
사용하면 **4,096개 연결**에서 예약 한계에 도달한다. 계약의 budget은
`min(memory의 5%, max(512 MiB, 방향 수 × 64 KiB))`여야 한다. 10,000 연결의 최소 총량은
1,310,720,000 B다. 새 연결이 추가된 topology로 계산하면 이 호스트에서 수용할 수 있다.
오류 순간의 monitor READY 관찰 수는 아직 pipe attach·READY 전달이 진행 중이므로
예약 한계 4,096과 같다고 해석할 수 없다.

예약 경로 도입은 `371162abf5d`, queue-count 기반 effective cap 도입은 **`2cea03c0161`**이다.
후자의 변경에서 예약 검사가 초기 count=0 budget을 사용하는 연결을 함께 고치지 않은 것이
이번 결함의 원인이다. CCU-2~5의 attach 최적화와 별개다.

## 경로별 판정과 비교

- I/O 분배: `ctx_io_thread_registry.cpp:108`은 STREAM session을 기본 round-robin으로 분배한다.
  C perf의 서버·클라이언트 I/O thread 기본값은 각 4개이며 그대로 사용했다.
- 남은 확장 비용: `socket_base_api.cpp:646`의 증분 plan 거부 시 전체 재계산 fallback,
  `ctx_physical_queue_registry.cpp:1008`의 queue ID 순서 제약, `stream.cpp:186`의
  64-shard route map 복사는 여전히 존재한다. 이번 실패는 이 경로의 10초 초과가 아니라
  ENOBUFS로 확정됐으므로 이들을 변경하지 않았다. 수정 후 10k 성공이 이번 목표의 근거다.
- Monitor: `core/doc/spec/core/06-monitoring.ko.md:103` §4는 같은 monitor의 transition commit
  순서와 queue 포화 시 새 record 폐기를 규정한다. 여러 I/O thread의 wall-clock 순서는 보장하지 않는다.
  `socket_monitor_runtime.cpp:240`의 bounded enqueue와 `socket_base_monitor.cpp:739`의 pump를 확인했다.
  HWM은 4,096,000 B 그대로다. 공개 drop counter는 없으므로 실패 당시 loss 수를 추정하지 않는다.
  성공한 10k 측정에서는 barrier가 실제 10,000 READY 관찰을 확인했다.
- Client: TCP connect가 전부 완료된 후 START gate에서 취소됐다. connect·monitor recv·handshake timeout으로 분류하지 않는다.

## 수정과 계약

`ctx_physical_queue_registry.cpp:426`에서 기존 최소 예약 aggregate를 `{bytes,directions}`로
관리한다. 같은 lock 아래 새 pair를 포함한 방향 수로 기존 `auto_hwm_effective_budget_bytes()`를
호출하고, 두 방향의 예약·등록을 함께 승인하거나 거부한다. 최종 endpoint 해제 시 같은
aggregate에서 bytes와 directions를 함께 반환한다(`:1342`).

비교한 대안은 매 attach마다 registry 전체를 다시 세는 방법과, 기존 원자적 예약에 방향 수를
함께 보관하는 방법이다. 전체 스캔은 접속 burst에 O(N²) 비용을 추가하므로 선택하지 않았다.
새 별도 registry나 타이머 없이 기존 예약 소유자가 관리하며, 최소 예약 판단 자체는 O(1),
기존 map 등록은 O(log N)이다. 데이터 송수신 hot path는 바꾸지 않았다.

- 소유 계층: **Core physical queue registry / Auto-HWM policy**.
- 사양: **`systems/06-auto-hwm.ko.md` §2, :73–96의 effective cap 및 :121–124의 pair 원자 예약**;
  monitor 계약 §4–5와 STREAM 계약 유지.
- 교차 구현 대조: **CppServer·Asio는 session 상태를 직접 공개하며 Core의 budget 예약 단계가 없다**.
  Framework runtime과 binding 계약은 변경하지 않았다.
- 변경 분류: **B — 기존 결함**. 계약 개정 불필요.
- 수정 전/후 규칙 수: **budget 계산 기준 2개(예약의 고정 cap, planner의 topology cap) → 1개(공통 budget 함수)**.

검토에서 Auto-HWM을 끈 상태로 만든 queue를 다시 활성화할 때의 기존 예약 재구성 경계도
확인했다. 기존 최소 예약은 생성 시 값이므로 이 전환의 count가 현재 planner 방향 수와 다를 수
있다. 이 작업의 항상 활성인 STREAM 경로와 구분하며, 해당 기존 전환 경계까지 해결했다고 주장하지 않는다.
