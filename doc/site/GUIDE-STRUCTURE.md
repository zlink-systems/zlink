# 사용자 가이드 목차

> 이 문서는 Framework 서버 가이드의 **목차와 각 장의 출처**를 정한다. 장을 새로 만들거나
> 옮길 때 여기를 먼저 고친다.
>
> 문장과 편집 규칙은 [기술문서 작성 원칙](../principal/documentation/documentation-principles.ko.md)이,
> 가이드의 층·코드 출처·형식은
> [사용자 가이드 문서 작성 가이드](../principal/documentation/guide-writing-guide.ko.md)가,
> 사이트 빌드 설정은 [SPEC.md](SPEC.md)가 소유한다.

## 1. 왜 바꾸는가

기존 가이드는 한 장이 **처음 쓰는 독자와 이미 써 본 독자에게 동시에** 말한다. 그래서 등록
코드 하나를 보려는 사람이 옵션 표와 실패 분기를 먼저 통과해야 한다. 05장이 2,185줄,
01장이 1,265줄인 것이 그 결과다.

> 이 문서의 줄 수는 **빈 줄을 뺀 파일 전체 줄 수**다. 다섯 언어 탭을 모두 센다. 독자 한
> 사람이 실제로 읽는 분량(`C#/.NET` 탭만 세는 값)과 다르며, 그쪽은
> [사용자 가이드 문서 작성 가이드](../principal/documentation/guide-writing-guide.ko.md) §3.2가
> 소유한다. 상한 300줄·500줄은 읽는 분량 기준이다.

두 층으로 나눈다.

| | 기능별 가이드 | 동작 원리 |
| --- | --- | --- |
| 독자 | 이 기능을 처음 쓴다 | 이미 써 봤고, 왜 그렇게 되는지 알아야 한다 |
| 답하는 질문 | 이걸 어떻게 쓰나 | 이게 어떻게 동작하나 |
| 끝나는 지점 | 따라 하면 돌아간다 | 경계와 실패까지 안다 |
| 상한 | 300줄 | 500줄 |

**자르는 기준은 하나다.**

> 기능별 가이드 장은 "한 번 따라 하면 도는 것"까지만 쓴다. 종류 비교표·변형·옵션이
> 나오기 시작하는 지점에서 자르고 동작 원리로 보낸다.

## 2. 목차

```
Framework
│
├─ 시작
│   ├─ 개요                          ← 01 (그대로)
│   ├─ 핵심 개념                     ← 03 (그대로)
│   └─ Quickstart                    ← 02 §1을 흡수한 언어별 정본
│
├─ 기능별 가이드
│   ├─ Channel 메시징                ← 05 §1·2(최소형)·3·4
│   ├─ Spot                          ← 06 §1·2·3·4
│   ├─ Actor                         ← 07 §1·2·3
│   ├─ STREAM                        ← 09 §1·2·3·5·6
│   ├─ Session과 Actor 연결          ← 08 (전체)
│   ├─ Location                      ← 10 §0·1·2·5
│   └─ 모니터링                      ← 11 (그대로)
│
├─ 동작 원리
│   ├─ 실행 모델                     ← 06 §3.1 + 05 "종결자"
│   ├─ Backpressure                  ← 04 (그대로)
│   ├─ 활성화와 수명                 ← 06 §5.2
│   ├─ Actor membership              ← 07 §4·5
│   ├─ Timer와 worker                ← 06 §7
│   ├─ Relocation                    ← 06 §8 + 07 §7 + 12 §2·3
│   ├─ 메시지 filter                 ← 05 §5
│   ├─ 연결 제어                     ← 05 §6
│   ├─ 직렬화 codec                  ← 05 §7
│   ├─ Channel 수평 확장             ← 05 §8·9
│   └─ ZLink를 어디에 쓰나           ← 17 (기술 선택 근거)
│
├─ 운영
│   ├─ 운영과 lifecycle              ← 12 §1·4·5·6
│   └─ 옵션                          ← 16
│
├─ 샘플과 테스트
│   ├─ 샘플 고르기                   ← 14
│   └─ E2E 테스트                    ← 15
│
├─ 레퍼런스                           ← 현 reference/ + 13 타입 색인
└─ 스펙                               ← 그대로
```

**손대지 않는 장** — 01 · 03 · 04 · 08 · 11 · 13 · 14 · 15 · 16 · 17. 자리만 옮긴다.
**해체하는 장** — 02 · 05 · 06 · 07 · 12. 다섯 장.

## 3. 층 이름

`nav_translations`는 라벨 문자열 전체를 키로 쓰는 평면 map이므로 기존 라벨과 겹치지 않게 잡는다.

| 한국어 | nav 라벨 |
| --- | --- |
| 시작 | `Start` |
| 기능별 가이드 | `Features` |
| 동작 원리 | `Fundamentals` |
| 운영 | `Operations` |
| 샘플과 테스트 | `Samples` |

## 4. 파일 번호

| 번호 | 층 |
| --- | --- |
| `01`~`19` | 시작 · **운영** · 샘플과 테스트 · 레퍼런스 (기존 번호 유지) |
| `20`~`29` | 기능별 가이드 |
| `30`~`39` | 동작 원리 |
| `40`~`49` | 한 언어에만 있는 장 |

**번호는 층이 바뀌어 번호대가 달라질 때만 새로 받는다.** `33-backpressure`는 동작 원리로
가면서 `33`을, `11-monitoring`은 기능별 가이드로 가면서 `26`을 받는다. `01`~`19` 안에서
움직이는 장은 이름을 유지한다 — 운영 층의 `12-operations`·`16-options`, 시작 층의
`01`·`03`·`17`이 그렇다. 그 장들은 mkdocs nav의 구획만 옮긴다.

> **`40`~`49`는 한 언어에만 있는 장이 쓴다.** C++의 `40-di-container` · `41-configuration` ·
> `42-http-hosting` · `43-execution-model`이 그것이다. 원래 `18`~`21`이었는데 `20`~`29`가
> 기능별 가이드 번호대라 `20-http-hosting`이 `20-channel-messaging`과, `21-execution-model`이
> `21-spot`과 겹쳤다. 네 장을 옮겨 번호대를 갈랐다. 다른 언어에만 있는 장이 생기면 같은
> 번호대를 쓴다.

## 5. 예상 분량

해체 대상 장에서 나오는 새 장의 크기다.

| 새 장 | 예상 |
| --- | --- |
| 실행 모델 | ~150줄 |
| 활성화와 수명 | ~215줄 |
| 메시지 filter | ~200줄 |
| 연결 제어 | ~220줄 |
| 직렬화 codec | ~180줄 |
| Channel 수평 확장 | ~370줄 |
| Actor membership | ~540줄 |

150~400줄대에 들어온다. 900~1,000줄짜리 장이 사라진다.

## 6. 지금까지 한 것

| 장 | 상태 | 파일 |
| --- | --- | --- |
| Channel 메시징 (기능) | **작성됨** | `20-channel-messaging.ko.md` · 242줄 |
| Channel 동작 원리 | **작성됨** | `30-channel-patterns.ko.md` · 305줄 |
| Handler와 메시지 처리 | **작성됨** | `31-handler-dispatch.ko.md` · 118줄 |

> 이 세 값만 **읽는 분량**(`C#/.NET` 탭만 센 값)이다. 상한 300·500과 비교할 값이므로
> §1의 셈법과 다르다. 진행 상태의 정본은
> [재작성 계획](../plan/guide-rewrite.ko.md) §6.1이 소유한다.

목차의 `메시지 filter` · `직렬화 codec`은 `31-handler-dispatch`가, `연결 제어` ·
`Channel 수평 확장`은 `30-channel-patterns`가 흡수했다. 그래서 목차 §2의 동작 원리 항목
넷이 두 장으로 합쳐진다.

**05장은 아직 삭제하지 않았다.** 세 장이 그 내용을 모두 받았는지 확인한 뒤 지운다.

남은 작업 목록 — tutorial 확장, `.en.md`, nav 재배치, 착수 순서 — 은
[재작성 계획](../plan/guide-rewrite.ko.md) §5.1·§6.4가 소유한다.

## 7. 장을 추가할 때

1. §4에서 번호를 고른다.
2. 나머지 절차는
   [사용자 가이드 문서 작성 가이드](../principal/documentation/guide-writing-guide.ko.md) §6과
   §7이 소유한다 — 공통 소스 작성, 다섯 언어 README 행, 생성기 실행, mkdocs nav, 완료 점검표.
   이 재작성 작업에서의 단계별 순서와 주의는 [재작성 계획](../plan/guide-rewrite.ko.md) §5.4에
   있다.
