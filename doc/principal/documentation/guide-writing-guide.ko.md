# 사용자 가이드 문서 작성 가이드

> 이 문서는 독자가 무엇을 왜 쓸지 판단하고 바로 따라 쓰게 돕는 **사용자 가이드**를
> 작성하거나 수정하는 작업자가 따르는 절차다. 주 독자는 문서 작업을 수행하는 AI다.
>
> [기술문서 작성 원칙](documentation-principles.ko.md)의 얇은 보충 문서다. 원칙
> 1~9는 그대로 적용한다. 이 문서의 §2·§3은 [스펙 문서 작성 가이드](spec-writing-guide.ko.md)
> §2·§3과 같은 자리를 차지하며, 완성된 사용자 가이드 묶음을 분석해서 뽑은 절차다 —
> 추측이 아니라 그 문서들이 실제로 따르고 있는 관행이다.

[기술문서 작성 원칙](documentation-principles.ko.md) ·
[스펙 문서 작성 가이드](spec-writing-guide.ko.md)

## 1. 스펙 문서와 다른 점

스펙은 공개 계약을 **서술**한다. 사용자 가이드는 독자가 무엇을 왜 쓸지 **판단**하고
바로 따라 쓰게 돕는다. 정확한 계약과 가이드의 설명이 어긋나면 스펙이 이긴다 — 이
관계는 문서 도입부에서 명시한다.

> 모델 문장: "개념의 언어 중립 정식 정의는 공통 스펙 개요가, 이 언어 public API의
> 정식 계약은 스펙 문서가 다룬다. **두 표기가 어긋나면 스펙이 우선이다.**"

## 2. 작업 순서

### 2.1 입력 자료를 확인한다

1. 이 챕터가 다루는 기능의 공통 스펙 챕터를 확인한다.
2. 언어별 exact interface 문서에서 정확한 public signature를 확인한다 — 코드 예제는
   오늘 배포된 동작이 아니라 exact interface가 정의하는 목표 계약을 따른다. 배포와
   목표가 다르면 "구현 차이" 문서가 그 간극을 소유하며, 가이드 코드는 목표 계약 쪽을
   보여준다.
3. 가능하면 실행되는 샘플과 코드 예제를 대응시킨다.
4. 자료가 충돌하면 스펙과 exact interface를 우선한다.

챕터를 열 때 소유 스펙 문서를 명시하고("정식 계약은 스펙이 다루며, 이 챕터는 사용법을
다룬다"), 닫을 때 **interface 색인 문서**의 해당 절 번호와 검증 클래스를 가리킨다.
입력 확인과 대조는 챕터의 시작과 끝 두 지점에 구조적으로 두며, 그러면 개별 문장마다
출처를 달 필요가 없다.

### 2.2 독자의 질문으로 목차를 만든다

기존 챕터는 아래 모양으로 갈린다. 새 챕터를 쓸 때는 먼저 어느 모양인지 정한다.

**모양 A — 도입 판단** (개요, 경쟁 기술과의 비교)

1. 한 줄 정의, 체감 난이도
2. 상황별 문제 → 제품 기능 대응 표
3. 경계 — 이 문서가 다루지 않는 것
4. 선택을 돕는 flowchart나 기준 표
5. 실행 가능한 샘플 링크
6. 상세 비교(경쟁 기술 등, 참고용)

추천 결론을 낼 때는 적용 범위를 결론 문장 안에 넣는다("gRPC를 고민 중이라면 이 제품을
써라"가 아니라 "내부 서비스 통신을 gRPC로 고민 중이라면"처럼). 판단 기준은 기술명이
아니라 반복되는 문제 증상으로 준다. 경쟁 기술과 비교할 때는 "없는 기능"과 "훅은 있는데
미리 구현된 도구가 없는 기능"을 각각 구분해 적는다.

**모양 B — 레퍼런스/입문** (시작하기, 개념 문서, interface 색인)

범위 선언 → 초반 용어/메타 절 → 개념 또는 interface 그룹별 본문(코드+표) → "관련
문서". 시작하기 챕터는 실제 샘플 하나를 처음부터 끝까지 따라가는 walkthrough이고,
개념 문서는 전체 용어 지도, interface 색인은 언어별 interface를 계약 순서로 색인한다 —
세 챕터는 각자 내용에 맞는 구성을 쓴다.

**모양 C — 기능 사용법** (가장 흔한 모양)

1. (선택) 익숙한 기술이나 "무엇을 해결해주는가" 문제로 방향 잡기
2. 핵심 개념 정의
3. 등록/builder 코드
4. 핵심 사용법 — "종류 | 보내는 함수 | 받는 handler" 같은 한눈에 보기 표
5. 운영 변형(filter, scaling, 오류 종류 등)
6. 자주 발생하는 문제 — 증상 → 원인 표
7. 관련 문서 — 스펙, interface 색인 절 번호, 검증 클래스, 샘플 링크

6번(자주 발생하는 문제)은 챕터에 따라 "오류 처리"나 "동작 방식" 절이 그 자리를
대신한다. 챕터 내용에 맞는 쪽을 고른다.

### 2.3 용어를 먼저 정리한다

가이드에서 핵심 개념의 정의 자리는 스펙의 공통 용어집이 아니라 **개념 문서**의 해당
절이다. 이것이 [기술문서 작성 원칙](documentation-principles.ko.md) 원칙 2 "용어는
문서 단위로 다시 소개한다"에서 말하는 정식 정의 자리다.

**용어는 처음 필요해지는 자리에서 설명한다.** 독자가 실제로 모를 만한 용어만 그
자리에서 푼다. 문서 앞에 "자주 나오는 용어" 표를 깔면 어렵지 않은 단어까지 목록에
섞여 진입 장벽만 늘어난다.

그 원칙을 그대로 적용한다: **이 챕터에서 그 용어가 처음 나오는 자리**에서는 한
문장으로 다시 풀고 링크한다. 같은 챕터 **안에서** 다시 나오면 링크 없이 이름만 쓴다.

```markdown
[session](concepts.ko.md#session--연결-하나를-대표하는-상태-객체)은 연결 하나를
대표하는 상태 객체다 — 이 챕터에서는 연결과 session 사이의 binding만 다룬다.
```

링크 옆에는 **한 문장 설명을 함께** 둔다. 독자는 그 챕터만 열었을 수 있어서, "용어가
낯설면 개념 문서를 보라"는 포인터만으로는 링크를 따라가기 전까지 그 문장을 읽을 수
없다.

제품 도메인 용어는 스펙과 정확히 같은 이름을 쓴다. 가이드만의 서술 장치(체감 난이도,
자주 발생하는 문제, 샘플에서 보기, 목표 계약)는 새로 만들어도 되며, 이때도 이미
쓰이는 표현을 재사용한다.

**스펙의 내부 계약 용어는 뜻을 풀어 쓴다.** 스펙이 계약을 정밀하게 쓰려고 도입한
단어(`membership`, `authority` 등)가 가이드 산문에 설명 없이 등장하면 독자는 그
단어부터 해석해야 한다. 그 자리에서 뜻하는 바를 평이한 말로 쓴다.

| 이렇게 쓴다 | 흔한 이탈 |
| --- | --- |
| "같은 기능을 **맡은 node들**을 묶는다" | "같은 기능을 제공하는 **membership**을 묶는다" |
| "요청을 **받을 수 있는 node** 중 하나" | "ready 상태인 **membership** 중 하나" |

### 2.4 쉬운 설명부터 작성한다

절(`§1` 이하) 수준에서는 스펙과 같은 규율을 쓴다 — 정의나 결과로 문장을 시작한다.
반면 **챕터 진입부(`§0`)는 동기·문제 먼저**로 시작해도 된다 — 이게 스펙과의 의도적인
차이다. 독자가 이미 아는 것에서 출발해 새 개념으로 넘어가는 게 onboarding 문서의
역할이다.

```text
예(주소 자동 해석 챕터 §0): "지금까지 챕터는 연결할 endpoint를 코드에 직접
적었다. 주소 저장소를 등록하면 호출하는 쪽에서 remote endpoint 값이 사라진다."
— 문제(before) → 해결(after) 순서.
```

한 문단(또는 표 한 칸)에 여러 판단을 담아도 되는 경우는 "자주 발생하는 문제" 같은
Q→원인 표 안에서뿐이다 — 원인, 조건, 관련 코드, 주의사항을 한 칸에 압축해도 괜찮다.
표 밖의 일반 산문에서는 스펙과 똑같이 한 문단에 주된 판단 하나만 둔다.

같은 단어가 문맥마다 다른 뜻이면 명시적으로 구분한다. 예: "여기서 말하는 직렬화는
payload를 bytes로 바꾸는 codec 직렬화가 아니다. 메시지를 어떤 실행 줄에서 어떤 순서로
처리하는가를 뜻한다"처럼 짚고 넘어간다.

### 2.5 정확한 계약을 다시 대조한다

대조는 스펙처럼 절마다 항목별 대조표를 두는 대신 **interface 색인 문서** 한 곳에
모은다 — 모든 interface 그룹이 그 문서에서 검증 클래스·테스트 메서드에 연결된다. 각
기능 챕터는 닫는 절에서 그 절 번호와 검증 클래스를 가리키는 한 줄을 반드시 둔다.

```text
예(기능 챕터의 마지막 절): "이 챕터 계약의 실행 검증 예문은 [interface 색인] §1 —
검증 클래스 `ChannelContracts`·`HandlerContracts`·`CodecContracts`."
```

새 기능 챕터를 쓰거나 고칠 때는 이 포인터가 실제로 맞는 절 번호·클래스를 가리키는지
확인하는 게 가이드의 "계약 대조" 단계다.

### 2.6 링크와 자동 검증을 확인한다

- 이 챕터에서 처음 쓰는 용어마다 한 문장 재설명 + 개념 문서 링크가 있는지
  확인한다(§2.3). 링크 옆에 설명이 함께 있는지 다시 훑는다.
- 저장소에 문서 회귀 테스트가 있으면 사용자 가이드는 그 테스트로 구조적으로 검증된다.
  - 목록에 적은 파일이 모두 존재하고 nav 마커·H1을 갖췄는지(내용 정확성은 아님).
    챕터를 더하거나 빼면 그 목록도 함께 고쳐야 한다.
  - 이름이 바뀌었거나 제거된 API를 걸러내는 금지 패턴 grep(대체된 interface 계열,
    폐기된 callback 모양이 문서에 남아 있는지).
- 계약 문서에 `## 회귀 테스트` 섹션을 강제하는 저장소라면 사용자 가이드는 그 대상에서
  **제외**한다 — 온보딩 산문이지 계약 문서가 아니기 때문이다.
- 계약 검증 스크립트를 두는 저장소에서도 그 스크립트는 스펙 전용이므로 사용자 가이드를
  검사하지 않는다. 가이드 코드 예제 검증은 위 금지 패턴 grep과, 가능하면 실제 샘플과의
  대조에 의존한다.
- Markdown 표·mermaid 문법을 확인하고 `git diff --check`를 실행한다.

## 3. 용어 작성 규칙

### 3.1 이미 소개한 개념 위에는 정의문을 바로 얹는다

스펙은 "동작을 먼저 설명하고 이름을 나중에 붙인다"를 모든 용어에 강제하지만,
사용자 가이드는 개념 문서가 이미 그림을 심어 둔 개념이라면 `"X는 Y다"` 정의문을 바로
써도 된다 — 실제로 대부분의 §1이 이렇게 시작한다. 단, **개념 문서가 아직 다루지 않은
새 용어**나 **문맥마다 뜻이 겹치는 단어**는 스펙 방식대로 동작을 먼저 풀고 이름을
붙인다(2.4의 "직렬화" 예).

### 3.2 개념 정의 자리와 챕터별 첫 링크

새 핵심 개념을 추가하면 개념 문서에 그 개념의 자리를 먼저 만든다. 그 뒤 **이 용어를
쓰는 모든 챕터**에서, 각 챕터의 첫 등장 자리마다 §2.3처럼 한 문장으로 다시 풀고
링크한다 — 링크는 챕터마다 다시 단다. 가이드 독자에게 정의 자리는 개념 문서이므로,
스펙의 공통 용어집 대신 그 절을 가리킨다.

### 3.3 정식 식별자와 모호한 단어를 구분한다

Public type·method 이름은 그대로 쓴다. 특히 대소문자나 철자가 비슷해 헷갈리는 쌍은
명시적으로 구분한다.

> 예: 서버 타입과 client 타입이 대소문자만 다른 이름을 쓰면(`FooBar` / `Foobar`),
> 표기 규칙을 개요 챕터에서 한 번 밝히고, 두 타입이 함께 등장하는 챕터의 "자주
> 발생하는 문제"에서 같은 혼동을 다시 짚는다.

### 3.4 도메인 용어는 스펙 이름을 쓰고, 서술 장치만 새로 만든다

제품 도메인 개념은 스펙·용어집에 등록된 이름을 그대로 쓴다. 가이드만의 온보딩 서술
장치(체감 난이도, 자주 발생하는 문제, 샘플에서 보기, 목표 계약/목표 사용법)는 새로
만들어도 되는 예외이며, 새 챕터에서도 이미 쓰이는 이름을 재사용한다.

## 4. 문서 사이의 경계

### 4.1 개념 문서는 개념까지만 쓴다

개념 문서(모양 B)와 기능 문서(모양 C)는 같은 주제를 다루되 멈추는 지점이 다르다.

| | 개념 문서가 답하는 것 | 기능 문서가 답하는 것 |
| --- | --- | --- |
| 범위 | 이게 무엇이고, 왜 있고, 언제 고르나 | 어떻게 등록하고 호출하고 실패를 다루나 |
| 종류·모드 | 갈래가 있다는 사실과 선택 기준 | 갈래별 차이표, 옵션, 제약 |
| 코드 | 개념이 코드에서 어떤 모양인지 보이는 최소한 | 실제로 따라 쓸 수 있는 등록·호출·lifecycle |

갈래·옵션·제약이 등장하면 기능 챕터로 넘긴다. 개념 문서가 갈래를 하나씩 해설하기
시작하면 그 문서는 각 기능 챕터의 요약본이 아니라 대체본이 된다.

### 4.2 경계를 넘은 내용은 소유 챕터로 옮긴다

경계를 넘은 내용을 발견하면 소유 챕터로 **이동**한다 — 삭제가 아니라 이동이다.
이동 뒤에는 다음을 확인한다.

1. 목적지에 이미 같은 내용이 있는지 — 있으면 더 정확한 쪽을 남기고 합친다.
2. 출발지에 남긴 요약이 목적지를 앵커 링크로 가리키는지.
3. 이동하면서 깨진 링크·앵커가 없는지.

### 4.3 문서 안 참조는 앵커 링크로 건다

같은 문서 안을 가리킬 때는 제목을 그대로 가리키는 앵커 링크를 건다. `§2~§3`처럼 절
번호만 적으면 독자가 그 번호가 어느 제목인지 찾아야 하고, 절이 재배치되면 조용히
틀린 참조가 된다.

```markdown
이렇게 쓴다:  [실행 단위](#2-실행-단위--상태를-소유하고-순서대로-처리한다),
              [상태 객체](#3-상태-객체--id로-식별된다)에서 각각 설명한다.
흔한 이탈:    실행 단위는 §2, 상태 객체는 §3에서 설명한다.
```

다른 문서를 가리킬 때는 문서 이름이 함께 보이므로 `[운영 챕터 §2](...)`처럼 절
번호를 덧붙여도 된다.

## 5. 설명 수단 고르기

### 5.1 API 사용법은 산문이 아니라 코드와 주석으로 쓴다

메서드 이름·인자·반환값을 문장으로 나열하면 문장이 길어지고 읽는 속도가 떨어진다.
산문은 개념만 설명하고, 시그니처와 인자의 의미는 코드 예제의 줄 주석으로 옮긴다.

```text
이렇게 쓴다:  산문 — "채널 위에서 실행 단위끼리 이벤트를 주고받는다. 받는 쪽은 같은
              topic을 구독한 대상으로 한정된다."
              코드 — 각 인자 옆에 "전달 범위를 정하는 채널 이름", "그 안에서 받을
              대상을 고르는 topic" 주석.

흔한 이탈:    보내는 쪽은 `Context.Outbound.Publish(channelName, topic, event)`로
              보내고(바깥에서는 별도 client 타입으로 같은 걸 한다), 받는 쪽은
              `Configure()`에서 `Context.Handlers.AddSubscribe<THandler>(...)`로
              구독한다.
```

### 5.2 코드 예제는 저장소 샘플에서 확인한 것으로 쓴다

실행되는 샘플에서 해당 흐름을 찾아 그대로 옮기고, 어느 샘플인지 밝힌다. 지어낸
예제에는 컴파일되지 않는 조합이나 이미 제거된 API가 들어간다. 옵션을 생략해 예제를
줄일 때는 그 옵션이 정말 선택인지 코드로 확인한다 — 필수 옵션을 빼면 startup에서
실패하는 예제가 된다.

### 5.3 예시가 주장을 실제로 뒷받침하는지 확인한다

개념을 설명하는 예시는 그 개념의 조건을 만족해야 한다. 조건이 다른 예시를 섞으면
독자가 개념을 잘못 일반화한다.

- "여러 요청이 같은 상태를 **동시에** 건드리는 대상"의 예시는 실제로 동시성이 있는
  대상으로 고른다.
- 기존 방식을 대비할 때는 그 분야가 실제로 쓰는 방식을 적는다. 대비를 크게 만들려고
  세운 전제는 독자가 자기 상황과 대조할 수 없게 만든다.

### 5.4 개념 설명에도 다이어그램을 둔다

개념 문서에도 다이어그램을 둔다. 구조·이동·선택은 그림이 문장보다 빠르다.
다이어그램을 그릴 때 확인할 것:

- **담김 관계를 실제 구조대로 그린다.** 실행 단위가 서로 포함 관계면 중첩 subgraph로
  그린다(예: process 안에 실행 단위, 실행 단위 안에 상태 객체). 나란히 놓고 화살표만
  이으면 관계가 틀리게 전달된다.
- **복수성이 개념의 일부면 복수로 그린다.** 여럿 중 하나를 고르는 동작은 후보를
  하나만 그리면 드러나지 않는다. 후보를 여럿 그리고 선택된 것을 강조한다.
- **역할이 다르면 구분해 표시한다.** client와 server, 이동 전과 이동 후처럼 역할이
  갈리는 요소는 색이나 선 굵기로 구분한다.
- **그 개념이 왜 중요한지 그림 뒤 한 문단으로 잇는다.** 구조만 보여주고 끝내면
  독자는 "그래서 뭐"에서 멈춘다.

### 5.5 다이어그램 가독성 규약

배경을 지정하는 요소에는 글자색도 함께 지정한다. mermaid 기본 테마는 중첩 subgraph의
테두리를 거의 그리지 않고 subgraph 제목 색은 뷰어 테마를 따라가므로, 밝은 배경만
지정하면 어두운 테마에서 제목이 묻힌다.

```text
style OuterBox fill:#eceff1,stroke:#546e7a,stroke-width:2px,color:#000000
style InnerBox fill:#ffffff,stroke:#1565c0,stroke-width:2px,color:#000000
classDef leaf   fill:#e8f5e9,stroke:#2e7d32,color:#1b5e20
classDef moving fill:#fff3e0,stroke:#e65100,stroke-width:3px,color:#bf360c
```

중첩할 때는 바깥 상자와 안쪽 상자의 배경을 다르게 둔다. 렌더 결과를 실제로 확인해
글자와 경계가 보이는지 본다([기술문서 작성 원칙](documentation-principles.ko.md)
원칙 6).

### 5.6 primitive는 primitive 이름으로, 예시는 도메인 단어로 쓴다

제품의 primitive를 가리킬 때는 primitive 이름을 쓰고, 도메인 예시를 가리킬 때만
도메인 단어를 쓴다. 둘을 섞으면 독자가 어디까지가 제품 규칙이고 어디부터가 예시인지
구분하지 못한다.

```text
이렇게 쓴다:  "그 실행 단위의 모든 callback을 직렬화한다 — 게임 방이라면 보드 상태와
              참가자 목록이 여기 해당한다"
흔한 이탈:    "방 안의 모든 일이 한 줄로 처리된다" (제품 규칙인데 도메인어)
```

## 6. 완료 점검표

- [ ] 챕터 여는 blockquote가 소유 스펙 문서를 명시하고, 닫는 절이 interface 색인 절
      번호·검증 클래스를 가리킨다(§2.1, §2.5).
- [ ] 챕터가 모양 A/B/C 중 어디에 해당하는지 정하고 그 템플릿을 따랐다 — 강제로
      맞추지 않아도 되는 절은 생략했다(§2.2).
- [ ] 새 개념의 정의 자리를 개념 문서에 만들었고, 그 용어를 쓰는 각 챕터의 첫 등장
      자리마다 한 문장 재설명 + 링크를 달았다(§2.3, §3.2).
- [ ] 실제로 모를 만한 용어만 그 용어가 필요해지는 자리에서 설명했다(§2.3).
- [ ] 스펙의 내부 계약 용어(membership, authority 등)를 평이한 말로 풀었다(§2.3).
- [ ] `§1` 이하는 정의·결과 먼저, `§0` 진입부는 동기·문제 먼저로 썼다(§2.4).
- [ ] 표 밖 일반 산문은 한 문단에 판단 하나만 담았다(§2.4).
- [ ] 문맥마다 뜻이 겹치는 단어와 철자가 비슷한 public 식별자를 명시적으로
      구분했다(§3.1, §3.3).
- [ ] 제품 도메인 용어는 스펙 이름을 그대로 썼고, 온보딩 서술 장치는 기존 표현을
      재사용했다(§3.4).
- [ ] 갈래별 차이표·옵션·제약은 기능 챕터에 두었다(§4.1).
- [ ] 경계를 넘은 내용을 소유 챕터로 옮겼고, 남긴 요약이 목적지를 가리킨다(§4.2).
- [ ] 같은 문서 안 참조를 앵커 링크로 걸었다(§4.3).
- [ ] 메서드·인자 설명을 코드 예제의 줄 주석에 두었다(§5.1).
- [ ] 코드 예제를 실제 샘플에서 확인했고, 생략한 옵션이 정말 선택인지 코드로
      확인했다(§5.2).
- [ ] 예시가 그 개념의 조건을 실제로 만족하는지 확인했다(§5.3).
- [ ] 개념 문서에도 다이어그램을 두었고, 담김 관계·복수성·역할 구분이 실제 구조와
      맞는지 확인했다(§5.4).
- [ ] 배경을 지정한 다이어그램 요소에 글자색을 함께 지정하고 렌더를 확인했다(§5.5).
- [ ] primitive는 primitive 이름으로, 도메인 예시는 도메인 단어로 썼다(§5.6).
- [ ] 문서 회귀 테스트가 있다면 그 금지 패턴 검사를 통과하는 API만 썼다(§2.6).

      한글 산문 문체와 원칙 6 렌더 확인을 확인했다.
