# 사용자 가이드 문서 작성 가이드

> 이 문서는 **사용자 가이드**를 쓰거나 고치는 작업자가 따르는 규칙이다. 주 독자는 문서 작업을
> 수행하는 AI다.
>
> **문장과 편집 규칙은 여기에 없다.** 문장의 형태, 용어, 예시, 표와 callout의 자리, 문서 사이
> 경계는 [기술문서 작성 원칙](documentation-principles.ko.md)이 모든 문서 공통으로 소유한다.
> 이 문서는 **가이드 종류에만 해당하는 것**을 다룬다 — 두 층, 코드 출처, 장의 형식, 점검표.

## 1. 두 층

### 1.1 기능별 가이드와 동작 원리

사용자 가이드는 두 층으로 나뉜다. 두 층은 독자가 다르고, 그래서 멈추는 지점이 다르다.

| | 기능별 가이드 | 동작 원리 |
| --- | --- | --- |
| 독자 | 이 기능을 처음 쓴다 | 이미 써 봤고, 왜 그렇게 되는지 알아야 한다 |
| 답하는 질문 | 이걸 어떻게 쓰나 | 이게 어떻게 동작하나 |
| 끝나는 지점 | 따라 하면 돌아간다 | 경계와 실패까지 안다 |
| 코드 | 붙여넣으면 실행된다 | 동작을 보이는 발췌 |
| 표 | 두지 않는다 | 종류 비교표가 여기에 있다 |

한 장이 두 질문에 모두 답하면 처음 쓰는 독자가 안 읽어도 될 내용을 통과해야 한다.
장이 길어지는 원인이 대부분 여기에 있다.

### 1.2 어느 층에 쓸지 정하는 기준

**한 번 따라 해서 돌아가게 하는 데 필요한 내용까지가 기능별 가이드다.** 종류 비교표,
종류별 차이, 옵션, 실패 분기가 등장하는 지점에서 자르고 동작 원리로 옮긴다.

> **자문:** "이 문단을 빼면 독자가 코드를 실행하지 못하나?" — 실행할 수 있으면 그
> 문단은 동작 원리에 속한다.

**두 가지는 실행에 필요 없어도 기능별 가이드에 남긴다.** 이 기능을 **언제 쓰는지**와, 잘못
쓰면 **무엇이 깨지는지**다. 앞의 것이 없으면 독자가 자기 상황에 맞는지 모른 채 따라 하고,
뒤의 것이 없으면 돌아가는 코드를 얻고도 잘못된 구성을 만든다. 둘 다 짧게 쓴다 — 종류별
비교와 옵션 표는 여전히 동작 원리로 보낸다.

경계에 걸리는 내용은 다음과 같이 나눈다.

| 내용 | 기능별 가이드 | 동작 원리 |
| --- | :---: | :---: |
| 등록과 최소 handler 하나 | O | |
| 호출 한 번과 그 결과 | O | |
| 자주 쓰는 변형 두세 개 | O | |
| 종류가 여럿이라는 사실과 기본값 | O | |
| 종류별 차이표와 선택 기준 | | O |
| lifecycle callback 전체 목록 | | O |
| 실행 순서, 동시 실행 범위 | | O |
| 옵션 표, 제약, 실패 분기 | | O |

기능별 가이드에서 종류를 언급해야 하면 **기본값 하나만 쓰고 동작 원리로 링크한다.**

### 1.3 동작 원리는 원리만 담는 곳이 아니다

"동작 원리"라는 이름 때문에 설명만 담기 쉽다. 그러나 **기능별 가이드에서 덜어 낸 상세 기능이
전부 여기로 와야 한다.** 종류별 차이, 옵션, 제약, 실패 분기, 그리고 기능 층에서 다루지 못한
API 표면까지 이 층이 받는다. 독자가 기능 층 다음에 찾아올 곳이 여기 하나뿐이기 때문이다.

한 장이 상한을 넘으면 주제로 나눈다. 예를 들어 channel은 배선·대상 선택·연결을 다루는 장과
handler·filter·codec을 다루는 장으로 나뉜다.

### 1.4 스펙 문서와 다른 점

스펙은 공개 계약을 **서술**한다. 사용자 가이드는 독자가 무엇을 왜 쓸지 **판단**하고
바로 따라 쓰게 돕는다. 정확한 계약과 가이드의 설명이 어긋나면 스펙이 이긴다 — 이 관계는 문서에 적지 않는다 — 작업자가
아는 것이지 독자가 읽을 내용이 아니다.

**배포된 동작과 스펙이 다르면 이렇게 나눈다.**

| 문서의 부분 | 무엇에 맞추는가 |
|---|---|
| 코드 예제, 실행 결과 | **지금 실행되는 것** |
| 산문 설명, 다이어그램 | 지금 실행되는 것. 목표와 다르면 그 차이를 한 문장으로 밝히고 열린 이슈를 링크한다 |

**그러나 독자를 스펙으로 내보내지 않는다.** 스펙은 작업자가 사실을 확인하는 곳이지 독자가
읽는 곳이 아니다. 가이드 본문에 "스펙에 따르면", "자세한 것은 스펙을 보라"를 쓰지 않고,
확인한 사실을 **가이드의 말로 직접 서술한다.** 독자는 그 장에서 할 일을 마칠 수 있어야 한다.

더 깊은 내용이 필요하면 스펙이 아니라 **같은 가이드의 동작 원리 장**으로 보낸다.

## 2. 작업 순서

### 2.1 입력 자료를 확인한다

1. 이 장이 다루는 기능의 공통 스펙 장을 확인한다.
2. 언어별 exact interface 문서에서 정확한 public signature를 확인한다 — 코드 예제는
   **가이드 코드는 지금 실행되는 것만 쓴다.** exact interface가 정의한 목표 계약과 배포된
   동작이 다르면, 그 차이를 본문 산문으로 밝히고 열린 이슈를 링크한다. 실행되지 않는 코드를
   예제로 싣지 않는다 — tutorial과 샘플에서 가져오는 이유가 이것이다.
3. 기능별 가이드는 tutorial 프로그램의 해당 단계와 코드를 맞춘다. 동작 원리는 실행되는
   샘플과 맞춘다([코드 예제](#4-코드-예제)).
4. 자료가 충돌하면 **사실 확인은 스펙과 exact interface를 우선한다.** 다만 문서에 싣는
   코드와 실행 결과는 지금 실행되는 것만 쓴다(아래).

장을 열 때는 **독자가 이 장에서 얻는 것**을 적는다. 소유 스펙 문서를 적지 않는다 — 스펙은
작업자가 사실을 확인하는 곳이지 독자가 읽는 곳이 아니다
([스펙 문서와 다른 점](#14-스펙-문서와-다른-점)). 머리말의 형식은
[장 머리말](#61-장-머리말)이 정한다.

### 2.2 독자의 질문으로 목차를 만든다

장은 아래 모양으로 나뉜다. 새 장을 쓸 때는 먼저 어느 모양인지 정한다.

**모양 A — 도입 판단** (개요, 경쟁 기술과의 비교)

1. 한 줄 정의, 체감 난이도
2. 상황별 문제 → 제품 기능 대응 표
3. 경계 — 이 문서가 다루지 않는 것
4. 선택을 돕는 flowchart나 기준 표
5. 실행 가능한 샘플 링크
6. 상세 비교(경쟁 기술 등, 참고용)

추천 결론을 낼 때는 적용 범위를 결론 문장 안에 넣는다("gRPC를 고민 중이라면 이 제품을
써라"가 아니라 "내부 서비스 통신을 gRPC로 고민 중이라면"처럼). 판단 기준은 기술명이
아니라 반복되는 문제 증상으로 준다. 경쟁 기술과 비교할 때는 "없는 기능"과 "훅은 있는데
미리 구현된 도구가 없는 기능"을 각각 구분해 적는다.

**모양 B — 개념·색인** (개념 문서, interface 색인)

범위 선언 → 초반 용어/메타 절 → 개념 또는 interface 그룹별 본문(코드+표) → "관련
문서". 개념 문서는 전체 용어 지도를, interface 색인은 언어별 interface를 계약 순서로
색인한다.

**모양 F — 기능별 가이드**

1. 이 기능이 푸는 문제 — 두세 문장. 표를 두지 않는다
2. 최소 동작 — 등록·handler·호출을 각각 한 덩어리씩
3. 확인 — 실행하면 무엇이 보이는지 한 줄
4. 한 가지씩 더하기 — 자주 쓰는 변형 두세 개, 각각 코드 한 덩어리
5. 다음 — 동작 원리 장 링크, 관련 문서

2번에 도달하기 전에 개념 설명이 세 문단 넘게 이어지면 코드가 늦은 것이다
([기술문서 작성 원칙 10.3](documentation-principles.ko.md)).

**모양 D — 동작 원리**

1. 무엇이 문제인가 — 이 구조가 없으면 무엇이 깨지는지
2. 어떻게 동작하나 — 다이어그램과 순서
3. 종류와 선택 기준 — 비교표가 들어가는 자리
4. 경계와 실패 — 보장하지 않는 것
5. 옵션
6. 자주 발생하는 문제 — 증상 → 원인 표
7. 관련 문서 — 같은 가이드의 다른 장, 샘플 링크. 스펙은 넣지 않는다

내용에 맞지 않는 절은 생략한다. 강제로 채우지 않는다.

### 2.3 용어를 먼저 정리한다

가이드에서 핵심 개념의 정의 자리는 스펙의 공통 용어집이 아니라 **개념 문서**의 해당
절이다. 이것이 [기술문서 작성 원칙](documentation-principles.ko.md) 원칙 2 "용어는
문서 단위로 다시 소개한다"에서 말하는 정식 정의 자리다.

**용어는 처음 필요해지는 자리에서 설명한다.** 독자가 실제로 모를 만한 용어만 그
자리에서 푼다. 문서 앞에 "자주 나오는 용어" 표를 두면 어렵지 않은 단어까지 목록에
섞여 진입 장벽만 늘어난다.

그 원칙을 그대로 적용한다: **이 장에서 그 용어가 처음 나오는 자리**에서는 한
문장으로 다시 풀고 링크한다. 같은 장 **안에서** 다시 나오면 링크 없이 이름만 쓴다.

```markdown
`session`은 연결 하나를
대표하는 상태 객체다 — 이 장에서는 연결과 session 사이의 binding만 다룬다.
```

링크 옆에는 **한 문장 설명을 함께** 둔다. 독자는 그 장만 열었을 수 있어서, "용어가
낯설면 개념 문서를 보라"는 포인터만으로는 링크를 따라가기 전까지 그 문장을 읽을 수
없다.

제품 도메인 용어는 스펙과 정확히 같은 이름을 쓴다. 가이드만의 서술 장치(체감 난이도,
자주 발생하는 문제, 샘플에서 보기, 목표 계약)는 새로 만들어도 되며, 이때도 이미
쓰이는 표현을 재사용한다.

**스펙의 내부 계약 용어는 뜻을 풀어 쓴다.** 스펙이 계약을 정밀하게 쓰려고 도입한
단어(`membership`, `authority` 등)가 가이드 산문에 설명 없이 등장하면 독자는 그
단어부터 해석해야 한다. 그 자리에서 뜻하는 바를 평이한 말로 쓴다.

| 이렇게 쓴다 | 흔한 이탈 |
| --- | --- |
| "같은 기능을 **맡은 node들**을 묶는다" | "같은 기능을 제공하는 **membership**을 묶는다" |
| "요청을 **받을 수 있는 node** 중 하나" | "ready 상태인 **membership** 중 하나" |

### 2.4 쉬운 설명부터 작성한다

절(`§1` 이하) 수준에서는 스펙과 같은 규율을 쓴다 — 정의나 결과로 문장을 시작한다.
반면 **장 진입부(`§0`)는 동기·문제 먼저**로 시작해도 된다 — 이게 스펙과의 의도적인
차이다. 독자가 이미 아는 것에서 출발해 새 개념으로 넘어가는 게 onboarding 문서의
역할이다.

```text
예(주소 자동 해석 장 §0): "지금까지 장은 연결할 endpoint를 코드에 직접
적었다. 주소 저장소를 등록하면 호출하는 쪽에서 remote endpoint 값이 사라진다."
— 문제(before) → 해결(after) 순서.
```

한 칸에 여러 판단을 담아도 되는 표는 "자주 발생하는 문제" 같은 증상 → 원인 표뿐이다
([기술문서 작성 원칙 11.3](documentation-principles.ko.md)). 표 밖의 일반 산문에서는 한 문단에 주된 판단 하나만 둔다.

같은 단어가 문맥마다 다른 뜻이면 명시적으로 구분한다
([기술문서 작성 원칙 7.15](documentation-principles.ko.md)). 예: "여기서 말하는 직렬화는 payload를 bytes로 바꾸는
codec 직렬화가 아니다. 메시지를 어떤 실행 줄에서 어떤 순서로 처리하는가를 뜻한다"처럼
짚고 넘어간다.

### 2.5 정확한 계약을 다시 대조한다

대조는 스펙처럼 절마다 항목별 대조표를 두는 대신 **interface 색인 문서** 한 곳에
모은다 — 모든 interface 그룹이 그 문서에서 검증 클래스·테스트 메서드에 연결된다. 각
기능 장은 닫는 절에서 그 절 번호와 검증 클래스를 가리키는 한 줄을 반드시 둔다.

```text
예(기능 장의 마지막 절): "이 장 계약의 실행 검증 예문은 [interface 색인] §1 —
검증 클래스 `ChannelContracts`·`HandlerContracts`·`CodecContracts`."
```

새 기능 장을 쓰거나 고칠 때는 이 포인터가 실제로 맞는 절 번호·클래스를 가리키는지
확인하는 게 가이드의 "계약 대조" 단계다.

### 2.6 링크와 자동 검증을 확인한다

- 이 장에서 처음 쓰는 용어마다 한 문장 재설명 + 개념 문서 링크가 있는지
  확인한다([용어를 먼저 정리한다](#23-용어를-먼저-정리한다)). 링크 옆에 설명이 함께
  있는지 다시 검토한다.
- **분량 상한을 넘지 않았는지 확인한다**([분량](#3-분량)). 넘으면 문체가 아니라 범위 문제이므로
  §1.2 기준으로 다시 자른다.
- 저장소에 문서 회귀 테스트가 있으면 사용자 가이드는 그 테스트로 구조적으로 검증된다.
  - 목록에 적은 파일이 모두 존재하고 nav 마커·H1을 갖췄는지(내용 정확성은 아님).
    장을 더하거나 빼면 그 목록도 함께 고쳐야 한다.
  - 이름이 바뀌었거나 제거된 API를 걸러내는 금지 패턴 grep(대체된 interface 계열,
    폐기된 callback 모양이 문서에 남아 있는지).
  - 언어 탭이 모든 지원 언어를 갖췄는지 검사하는 스크립트가 있으면 함께 돌린다.
- **장을 나누거나 절 번호를 바꾸면 다른 장이 걸어 둔 앵커가 깨진다.** 링크 검사
  스크립트를 돌려 0건을 확인한다. 앵커는 제목에서 만들어지므로 제목만 고쳐도 깨진다.
- 계약 문서에 `## 회귀 테스트` 섹션을 강제하는 저장소라면 사용자 가이드는 그 대상에서
  **제외**한다 — 온보딩 산문이지 계약 문서가 아니기 때문이다.
- 계약 검증 스크립트를 두는 저장소에서도 그 스크립트는 스펙 전용이므로 사용자 가이드를
  검사하지 않는다.
- Markdown 표·mermaid 문법을 확인하고 `git diff --check`를 실행한다.

## 4. 코드 예제

### 4.1 기능별 가이드 — tutorial 프로그램 하나에서 읽는다

기능별 가이드의 코드는 **독자가 앞 장에서 만든 것 위에 이 장의 코드를 더하면 그대로
실행되는** 상태여야 한다. 그러려면 문서가 참조하는 실제 프로그램이 있어야 한다.

언어마다 **tutorial 프로그램 하나**를 둔다. 기능별 가이드의 모든 장이 그 하나를 단계적으로
키우며, 각 장은 그 프로그램의 해당 단계에서 코드를 읽는다.

```
framework/languages/<언어>/tutorial/
```

- **quickstart와 나눠 둔다.** quickstart는 "설치부터 첫 응답까지"가 목적이라 거기에 기능을
  추가하면 그 목적이 사라진다. tutorial은 기능을 차례로 더해 가는 자리다.
- **샘플과도 나눠 둔다.** 샘플은 완결된 업무 흐름을 보이는 application이고, tutorial은
  기능마다 최소한만 담는다. tutorial이 도메인 로직을 갖기 시작하면 샘플의 축소판이 된다.
- **지원 언어의 소스 예제를 손으로 적지 않는다.** snippet 문법으로 그 파일에서 읽는다. 손으로 적은
  코드는 프로그램이 바뀌어도 함께 바뀌지 않는다.
- **구간 마커로 그 장의 코드만 읽는다.** 파일 전체를 읽으면 뒤 장에서 더한 코드까지 앞
  장에 나온다.
- **실행 결과를 한 줄로 보인다** — 응답 값, 로그 한 줄, 상태 코드 중 확인 가능한 것.

````markdown
```csharp title="Server/Program.cs"
--8<-- "framework/languages/<언어>/tutorial/Server/Program.cs:spot-register"
```
````

> **선행 조건.** tutorial 프로그램이 CI에서 빌드되지 않으면 이 규칙은 검증되지 않는 코드를
> 문서 전체의 근거로 삼는 결과가 된다. 장을 쓰기 전에 그 프로그램을 빌드 대상에 넣는다.
> 샘플을 CI에서 제외하는 저장소라도 tutorial은 예외로 둔다 — 샘플은 문서가 참조하는
> 발췌본이지만 tutorial은 문서가 성립하는 근거다.

### 4.2 동작 원리 — 샘플에서 발췌하고, 없으면 tutorial에 만든다

동작 원리의 코드는 동작을 보이는 것이 목적이므로 실행되는 샘플에서 해당 흐름을 찾아
발췌하고, 어느 샘플인지 밝힌다.

**출처는 다음 순서로 고른다.**

1. **샘플** — 그 흐름이 이미 있으면 snippet 마커를 달아 인용한다.
2. **tutorial** — 샘플에 없으면 **tutorial에 그 코드를 추가하고** 실행해 확인한 뒤 인용한다.
   가이드에 필요한 코드가 곧 tutorial이 보여야 할 기능이라는 뜻이기도 하다.
3. 그 밖의 위치에서는 가져오지 않는다.

**unit test와 e2e 프로그램에서는 가져오지 않는다.** 테스트 코드는 harness와 assertion이
섞여 있어 독자가 자기 코드로 옮길 수 있는 형태가 아니고, e2e는 완성된 기준이 아니다.

**어느 출처에서 가져오든 지어낸 코드를 섞지 않는다.** 지어낸 예제에는 컴파일되지 않는
조합이나 이미 제거된 API가 들어간다. 옵션을 생략해 예제를 줄일 때는 그 옵션이 정말
선택인지 코드로 확인한다 — 필수 옵션을 빼면 startup에서 실패하는 예제가 된다. 인용 형식은
[지원 언어 소스 예제는 snippet 참조다](#43-지원-언어-소스-예제는-snippet-참조다)가 정한다.

**기본 구현이 있는 callback을 필수처럼 보이지 않게 한다.** interface에 기본 구현이 있으면
최소 예제에서는 적지 않는다. 네 개를 모두 구현한 예제를 처음 보여주면 독자는 그것이
필수라고 판단한다.

### 4.3 지원 언어 소스 예제는 snippet 참조다

````markdown
=== "C#/.NET"

    ```csharp
    --8<-- "framework/languages/dotnet/tutorial/Server/Program.cs:mesh-register"
    ```
````

문서에 직접 적은 코드는 실행되지 않으므로 시간이 지나면 조용히 틀린다. 출처를 고르는 순서는
[코드 예제](#4-코드-예제)가 소유한다.

**여기서 "코드"는 지원 언어의 소스 예제를 뜻한다.** 다음 셋은 이 규칙의 대상이 아니다.

| 대상이 아닌 것 | 형태 |
| --- | --- |
| 실행 명령과 그 출력 | ```` ```bash ```` |
| 아직 쓰지 못한 언어 탭의 자리 표시 | §4.2의 한 줄 주석 |
| 순서·흐름을 보이는 도식 | ```` ```text ```` |

### 4.4 지원 언어 탭을 모두 둔다

`C#/.NET` · `C++` · `Java` · `Kotlin` · `Node/TypeScript` 다섯 개를 모두 둔다. 아직 쓰지
못한 탭은 **비워 두지 말고 그렇다고 적는다.**

````markdown
=== "C++"

    ```cpp
    // 이 언어 탭은 아직 작성되지 않았다.
    ```
````

검증하지 않은 코드를 채워 넣는 것보다 비어 있다고 말하는 편이 낫다.

**자리 표시는 작업 중 상태다.** 그 언어 독자에게 이 장은 아직 미완성이므로, 남아 있는 동안은
장을 "완료"로 보지 않는다. 장을 넘길 때 몇 개가 남았는지 함께 알린다.

### 4.5 언어 탭을 전제로 길이를 잡는다

지원 언어마다 탭을 두므로 코드 한 덩어리의 길이가 언어 수만큼 곱해진다. 원본에서 다섯 줄을
더하면 문서에서는 스물다섯 줄이 는다.

- **탭 하나의 코드 덩어리는 25줄 이하로 유지한다.** 넘으면 덩어리를 나누고 사이에 설명
  문장을 둔다.
- 한 절에 탭 그룹을 넷 이상 두지 않는다. 넘으면 절을 나눈다.
- 모든 지원 언어의 탭을 갖춘다. 일부 언어만 적으면 그 언어 독자에게는 미완성 문서다.

### 4.6 실행 결과는 실제로 찍어 본 값을 적는다

````markdown
### N.4 실행 결과

```bash
curl http://127.0.0.1:5080/players/p1/profile
# {"playerId":"p1","nickname":"rookie","level":1}
```
````

지어낸 출력을 적지 않는다. 실패 동작을 보여야 하면 그것도 실제로 호출해 확인한 값을 적는다.

## 5. 다이어그램

### 5.1 다이어그램을 두는 자리

**기능별 가이드는 기능마다 하나씩 둔다.** 등록과 호출 코드만 보면 무엇이 어디로 가는지
드러나지 않기 때문이다. 동작 원리 장과 개념 문서에도 둔다 — 구조·이동·선택은 그림이
문장보다 빠르다.

다이어그램을 그릴 때 확인할 것:

- **담김 관계를 실제 구조대로 그린다.** 실행 단위가 서로 포함 관계면 중첩 subgraph로
  그린다(예: process 안에 실행 단위, 실행 단위 안에 상태 객체). 나란히 놓고 화살표만
  이으면 관계가 틀리게 전달된다.
- **복수성이 개념의 일부면 복수로 그린다.** 여럿 중 하나를 고르는 동작은 후보를
  하나만 그리면 드러나지 않는다. 후보를 여럿 그리고 선택된 것을 강조한다.
- **역할이 다르면 구분해 표시한다.** client와 server, 이동 전과 이동 후처럼 역할이
  달라지는 요소는 색이나 선 굵기로 구분한다. 색이 뜻하는 바는
  [다이어그램 작성·변환 가이드](diagram-authoring-guide.ko.md) §3이 소유한다.
- **그 개념이 왜 중요한지 그림 뒤 한 문단으로 잇는다.** 구조만 보여주고 끝내면
  독자는 "그래서 뭐"에서 멈춘다.

### 5.2 mermaid로 그리고 iframe으로 바꾼다

가이드에 mermaid 블록을 그대로 남기지 않는다. 그림은 다음 순서로 만든다.

1. mermaid로 그린다. 색과 박스 제약은
   [다이어그램 작성·변환 가이드](diagram-authoring-guide.ko.md)가 정한다.
2. archify로 변환해 `framework/doc/framework/common/diagrams/`에 HTML로 둔다.
3. 본문의 mermaid 블록을 iframe으로 바꾼다.

```markdown
<iframe class="zlink-diagram" src="/common/diagrams/<name>.html" title="<그림 제목>" loading="lazy" style="width:100%;border:0"></iframe>
<p><a href="/common/diagrams/<name>.html" target="_blank">↗ 크게 보기</a></p>
```

경로는 root-absolute로 쓴다.

### 5.3 페이지당 높이 스크립트 하나

장 맨 끝에 둔다. `body.scrollHeight`를 쓰고 `documentElement`와 `Math.max`로 묶지 않는다 —
body가 내용보다 짧으면 `documentElement`가 뷰포트 높이로 늘어나 그림이 읽는 사람 화면만큼
부풀어 오른다.

### 5.4 한 장의 그림은 같은 폭으로 맞춘다

`pad-viewbox.mjs`로 그 장에서 가장 넓은 그림의 폭에 맞춘다. 다른 장의 폭에 맞추지 않는다 —
작은 그림이 불필요하게 작게 렌더된다.

### 5.5 카드는 그림만 보고 알아야 할 것만 남긴다

본문 산문이 이미 말한 내용을 카드에 반복하지 않는다. 카드가 길어지면 그림 전체가 세로로
늘어나 읽기를 방해한다.

## 6. 장의 형식

가이드 소스는 `framework/doc/framework/common/guide/server/`에 둔다. 언어별 문서
(`framework/doc/framework/<lang>/guide/server/`)는 생성물이므로 직접 편집하지 않는다.

```bash
# 공통 소스를 고친 뒤 5개 언어 문서를 다시 만든다
cd doc/site && python scripts/generate_language_guides.py
```

| 번호대 | 층 | 예 |
| --- | --- | --- |
| `01`~`19` | 개요·개념·기술 선택·색인 | `01-overview.ko.md`, `03-concepts.ko.md` |
| `20`~`29` | 기능별 가이드 | `20-channel-messaging.ko.md` |
| `30`~`39` | 동작 원리 | `30-channel-patterns.ko.md`, `31-handler-dispatch.ko.md` |
| `40`~`49` | 한 언어에만 있는 장 | `cpp/guide/server/40-di-container.ko.md` |

한 주제의 기능 층과 동작 원리 층은 **번호 끝자리를 맞추지 않는다.** 동작 원리가 둘로 나뉘면
`30`·`31`처럼 이어서 붙인다.

읽는 순서는 각 언어 README의 표가 정한다. **장을 추가하면 다섯 곳에 모두 행을 넣는다.**

```
framework/doc/framework/{dotnet,cpp,java,kotlin,node}/guide/server/README.ko.md
```

사이트 메뉴에 올리려면 `doc/site/mkdocs.yml`의 `nav`와 `nav_translations`에도 넣는다. 다만
`.en.md`가 없는 장은 nav가 해석하지 못하므로, 초안 동안에는 README 표만으로 도달한다.

### 6.1 장 머리말

장은 제목, "이 장을 읽고 나면" callout, 도입 산문 순으로 연다.

````markdown
# <장 제목>

!!! info "이 장을 읽고 나면"

    <이 장을 읽은 뒤 할 수 있게 되는 일 한두 문장.>
    <이 장 코드의 출처 한 문장.>

<도입 산문 2~4줄. 이 장이 다루는 범위와, 다루지 않고 넘기는 것.>
````

**기능별 가이드는 첫 코드가 첫 화면에 보여야 한다.** 표나 긴 도입부가 첫 코드를 화면
밖으로 밀어내면 독자는 그 장을 어려운 문서로 판단한다.

### 6.2 절에 번호를 달고, 기능마다 한 절을 둔다

`##` 절에 `1.` `2.` 같은 번호를, `###` 절에 `1.1` `1.2` 같은 번호를 단다. 번호는 장마다
`1`부터 센다. 파일 이름의 번호대와는 무관하다.

패턴이나 기능이 여럿이면 **하나마다 한 절**을 두고, 그 절 안에서 그림과 코드가 이어지게 한다.
그림을 따로 모으지 않는다.

### 6.3 받는 쪽과 호출하는 쪽을 소제목으로 가른다

한 기능을 handler 등록과 호출 두 방향으로 보일 때는 **각각 한 절**을 두고, 소제목에 어느
방향인지 적는다. 뒤 절 첫 문장에 앞 절과 짝이라는 것을 적는다.

```markdown
### 3.2 받는 쪽 — handler를 등록한다
### 3.3 호출하는 쪽 — 같은 채널 이름으로 부른다
```

한 절 안에 두 방향의 코드를 섞지 않는다. 독자가 지금 보는 코드가 어느 쪽인지 잃는다.

### 6.4 절 참조는 실제 링크로 쓴다

```markdown
[Spot·Actor 호출하기](#37-spotactor-호출하기)
```

`(§3.7)` 같은 표기를 쓰지 않는다. 번호만으로는 어디로 가는지 알 수 없고, 절 번호가 바뀌면
본문이 조용히 틀린다. **링크 글자는 절 번호가 아니라 절 이름**으로 쓴다.

금지 대상은 **같은 장 안을 가리키는 맨 번호**다. 다른 문서를 가리킬 때는 문서 이름과 절
이름을 함께 쓴다 — `[기술문서 작성 원칙 7.9](...)`처럼 링크 글자에 번호가 들어가는 것은
그 문서의 절이 안정된 식별자이므로 허용한다.

### 6.5 제목을 고치면 앵커를 함께 고친다

앵커 id는 제목에서 생성되므로 제목을 바꾸면 그 절을 가리키던 링크가 깨진다. 장을 마칠 때
렌더된 페이지에서 `href="#..."`의 대상이 실재하는지 센다.

### 6.6 본문에서 스펙으로 내보내지 않는다

"자세한 것은 스펙을 보라"로 끝내지 않는다. 독자가 그 장에서 할 일을 마칠 수 있어야 한다.
더 깊은 내용이 필요하면 **같은 가이드의 동작 원리 장**으로 보낸다.

### 6.7 용어를 처음 쓰는 자리

처음 나오는 용어를 그 자리에서 한 줄로 정의하는 규칙은
[기술문서 작성 원칙](documentation-principles.ko.md)이 소유한다. 가이드에서 정의할 대상을
고르는 기준은 [용어를 먼저 정리한다](#23-용어를-먼저-정리한다)에 있다.

## 7. 완료 점검표

장을 마칠 때 아래 점검표를 돌린다. 기계로 세는 항목과 읽고 판단하는 항목을 함께 둔다.

### 7.1 층과 경계

- [ ] 이 장이 기능별 가이드인지 동작 원리인지 정했다([두 층](#11-기능별-가이드와-동작-원리)).
- [ ] "이 문단을 빼면 독자가 코드를 실행하지 못하나"로 경계를 확인했다. 종류 비교표·옵션·
      실패 분기를 동작 원리로 보냈고, **언제 쓰는지와 잘못 쓰면 무엇이 깨지는지는 남겼다**
      ([어느 층에 쓸지 정하는 기준](#12-어느-층에-쓸지-정하는-기준)).
- [ ] 기능 층에서 덜어 낸 상세가 동작 원리 장에 실제로 들어갔다
      ([동작 원리는 원리만 담는 곳이 아니다](#13-동작-원리는-원리만-담는-곳이-아니다)).
- [ ] 경계를 넘은 내용을 소유 장으로 옮겼고, 남긴 요약이 목적지를 가리킨다
      ([기술문서 작성 원칙 2.2](documentation-principles.ko.md)).

### 7.2 문장

- [ ] [기술문서 작성 원칙 10.1](documentation-principles.ko.md)의 열 가지 형태로 썼다 —
      정의 한 문장, 역할 먼저, 행위자를 주어로, 이웃과 비교, 순서와 경계, 조건과 결과,
      코드 앞뒤 한 문장, 이유는 절로, 볼드는 판단이 달라지는 말에만, 한 문장에 한 가지.
- [ ] 처음 들이는 개념은 동작을 먼저 보이고 이름을 뒤에 붙였다
      ([기술문서 작성 원칙 7.2](documentation-principles.ko.md)).
- [ ] 2인칭 지시·권유형·구어 강조를 쓰지 않았다
      ([기술문서 작성 원칙 7.7](documentation-principles.ko.md)).
- [ ] 곁가지를 callout으로 분리하고 제목을 달았다
      ([기술문서 작성 원칙 11.2](documentation-principles.ko.md)).
- [ ] 둘의 비교는 산문으로, 셋 이상이나 항목이 여럿이면 표로 썼다
      ([기술문서 작성 원칙 11.3](documentation-principles.ko.md)).

### 7.3 코드

- [ ] 기능별 가이드는 tutorial에서, 동작 원리는 샘플 → tutorial 순서로 가져왔다. unit test와
      e2e에서 가져오지 않았다([기능별 가이드](#41-기능별-가이드--tutorial-프로그램-하나에서-읽는다),
      [동작 원리](#42-동작-원리--샘플에서-발췌하고-없으면-tutorial에-만든다)).
- [ ] 샘플에 없어 tutorial에 추가한 코드는 **실행해 확인했다**
      ([동작 원리](#42-동작-원리--샘플에서-발췌하고-없으면-tutorial에-만든다)).
- [ ] 생략한 옵션이 정말 선택인지 코드로 확인했다. 기본 구현이 있는 callback을 최소 예제에
      적지 않았다([동작 원리](#42-동작-원리--샘플에서-발췌하고-없으면-tutorial에-만든다)).
- [ ] 메서드·인자 설명을 코드 예제의 줄 주석에 두었다
      ([기술문서 작성 원칙 4.3](documentation-principles.ko.md)).
- [ ] 예시가 그 개념의 조건을 실제로 만족하는지 확인했다
      ([기술문서 작성 원칙 4.2](documentation-principles.ko.md)).

### 7.4 용어

- [ ] 실제로 모를 만한 용어만, 그 용어가 필요해지는 자리에서 설명했다
      ([용어를 먼저 정리한다](#23-용어를-먼저-정리한다)).
- [ ] 스펙의 내부 계약 용어(membership, authority 등)를 평이한 말로 풀었다
      ([용어를 먼저 정리한다](#23-용어를-먼저-정리한다)).
- [ ] 뜻이 겹치는 단어와 철자가 비슷한 public 식별자를 명시적으로 구분했다
      ([기술문서 작성 원칙 7.15](documentation-principles.ko.md)).
- [ ] 제품 도메인 용어는 스펙 이름을 그대로 썼다
      ([기술문서 작성 원칙 7.16](documentation-principles.ko.md)).
- [ ] 예시의 근거가 샘플에 있고, 독자를 문서 밖으로 내보내지 않는다
      ([기술문서 작성 원칙 4.1](documentation-principles.ko.md)).

### 7.5 스펙과의 관계

- [ ] 사실은 스펙과 exact interface로 확인했다([입력 자료를 확인한다](#21-입력-자료를-확인한다)).
- [ ] 본문이 스펙을 근거로 들거나 스펙으로 내보내지 않는다
      ([스펙 문서와 다른 점](#14-스펙-문서와-다른-점)).
- [ ] 배포된 동작과 목표 계약이 다르면 그 차이를 밝히고 열린 이슈를 링크했다
      ([스펙 문서와 다른 점](#14-스펙-문서와-다른-점)).

### 7.6 다이어그램

- [ ] 기능마다, 그리고 동작 원리와 개념 문서에 다이어그램을 두었다
      ([다이어그램을 두는 자리](#51-다이어그램을-두는-자리)).
- [ ] 담김 관계·복수성·역할 구분이 실제 구조와 맞는지 확인했다
      ([다이어그램을 두는 자리](#51-다이어그램을-두는-자리)).
- [ ] mermaid 블록을 archify로 변환해 iframe으로 바꾸었고, 렌더를 확인했다
      ([mermaid로 그리고 iframe으로 바꾼다](#52-mermaid로-그리고-iframe으로-바꾼다)).
- [ ] primitive는 primitive 이름으로, 도메인 예시는 도메인 단어로 썼다
      ([기술문서 작성 원칙 4.4](documentation-principles.ko.md)).

### 7.7 기계로 세는 것

아래는 모두 파일이나 렌더된 페이지에서 세어 확인한다. 앵커 검사는 렌더된 페이지에서
`article` 안의 `href="#..."`를 모아 대상 id가 실재하는지 본다.

- [ ] 머리말이 `!!! info "이 장을 읽고 나면"`으로 시작한다([장 머리말](#61-장-머리말)).
- [ ] 본문에 `spec/server` 링크가 0개다
      ([본문에서 스펙으로 내보내지 않는다](#66-본문에서-스펙으로-내보내지-않는다)).
- [ ] 소스 예제 코드 블록이 전부 `--8<--` 참조다
      ([snippet 참조](#43-지원-언어-소스-예제는-snippet-참조다)).
- [ ] 각 탭 그룹에 다섯 언어가 모두 있다([지원 언어 탭](#44-지원-언어-탭을-모두-둔다)).
- [ ] 남아 있는 자리 표시 탭의 개수를 센다([지원 언어 탭](#44-지원-언어-탭을-모두-둔다)).
- [ ] 그림 폭이 그 장 안에서 같고([같은 폭](#54-한-장의-그림은-같은-폭으로-맞춘다)),
      높이 스크립트가 하나다([높이 스크립트](#53-페이지당-높이-스크립트-하나)).
- [ ] 같은 장 안을 가리키는 `§번호` 표기가 0개다
      ([절 참조는 실제 링크로 쓴다](#64-절-참조는-실제-링크로-쓴다)).
- [ ] 렌더된 페이지의 `href="#..."` 대상이 모두 실재한다
      ([제목을 고치면 앵커를 함께 고친다](#65-제목을-고치면-앵커를-함께-고친다)).
- [ ] 분량이 상한 안이다([세는 방법](#32-세는-방법)).

### 7.8 사람이 보는 것

- [ ] 기능이 여럿이면 하나마다 한 절이고, 그 절 안에 그림과 코드가 함께 있다
      ([절에 번호를 달고, 기능마다 한 절을 둔다](#62-절에-번호를-달고-기능마다-한-절을-둔다)).
- [ ] 받는 쪽·호출하는 쪽이 각각 한 절이고 소제목에 방향이 적혀 있다
      ([받는 쪽과 호출하는 쪽](#63-받는-쪽과-호출하는-쪽을-소제목으로-가른다)).
- [ ] 제목이 [기술문서 작성 원칙 7.9](documentation-principles.ko.md)의 형태를 따른다.
- [ ] 실행 결과가 실제로 찍어 본 값이다
      ([실행 결과](#46-실행-결과는-실제로-찍어-본-값을-적는다)).
- [ ] 이 제품의 개념어가 처음 나올 때 그 자리에서 정의된다
      ([용어를 처음 쓰는 자리](#67-용어를-처음-쓰는-자리)).
