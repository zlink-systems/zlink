# 스펙 문서 작성 가이드

> 이 문서는 한 주제의 **공개 계약과 그 구현**을 함께 서술하는 권위 있는 스펙 문서를
> 작성하거나 수정하는 작업자가 따르는 절차다. 주 독자는 문서 작업을 수행하는 AI다.
>
> 목표는 정확한 계약과 그 구현을 처음 읽는 개발자와 유지보수자도 이해할 수 있게 설명하는
> 것이다. 정해진 문서 모양을 만드는 것이 목표가 아니다. 한 문서 안의 계약 서술과 구현
> 서술은 코드와 어긋났을 때 고치는 방향이 반대이므로 §4.4로 구분한다.

[기술문서 작성 원칙](documentation-principles.ko.md) ·
[사용자 가이드 문서 작성 가이드](guide-writing-guide.ko.md)

## 1. 완료 결과

완성된 스펙은 다음 독자가 외부 초안이나 구현 코드를 다시 읽지 않아도 공개 동작을
판단할 수 있어야 한다.

- 제품과 각 언어 binding을 구현하는 개발자
- Public interface와 contract test를 검토하는 개발자
- 기능을 사용하는 application 개발자

문서를 읽은 독자는 다음 질문에 답할 수 있어야 한다.

| 질문 | 문서가 제공해야 하는 답 |
|---|---|
| 이 기능은 무엇을 하는가? | Application에서 관찰할 수 있는 결과를 설명한다. |
| 누가 무엇을 결정하는가? | Application, runtime, provider와 remote runtime의 책임을 구분한다. |
| 정상 처리는 어떤 순서인가? | 입력부터 완료까지 상태 확인과 변경 순서를 설명한다. |
| 어떤 값이 판단 기준인가? | Identity, generation, 저장 record와 상태의 역할을 설명한다. |
| 언제 완료되는가? | Queue 수락, remote 전달, handler와 reply 완료를 구분한다. |
| 실패하면 무엇이 남는가? | 반환 오류, 유지하는 상태, 재시도와 정리 규칙을 설명한다. |
| 제한은 어디에 적용되는가? | 시스템, object, record, payload와 memory 제한을 구분한다. |

이 질문에 답하려고 용어집을 먼저 읽거나 여러 절의 문장을 조합해야 한다면 아직
완료되지 않은 문서다. 용어집과 exact interface는 세부 내용을 확인하는 자료이며
본문의 기본 설명을 대신하지 않는다.

## 2. 작업 순서

AI는 다음 순서를 지킨다. 계약을 먼저 확인하고, 확인한 계약 위에 문장을 쓴다.

### 2.1 입력 자료를 확인한다

1. 수정 대상 문서가 소유하는 공개 계약 범위를 확인한다.
2. 관련 공통 스펙과 언어별 exact interface를 확인한다.
3. 용어집에서 사용할 용어의 정의를 확인한다.
4. 구현, E2E와 이전 문서는 누락을 찾는 증거로만 사용한다.
5. 서로 다른 자료가 충돌하면 정식 계약의 소유 문서를 확인해 어느 쪽이 계약인지 판정한다.

현재 계약으로 적는 public 동작은 정식 스펙에 있는 것으로 한정한다. 구현에만 있는 동작이
필요하면 공개 계약 관리 절차에 따라 설계를 먼저 확정하고, 확정된 뒤에 적는다. 이 규칙은
계약 서술에 적용한다 — 구현 서술은 확정된 구현을 따라가므로 §4.4를 따른다.

### 2.2 독자의 질문으로 목차를 만든다

절은 독자가 순서대로 묻게 될 질문을 기준으로 나눈다 — 기능 이름이나 내부 class
이름이 아니라.

공개 operation을 설명할 때는 다음 순서를 출발점으로 사용할 수 있다.

1. 범위와 Application에서 보이는 결과
2. 역할과 책임
3. 입력, identity와 대상 선택
4. 정상 처리 순서
5. 동시 요청과 상태 변경
6. 완료, 실패와 cancellation
7. 수명, 정리와 shutdown
8. 구현 및 contract test 검증 요구

자료구조는 `작은 예 → 구성 요소 → 읽기·변경 규칙 → 실패` 순서가 더 적합하다.
여러 방식을 비교할 때는 `공통 목적 → 차이 표 → 방식별 상세` 순서를 사용한다.
목차는 문서마다 그 내용에 맞는 순서를 고른다.

**문서 묶음은 주제 디렉터리로 나누고, 번호는 주제 안에서 다시 시작한다.** 디렉터리는
`NN-주제/`로, 그 안의 문서는 `NN-slug.md`로 이름 붙이며 주제마다 `01`부터 센다. 주제 진입
문서는 번호 없이 `README`로 둔다. 문서 묶음 전체를 관통하는 전역 번호는 주제 순서와 곧
어긋나므로 파일 이름에 남기지 않는다.

**모든 문서의 제목 아래와 본문 끝에 같은 내비게이션 줄을 둔다.** 주제 목차, 상위 목차,
그리고 주제 안의 이전·다음 문서를 링크한다. 긴 문서를 끝까지 읽은 독자가 위로 돌아가지 않고
다음 문서로 넘어갈 수 있어야 한다.

```markdown
[Session 주제 목차](README.md) · [스펙 목차](../README.md) · [다음: 02. …](02-….md)
```

**문서 전체 형태는 개념을 먼저, 선언과 레퍼런스를 뒤로 둔다.** 첫 부분은 "이것이 무엇이고
무엇을 소유하는가"(개요)와 관련 계약 소유 문서를 밝히고, 이어서 동작과 개념을 설명한다.
enum·상수·struct·함수 signature 같은 **선언과 옵션·함수 레퍼런스는 개념 뒤 절로 내리고**,
문서 **마지막에 검증 요구 절**(§9.3)을 둔다. 독자가 "무엇을 하는지"를 먼저 이해한 뒤 정확한
표면을 참조하게 한다. 개요 절의 제목은 "이 문서가 정의하는 범위"처럼 문서를 가리키는 메타
문구 대신 그 주제 이름(예: "Context 개요")으로 달아, 첫 blockquote와 겹쳐 읽히지 않게 한다.

### 2.3 용어를 먼저 정리한다

초안에 사용할 영어 명사와 제품 개념을 목록으로 만든다.

- Public identifier인가?
- 업계에서 같은 의미로 널리 사용하는 용어인가?
- 제품 전용 용어라면 용어집에 있는가?
- 같은 철자를 현재 문서에서 한 가지 의미로만 쓰는가?

용어집에 등록된 표현을 쓴다. 동작을 쉬운 문장으로 풀 수 있으면 그 문장을 쓰고,
반복해서 구분해야 하는 개념이면 §3.4에 따라 용어집부터 수정한 뒤 사용한다.

### 2.4 쉬운 설명부터 작성한다

각 절은 결과나 질문의 답으로 시작한다. 내부 record, protocol command와 helper
이름은 그 결과를 설명하는 데 필요한 자리에서 쓴다.

한 문단에는 주된 판단 하나만 둔다. 다음 항목이 바뀌면 문단을 나누거나 비교 표를
사용한다.

구현이 따라야 하는 구조 규칙을 그 이유와 함께 적을 때는 **굵은 규칙 문장 + 이유** 불릿으로
쓴다. 규칙이 여러 개 이어지면 한 목록으로 묶는다. "결정"이나 "규칙" 같은 라벨은 붙이지
않는다(§4.4).

```markdown
- **Framework는 queue admission이 실패한 동안 새 packet을 읽지 않는다.** 넣을 수 없는
  상태에서 receive를 계속하면 Core receive pipe의 HWM이 backpressure 경계로 동작하지 않기
  때문이다.
```

- 동작 주체
- 처리 단계
- 정상 조건과 실패 조건
- 저장하는 정보
- 수치가 적용되는 범위

### 2.5 한 덩어리로 뭉친 서술을 나눈다

규칙을 빠짐없이 적었는데도 읽히지 않는 문단이 있다. 대개 여러 판단이 한 덩어리에
들어가 독자가 어디서 끊어 읽을지 알 수 없기 때문이다. 다음 넷 중 하나에 해당하면 나눈다.

| 신호 | 나누는 방법 |
|---|---|
| 한 문단·불릿에 독립된 판단이 셋 이상 | 판단마다 문단을 나누고, 묶음이 커지면 소제목(`###`)을 단다 |
| 순서가 있는 절차가 산문 한 덩어리 | 번호 목록으로 편다. 각 항목은 한 주체가 하는 한 동작 |
| 조건마다 결과가 갈리는데 산문 | 비교 표로 바꾼다(§7.1) |
| 설명 없는 용어가 문장의 주어 | 하는 일을 먼저 쓰고 이름을 뒤에 붙인다(§3.1) |

나누는 것은 **문장을 옮기는 일이지 다시 정하는 일이 아니다.** 수치·상태·오류 값·순서·부정
규칙이 하나라도 달라지면 나누기에 실패한 것이다. 특히 순서가 있는 절차를 목록으로 펼 때는
편 뒤에 원문과 단계를 하나씩 대조한다.

과하게 나누지 않는다. 판단이 하나뿐인 문단은 길어도 그대로 둔다. 소제목이 세 문장마다
나오면 독자는 흐름을 잃는다.

**이렇게 나눈다** — 판단 넷이 한 불릿에 있던 자리:

> - **Instance Spot은 Actor membership이 없는 Spot kind다.** Missing Instance 생성은 Spot
>   direct fluent call의 명시적인 Instance intent만 시작한다. Location Store reservation이
>   정한 owner 하나가 factory를 실행하고 durable activation inbox first record를 확정한 뒤
>   recovery root·cursor를 포함한 location `Ready`를 commit한다. …

정의 한 문장, 생성을 시작하는 조건 한 문단, 그리고 경쟁이 하나로 수렴하는 절차를 번호
목록으로 나눈다. 목록의 각 항목은 "누가 무엇을 한다" 형태가 된다.

### 2.6 정확한 계약을 다시 대조한다

초안을 쓴 뒤 입력 자료와 항목별로 대조한다.

| 확인 영역 | 확인할 계약 |
|---|---|
| 입력 | Required·optional 값, 형식, 범위와 중복 설정 |
| 대상 선택 | 조회 순서, 후보 조건과 caller가 지정할 수 없는 값 |
| 정상 흐름 | 생성, 초기화, 상태 변경과 최초 message 처리 순서 |
| 경쟁 처리 | 동시 요청이 하나로 수렴하는 조건 |
| 완료 | Send 수락, remote queue, handler와 reply의 관계 |
| 실패 | Status, exception, timeout, cancellation과 shutdown |
| 수명 | 새 작업 차단, 이미 수락한 작업과 resource 정리 |
| 검증 | 구현과 contract test가 확인할 조건 |

대조가 끝난 문서의 수치·상태·실패 규칙은 입력 자료와 같은 집합이어야 한다. 문장을
자연스럽게 만들려고 규칙을 덜어내거나, 이해를 돕는다는 이유로 입력 자료에 없는 보장을
더하면 대조 실패로 본다. 다음도 같은 실패다.

- 입력 자료가 번호만 준 command나 값에 이름을 지어 붙인다(`reserved command 45`에 이름을 만드는 것).
- 입력 자료의 이유 문장을 더 강한 주장으로 바꾼다("만족하지 못한다" → "유일한 방법이다").
- 관계를 설명하려고 입력 자료에 없는 방향·개수·소유 문장을 새로 만든다.

이전 문서를 대체하는 재작성에서는 규칙마다 새 문서의 위치를 적는 대장을 만들되, 대장에
적었다는 사실을 완료로 보지 않는다. 규칙의 핵심 문구를 새 문서에서 grep으로 실물 확인한
뒤에만 그 행을 완료로 표시한다.

### 2.7 링크와 자동 검증을 확인한다

1. 각 용어의 첫 설명에 용어집 링크가 있는지 확인한다.
2. 관련 계약 링크가 정식 스펙을 가리키는지 확인한다.
3. Markdown 표, code fence와 diagram 문법을 확인한다.
4. `git diff --check`를 실행한다.
5. 저장소에 문서 계약 검증 스크립트가 있으면 실행한다.

자동 검사는 의미를 대신 검토하지 않는다. 검사가 통과해도 처음 읽는 독자가 §1의
질문에 답할 수 없으면 문장을 다시 작성한다.

## 3. 용어 작성 규칙

### 3.1 동작을 설명한 문장에서 용어를 소개한다

독자가 그 용어를 처음 본다고 보고 쓴다. 무엇을 하는지 먼저 설명하고, 같은 문장에서
용어 이름을 붙인다. 공개 계약을 설명하는 데 필요한 이름만 남긴다.

이렇게 쓴다:

> 대상 node에 현재 그 객체가 없으면 위치 저장소에 객체를 만들어도 되는지 요청한다.
> 여러 대상이 동시에 요청해도 생성 권한을 먼저 확보한 대상만 자신을 owner로 기록하고
> 객체를 만든다.

흔한 이탈 — 내부 이름만으로 동작을 대신한 문장:

> Target runtime은 local exact instance가 없으면 placement reservation을 획득하고
> CAS winner만 owner claim을 만든다.

### 3.2 용어집 정의와 첫 링크

용어집은 여러 스펙이 공유하는 용어 정의의 기준이다.

각 문서에서 용어집 용어를 처음 사용할 때는 다음 두 조건을 함께 만족한다.

1. 현재 문맥에서 하는 일을 쉬운 문장으로 설명한다.
2. 용어 이름을 용어집의 정확한 항목에 연결한다.

```markdown
실행 중인 instance가 없을 때 새로 만들고 초기화하는 과정을
[cold activation](glossary.ko.md#cold-activation)이라고 한다.
```

문서에서 한 번만 사용하는 용어도 링크한다. 같은 문서 안에서 두 번째부터는 이름만 쓴다.
다른 문서는 독립적으로 읽어야 하므로 그 문서의 첫 사용에서 다시 설명하고 링크한다 —
[기술문서 작성 원칙](documentation-principles.ko.md) 원칙 2 "용어는 문서 단위로 다시
소개한다"를 용어집에 적용한 것이다.

**흔한 이탈 — 문서 맨 앞에 용어를 표로 모아 둔다.** 용어 정의는 그 용어가 처음 나오는
문장에서 풀어 설명하고 용어집에 링크한다. 맨 앞 "용어" 표는 독자가 아직 맥락 없이 정의를
외우게 만들고, 용어집과 중복돼 drift가 생긴다. 정의의 기준은 용어집 한 곳이며, 개별 스펙은
첫 사용 자리에서 그 자리에 맞는 한 문장으로 소개하고 링크만 건다.

제목, 목차, interface signature와 code block은 첫 사용 판단에서 제외할 수 있다.
본문의 public identifier, 상태와 오류 값은 용어집 항목이 있으면 첫 사용 판단에 포함한다.

용어집 링크에는 그 자리에서 하는 일을 설명하는 한 문장을 함께 둔다. 현재 문서의
설명이 용어집과 다르면 다음 중 하나로 고친다.

- 같은 개념이면 용어집 정의와 문서를 같은 뜻으로 맞춘다.
- 서로 다른 개념이면 이름과 용어집 항목을 분리한다.
- 현재 문서에 필요 없는 용어면 제거하고 동작을 풀어서 쓴다.

예를 들어 객체가 그룹에 속하는 관계와 node가 채널에 참여하는 관계가 다르면 각각 다른
이름과 정의를 쓴다. 두 관계를 같은 `Membership`으로 연결하면 독자는 두 관계를 같은
규칙으로 읽는다.

### 3.3 정식 식별자와 업계 용어

Public type, method, field, wire 값, status와 error 이름은 선언된 그대로 쓴다. 이름
바로 옆에 caller가 관찰하는 의미를 설명한다.

```text
`RuntimeShutdown`: runtime이 종료 중이어서 새 operation을 받지 않는다.
```

한글 산문의 어휘 선택은 [기술문서 작성 원칙](documentation-principles.ko.md) 원칙 7을
따른다 — 특히 7.3의 "널리 쓰지 않는 한자어 대신 익숙한 영어 또는 쉬운 말"(예: "정본" 대신
"이 규칙을 소유하는 문서").

API, callback, transaction과 cache처럼 업계에서 널리 쓰는 용어도 현재 문맥에서
무엇을 하는지 처음에 설명한다. 업계 용어인지 확실하지 않으면 새 제품 용어로
간주하고 쉬운 문장으로 바꾼다.

`descriptor`, `target`, `owner`처럼 기능에 따라 의미가 달라지는 단어는 구체적으로
쓴다.

| 이렇게 쓴다 | 흔한 이탈 |
|---|---|
| node descriptor, server descriptor | descriptor |
| 선택한 target node, 현재 owner 객체 | target |
| 그룹의 member 객체, 채널 server member | member |

### 3.4 새 제품 용어

다음 조건을 모두 만족할 때만 새 용어를 추가한다.

- 기존 public identifier나 업계 용어로 정확히 설명할 수 없다.
- 여러 문서나 API에서 같은 개념을 반복해서 구분해야 한다.
- 이름을 붙이는 편이 동작을 반복해서 설명하는 것보다 이해하기 쉽다.
- 다른 용어와 의미가 겹치지 않는다.

새 용어가 필요하면 용어집에 먼저 다음 내용을 기록한다.

| 항목 | 기록할 내용 |
|---|---|
| 쉬운 정의 | 무엇을 나타내고 왜 필요한지 설명한다. |
| 형태 | 단일 값, 복합 값, 상태 또는 동작인지 밝힌다. |
| 공개 구성 | Field, 형식, 길이와 값의 범위를 적는다. |
| 생성·관리 | 값을 만드는 주체와 uniqueness 범위를 적는다. |
| 전달 | 어느 request, reply, 저장 record나 상태에 포함되는지 적는다. |
| 수명 | 언제부터 유효하고 언제 사용할 수 없게 되는지 적는다. |
| Application 권한 | Application이 생성·해석·변경할 수 있는지 적는다. |

실제 public type이 있으면 exact interface의 선언을 그대로 사용한다. 독립된 public
type이 없으면 `public type 없음`이라고 쓴다. 설명용 선언은 `contract
pseudocode이며 실제 API가 아니다`라고 명시한다.

이름 없이 설명해도 충분하면 용어집 항목과 본문 용어를 함께 걷어낸다 — 용어집에
등록했다는 사실 자체는 그 용어를 쓸 근거가 되지 않는다.

### 3.5 압축한 명사구 대신 동작 문장을 쓴다

여러 구현 동작을 영어 명사로 묶은 표현 대신, 각 동작이 무엇을 하는지 문장으로 쓴다.

이렇게 쓴다:

> Target은 위치 저장소에서 현재 owner를 다시 확인한다. 이동 대상 목록과 저장한
> payload 목록이 모두 일치하면 복원을 시작한다. 복원이 끝나면 이동 중에만 사용한
> 정보를 제거한다.

흔한 이탈 — 동작들을 영어 명사로 묶어 새 개념처럼 쓴 문장:

> Target은 closed owner rule과 participant projection을 확인한 뒤 steady
> normalization을 수행한다.

`canonical`, `exact`, `bounded`, `projection`, `fence`, `root`, `manifest`,
`admission`, `normalization`, `handoff`를 쓸 때는 무엇이 일치하는지, 무엇을
제한하는지, 어떤 값을 가리키는지, 어떤 상태가 바뀌는지를 문장으로 밝힌다. 이
단어들을 다른 명사와 이어 붙이면 그 정보가 모두 사라진다.

**`exact`는 특히 자주 이 방식으로 쓰인다.** 같은 철자가 문맥마다 다른 뜻을 감춘다.

| `exact`가 감춘 뜻 | 이렇게 쓴다 |
|---|---|
| 값을 그대로 비교한다(대소문자 구분, 정규화 없음) | "대소문자를 구분해 그대로 비교하는 값이다" |
| 같은 ID의 다른 것이 아니라 바로 그 대상이다 | "교체 대상인 그 binding", "지정한 target" |
| 특정 버전·세대만 받아들인다 | "같은 generation일 때만" |
| 이름 앞에 붙어 문서 종류를 가리킨다 | 그 종류를 그대로 부른다("언어별 interface") |

## 4. 문서 구조와 책임 경계

### 4.1 결과와 범위를 먼저 쓴다

첫 단락에서 이 문서가 답하는 질문과 Application에서 관찰할 결과를 말한다. 내부
component 목록과 구현 배경은 그것이 필요한 절로 내린다.

```text
이 문서는 객체 ID로 message를 보낼 때 runtime이 현재 owner를 찾고,
그 객체의 queue에 message를 제출하는 방법을 정의한다.
```

첫 부분에는 가능하면 다음 책임을 함께 구분한다.

| 주체 | 설명할 내용 |
|---|---|
| Application | 지정할 수 있는 값과 호출하는 API |
| Runtime | 자동으로 조회·선택·저장하는 값 |
| Provider | 반드시 구현해야 하는 저장·전송 계약 |
| Remote runtime | 다시 검증하는 상태와 handler 실행 조건 |

### 4.2 다른 문서가 소유한 계약은 링크로 가리킨다

현재 문서가 보장할 결과만 설명한다. 세부 동작을 다른 정식 스펙이 소유하면 현재
문서에는 경계를 이해하는 데 필요한 결과와 그 문서 링크를 둔다.

공개 보장으로 적는 것은 정식 스펙이 소유한 계약뿐이다. 관련 정식 문서가 아직 없으면
그 사실을 적고, 계약이 확정된 뒤에 링크한다 — 구현 코드에서 읽은 내부 알고리즘이나
폐기 예정 문서는 계약의 출처가 아니다. 이 문서가 구현을 함께 서술할 때 그 구현 서술은
공개 보장이 아니라 현재 상태다 — 두 서술의 방향은 §4.4가 구분한다.

### 4.3 요약·상세·검증에 각각 다른 층을 둔다

같은 규칙은 한 층에서만 쓰고, 나머지 층은 그 층을 가리킨다.

- 요약에는 결과와 큰 흐름만 둔다.
- 상세 절에는 조건, 순서, 상태와 수치를 둔다.
- 검증 절에는 구현이나 test가 확인할 관찰 가능한 결과만 둔다.
- Checklist에는 누락 여부를 묻는 문장을 둔다.

앞 절의 설명이 다시 필요하면 그 절을 링크한다.

### 4.4 계약 서술과 구현 서술

한 스펙 문서는 두 종류의 문장을 함께 담는다. 하나는 caller가 의존하는 **계약**을 서술하고,
다른 하나는 그 계약을 **구현이 어떻게 달성하는지** 서술한다. 두 문장은 코드와 어긋났을 때
고치는 방향이 반대이므로, 어느 쪽인지 밝힌다([원칙 4](documentation-principles.ko.md)).

| 문장 종류 | 서술 대상 | 코드와 다를 때 |
|---|---|---|
| 계약 서술 | signature, result, errno, ownership, timeout, thread safety, 관찰 가능한 값과 제한 | 코드를 고친다 — 문서가 목표다 |
| 구현 서술 | thread·queue·lock·buffer 배선, codec 절차, 저장 record 변경 순서, source 구획 | 문서를 고친다 — 코드가 사실이다 |

계약 서술은 구현이 도달해야 할 목표이므로 구현이 확정되기 전에도 현재형으로 쓴다. 구현
서술은 확정된 구현을 따라가므로 구조가 확정된 뒤에 쓰고, 구현이 바뀌면 문서를 코드에
맞춘다. 같은 규칙을 두 서술에 중복해서 쓰지 않는다 — 계약은 계약 서술에, 그 실현 방법은
구현 서술에 한 번씩만 둔다.

**여러 runtime이 공통으로 따르는 구현 규칙은 계약 서술과 같은 방향이다.** 같은 계약을
서로 다른 언어의 runtime이 각각 구현할 때, 한 runtime의 선택이 아니라 모든 runtime이
따라야 하는 구조 — 예를 들어 owner를 가져올 때 배타권을 함께 가져오는 것, 관측이 실행
권한을 점유하지 않는 것 — 는 계약 문장과 같은 평서문으로 쓰고, 코드가 다르면 코드를 고친다.
스펙의 문장은 모두 결정이므로 "결정"이라는 표시를 따로 붙이지 않는다. 표시가 필요한 쪽은
반대다 — 그 규칙 아래에서 **언어마다 달라도 되는 방법**만 `**언어별 재량**`으로 표시하고,
위 표의 구현 서술처럼 코드를 사실로 삼는다. 재량으로 적으려면 관찰 결과가 왜 같은지와
그것을 확인하는 기준을 함께 적는다 — 둘 중 하나가 없으면 재량이 아니라 아직 정하지 않은
것이다. 구현 규칙이 만족해야 하는 결과 중 공개 표면에서 관찰되는 것은 문서 마지막 검증 요구
절(§9.3)에 두고, 내부 구조로만 확인할 수 있는 것(white-box 불변 조건, 정적 검사)은 그 규칙
문단이 "내부 확인 조건"으로 함께 소유한다 — 검증 요구 절에는 넣지 않는다.

이 문서가 구현만 서술하고 그 계약을 다른 스펙이 소유하면, 첫 부분에서 계약 소유 문서를
밝히고 링크한다(§4.2). 계약 서술을 이 문서에서 다시 정의하지 않는다. 구현 규칙이 계약
서술과 충돌하면 그 충돌은 결함이다 — 계약을 기준으로 구현 규칙을 고치거나, 계약 자체를
바꿔야 하면 공개 계약 절차를 먼저 따른다. 어느 한쪽이 "우선한다"고 적어 충돌을 남겨 두지
않는다.

wire 형식은 상호운용 계약과 codec을 나눈다. ZMP·RAW 같은 wire 문서에서, 다른 구현이
상호운용을 위해 의존하는 byte 배치는 계약 서술이다. 그 byte를 만드는 절차 — 어느 함수가
buffer를 재사용하고 control part를 언제 붙이는가 — 는 구현 서술이다.

계약 서술과 구현 서술을 절로 나눌지는 읽기 편의로 정한다. 나누면 독자가 계약만 읽고
넘어갈 수 있어 편하고, 짧은 주제는 한 흐름에 두되 계약 문장만 방향을 밝혀도 된다.

## 5. 동작을 설명하는 방법

### 5.1 주체와 순서를 분리한다

분산 호출은 다음 순서로 확인한다.

1. Caller가 지정하는 값
2. Source runtime이 조회하거나 선택하는 값
3. Transport가 수락하는 시점
4. Target runtime이 확인하는 상태
5. Queue와 handler가 실행하는 작업
6. Caller에게 결과가 돌아오는 시점

각 단계마다 주어와 조건을 밝힌다 — `resolve 후 reserve하고 dispatch한다`는 누가
무엇을 확인하는지 남기지 않는다.

### 5.2 존재 여부와 생성 위치를 명시한다

Object 생성이나 메시징 문서는 다음 질문에 직접 답한다.

- Source가 저장소에서 존재 여부를 확인하는가?
- Target이 process 내부 object 목록을 확인하는가?
- Object가 없을 때 누가 target을 고르는가?
- 누가 생성 권한과 수용 공간을 확보하는가?
- 최초 message를 target이 보관하는가, source가 다시 보내는가?
- 여러 caller가 동시에 요청하면 factory가 몇 번 실행되는가?

이 질문에 답하지 않으면 정상 흐름 설명이 완성되지 않은 것이다.

### 5.3 자동 동작과 명시적 호출을 구분한다

`자동으로 중계하지 않는다`처럼 runtime이 하지 않는 일을 적을 때는 다음 내용을 함께
써서, API 자체가 막혔다는 뜻으로 읽히지 않게 한다.

1. Runtime이 현재 operation에서 자동으로 하지 않는 동작
2. 실패했을 때 fallback이나 retry 여부
3. Application이 별도 API로 새 operation을 시작할 수 있는지
4. 새 operation이 중복 실행 위험을 만들면 그 책임

### 5.4 Role과 target 선택을 구체적으로 쓴다

role과 target에는 적용 범위를 붙여 쓴다 — `Server가 없다`가 아니라 어느 role이 어느
process에 없는지까지.

- 현재 process에 어떤 role이 필요한가?
- 호출을 시작할 local 송신 role은 무엇인가?
- Remote target이 제공해야 하는 role은 무엇인가?
- 어느 role이 descriptor와 target membership을 게시하는가?
- 서로 다른 role 축을 함께 설정할 수 있는가?

자동 선택과 identity 직접 지정 호출도 분리한다.

| 호출 방식 | 상태가 적용되는 방법 |
|---|---|
| Runtime이 target을 선택 | Ready, drain과 weight를 후보 구성에 적용한다. |
| Caller가 identity를 직접 지정 | Runtime은 다른 identity를 대신 선택하지 않는다. 지정한 target이 수락한다는 보장은 별도로 판단한다. |

`target을 바꾸지 않는다`와 `호출이 성공한다`는 서로 다른 보장이므로 각각 밝힌다.

### 5.5 비슷한 API는 공통 차이부터 설명한다

주소 지정 방식만 다른 비슷한 API(node 지정, 객체 지정, 하위 객체 지정)는 다음 순서로
설명한다.

1. 주소 지정 방식의 가장 큰 차이를 설명한다.
2. 각 방식이 사용하는 identity와 target을 설명한다.
3. 실행하는 queue와 handler를 설명한다.
4. Runtime이 자동 변환하지 않는 경계를 설명한다.

Payload type이 같아도 다른 주소 지정 방식의 handler로 자동 전달하지 않는다면
마지막 단계에서 명시한다.

### 5.6 내부 제어 입력은 Application 관점에서 설명한다

Liveness beacon이나 이동 control message는 내부 이름보다 다음 결과를 먼저 설명한다.

- Runtime이 사용하는 목적
- Application payload와 구분하는 기준
- 실행하지 않는 handler나 callback
- 일반 message monitoring이나 tracing에 포함하는지
- Byte 형식이나 timeout을 소유한 다른 계약

### 5.7 종류와 역할은 독자가 아는 예에 붙여 설명한다

같은 계열의 종류(Spot 세 종류, Channel 종류, 실행 mode 등)를 나열할 때 "무엇이다"만 쓰면
독자는 셋 다 읽고도 어느 것을 골라야 할지 모른다. 정의 앞이나 옆에 **독자가 이미 아는
구체물**을 하나 붙인다.

- 추상적인 성질("Application이 수명을 관리하는 Actor container")이 아니라 **어떤 자리인지**를
  쓴다. 그 자리에서 무슨 일이 벌어지는지 그려지면 성공이다.
- 비유는 "게임으로 치면 lobby다"처럼 **비유임이 드러나게** 쓴다. 계약 문장 자리에 비유를
  섞지 않는다. 비유는 이해를 돕는 예일 뿐이고, 규범은 그 아래 표와 규칙 문장이 진다.
- 독자층이 갈리면 예를 **하나 더 붙여도 된다.** 게임 서버 예와 웹 서비스 예를 나란히 두는
  식이다. 다만 예가 셋 이상이 되면 그 자체가 읽는 부담이 된다.
- 비유가 계약과 어긋나는 지점이 있으면 그 자리를 적는다. "lobby와 달리 Entry Spot은 닫히지
  않는다"처럼 한 문장이면 된다.

```markdown
- **Entry Spot** — Actor가 태어나고 사라지는 장소다. 아직 어느 방에도 들어가지 않은 Actor가
  머무는 곳이다. 게임으로 치면 **lobby**, 웹 서비스로 치면 접속 직후의 **세션 진입점**이다.
- **User Spot** — 여러 Actor가 한자리에 모여 서로 주고받는 장소다. 게임으로 치면
  **game room**이다.
```

종류를 비교하는 표에는 **"언제 쓰는가" 열을 맨 앞에 둔다.** 독자가 먼저 던지는 질문이
"셋 중 무엇을 골라야 하는가"이고, 생성 방식과 제약은 그다음이기 때문이다.

## 6. 값, 상태와 제한을 설명하는 방법

### 6.1 간접 구조는 실제 예로 푼다

Root, manifest, reference, generation, tree와 digest처럼 다른 값을 가리키는 구조는
다음 순서로 푼다.

1. 원래 값이 무엇인지 설명한다.
2. 왜 여러 record로 나누는지 설명한다.
3. 각 record에 무엇이 들어가는지 설명한다.
4. 어떤 변경이 새 상태를 공식적으로 공개하는지 설명한다.
5. 중간에 실패한 record를 어떻게 정리하는지 설명한다.

예를 들어 객체 10,000개의 목록을 최대 1,024개씩 나눈다면, 전체 객체 상한과 목록
페이지 하나의 제한을 각각 다른 값으로 적는다.

### 6.2 수치는 적용 범위를 붙인다

같은 단위라도 목적이 다르면 별도 행으로 설명한다.

| 범위 | 예 |
|---|---|
| 시스템 전체 | 전체 object 수에 고정 상한이 있는가? |
| Object 하나 | 그룹 하나에 속할 수 있는 object 수 |
| Record 하나 | 목록 페이지의 항목 수와 저장 크기 |
| Payload | Application state와 queue data의 전체 크기 |
| 실행 중 memory | 동시에 처리하는 in-flight byte 상한 |

수치에는 무엇의 encoded 크기인지를 같은 문장이나 표 제목에서 함께 밝힌다 —
`최대 1 MiB`만으로는 적용 대상이 남지 않는다.

### 6.3 상태 변경의 원자적 범위를 밝힌다

여러 값을 함께 바꿔야 하면 다음 내용을 설명한다.

- 함께 검증하는 이전 값
- 한 번에 바꾸는 record와 field
- 충돌했을 때 변경되는 값이 있는지
- 성공 전과 성공 후에 어느 node를 owner로 인정하는지
- 실패 후 다시 읽어야 하는 공식 record

`atomic`·`CAS`·`transaction`을 쓸 때는 무엇이 전부 바뀌거나 전혀 바뀌지 않는지를
함께 설명한다.

## 7. 표와 다이어그램

### 7.1 표

표는 역할, 조건이나 결과를 비교할 때 사용한다. 시간 순서는 번호 목록이나 sequence
diagram을 사용한다.

표는 다음 조건을 만족해야 한다.

- 열 제목만 읽어도 비교 기준을 알 수 있다.
- 각 셀에 주어, 조건과 결과가 있다.
- 조건만 적고 끝내지 않는다. **그 조건이 무슨 결과를 낳는지**가 같은 행에 있다. 없으면
  "그래서" 열을 만든다.
- 종류·선택지를 비교하는 표에는 "언제 쓰는가" 열이 맨 앞에 있다(§5.7).
- Status와 field 옆에 Application이 관찰하는 의미가 있다.
- 각 셀은 용어 대신 그 용어가 뜻하는 조건과 결과를 담는다.
- 표에 들어가지 않는 예외는 바로 아래 문장으로 설명한다.

### 7.2 Sequence diagram

다음 중 하나에 해당하는 절은 문장만으로 끝내지 않고 sequence diagram을 둔다.

- 세 주체 이상이 순서대로 주고받는 흐름을 설명한다.
- 무엇이 어느 process·node에 머물고 무엇이 그 경계를 넘는지를 설명한다(물리 층 그림).
- 정상 경로와 실패·timeout 분기가 같은 자리에서 갈린다.

설명하려는 완료 경계에 맞는 call 형태를 선택한다. One-way 수락이 핵심이면 send
흐름을 사용한다. Reply까지 설명해야 할 때만 request/reply를 사용한다.

Participant에는 정식 component 이름을 사용할 수 있다. 화살표, 조건과 note는
한국어 문장으로 쓴다. 정상 경로만 그렸다면 diagram 아래에서 제외한 실패나 경쟁
경로를 밝힌다.

물리 connection과 논리 target 선택은 그림을 나눠 그린다.

- 물리 diagram: node 식별자, listener와 peer connection
- 논리 diagram: caller가 지정한 identity, target 후보, ready·weight와 handler

두 diagram의 관계를 함께 설명해, 논리 채널 등록이 새 socket을 만드는 것으로
읽히지 않게 한다. 한 그림에는 한 층만 담는다 — candidate 목록, selector, transport,
queue와 handler를 한꺼번에 넣으면 어느 층의 그림인지 남지 않는다.

## 8. Public interface와 예제

### 8.1 설명하는 절에 필요한 interface를 둔다

독자가 의미를 확인하려고 다른 문서를 계속 오가지 않게, 필요한 public interface와
result type을 정확히 발췌한다. 설명에 필요한 overload만 싣고 나머지는 exact interface
문서로 연결한다.

같은 선언과 예제는 의미를 가장 직접 설명하는 절 한 곳에 두고, 다른 절에서는 그 절을
링크한다.

### 8.2 공통 계약과 언어별 표현을 구분한다

공통 스펙에서 특정 언어 코드를 예시로 사용할 수 있다. 코드 앞에 다음 내용을 명시한다.

- 공통 동작을 설명하는 예시다.
- 다른 언어에 같은 signature를 요구하지 않는다.
- 정확한 signature는 언어별 exact interface가 정의한다.

실제 public interface가 아닌 설명용 코드는 `contract pseudocode`라고 표시한다.

### 8.3 코드 주석은 목적과 계약을 설명한다

핵심 호출 옆에 코드만으로 알 수 없는 이유, 완료 시점이나 제약을 주석으로 쓴다.

```csharp
return client
    .RequestTo(objectId, request)
    .CreateWith("CartFactory")         // 객체가 없을 때 사용할 factory type이다.
    .InGroup("orders")                 // 처음 배치할 그룹에만 적용한다.
    .Async<TReply>(cancellationToken); // Handler가 반환한 reply까지 기다린다.
```

주석에는 코드에 이미 있는 호출 이름 대신, 그 호출의 이유·완료 시점·제약을 쓴다.

enum 값, `#define` 상수, struct field, 그리고 builder·interface의 method와 option의 의미는
**코드 밖 '이름·값·설명' 표 대신 그 줄의 인라인 주석**으로 단다. 필수·선택 여부와 기본값도
주석에 넣는다. 이전 문서에 "축 | 의미" 같은 설명 표가 있어도 그대로 옮기지 않고 선언 옆
주석으로 바꾼다 — 독자가 선언과 표를 오가며 짝을 맞추게 하지 않는다. 독자가 값과 설명을 눈으로 짝지을 필요가 없고, 선언과 설명이 한
곳에 있어 어긋나지 않는다. 주석에는 타입·범위·기본값·읽기 전용·`0`의 의미처럼 계약에
필요한 사실을 담고, 한 줄에 안 들어갈 상세는 소유 절로 링크한다.

```c
ZLINK_MAX_MSGSZ  = 5,   // 최대 메시지 크기 (byte, >= 0, 기본 INT_MAX)
ZLINK_MSG_T_SIZE = 6,   // zlink_msg_t 크기 (byte, 읽기 전용)
```

### 8.4 송신과 수신을 한 흐름으로 보여준다

Caller가 설정하고 target이 읽는 metadata, timeout, filter와 correlation은 같은
절에서 다음 내용을 연결한다.

1. 값을 설정하는 call builder
2. 값을 읽는 handler context
3. 선택한 target에서 보이는 최소 예제
4. Ownership, 크기와 자동 복사 여부

Handler 설명에는 handler를 찾는 key, 등록 builder, 실행 queue 또는 turn과 namespace
경계를 함께 둔다.

## 9. 완료와 실패

### 9.1 완료 경계를 나눈다

다음 시점을 별도로 설명한다.

- Source queue 또는 transport가 작업을 수락한 시점
- Remote queue가 message를 수락한 시점
- Handler가 실행을 시작하거나 끝낸 시점
- Request reply가 caller에게 도착한 시점

Timeout이 어느 구간에 적용되는지, cancellation 뒤 remote 작업이 계속될 수 있는지,
일부 target만 성공했을 때 이미 수락한 작업을 유지하는지도 설명한다.

오류는 caller가 어떤 조건에서 어떤 status나 exception을 관찰하는지 표로 설명한다.

### 9.2 비동기 terminal 이름은 한 벌로 고정한다

같은 operation의 정상 비동기 완료를 나타내는 terminal 이름은 언어별로 하나만 정하고
문서 전체에서 같게 쓴다. **언어별로 어떤 이름을 쓰는지는 그 제품의 비동기 실행 정책
스펙이 소유하며**, 개별 스펙 본문은 그 이름을 인용한다. 이 가이드는 이름 목록을 담지
않는다.

- 한 이름은 한 가지 완료 의미만 가리킨다. 제출 수락과 실행 완료처럼 서로 다른 완료
  의미를 한 이름에 담지 않는다.
- 규칙을 적용하는 call builder 범위와, 적용하지 않는 API(구성·등록·수명주기 method
  등)를 정책 문서가 함께 밝힌다.
- 특례가 있으면 어떤 실행 문맥에서만 허용되는지까지 적는다.

### 9.3 검증 요구를 인터페이스 관찰로 쓴다

문서 **마지막 top-level 절**에 구현과 contract test가 확인할 **검증 요구**를 둔다. 이 절은
작업자가 무엇을 test로 확인해야 하는지 알려주며, 잘 쓰면 **이 절만 읽어도 그 기능이 바깥에서
어떻게 동작하는지** 정리된다 — 검증 요구가 곧 그 문서의 관찰 가능한 행동 계약이다.

- **인터페이스 관찰만 쓴다.** 내부 구현 상태가 아니라 공개 표면 — signature, 옵션, 조회·snapshot
  API, 반환값·errno, send·receive 결과 — 으로 확인할 수 있는 결과만 적는다. `allocation 전`,
  `내부 예약`처럼 화이트박스 표현은 관찰 가능한 문장으로 바꾼다(예: "폐기 후 snapshot의 `X`가
  `0`으로 돌아온다").
- **각 항목은 test 하나로 이어진다.** "이 공개 호출을 하면 → 이게 관찰된다" 형태로 쓴다.
- **행동을 이 절이 소유한다.** 관찰 가능한 행동은 여기에 한 번만 적고, 다른 절(선언·개념·내부
  구조 산문)은 같은 행동을 다시 서술하지 않고 이 절을 가리킨다(§4.3). 산문은 *왜·어떻게*(근거와
  메커니즘)를 소유한다.
- **주제별로 묶어 완결되게 쓴다.** 평평한 나열이 아니라 관련 항목을 묶어, 위에서 아래로 읽으면
  관찰 행동이 그림으로 서게 한다.
- **ID나 추적 레지스트리는 만들지 않는다.** 작업자가 검증할 항목의 체크리스트로 남긴다.

형식은 첫 문장에서 "무엇만으로 확인하는가"(공개 표면의 목록)를 밝히고, 주제별 굵은 소제목 아래
한 항목 한 문장의 불릿으로 쓴다 — 표의 열에 문장을 넣지 않고, "확인 방법" 열도 두지 않는다
(이 절의 모든 항목은 contract test다). 각 불릿은 "이 공개 호출·입력을 하면 → 이 값·상태·호출이
관찰된다"를 한 문장에 담는다.

```markdown
## 8. 구현 및 contract test 검증 요구

공개 표면(`zlink_msg_*` 함수, 반환값·errno, `zlink_free_fn` callback 호출)만으로 다음을
확인한다. 각 항목은 unit test 하나로 이어진다.

**초기화와 해제**

- `zlink_msg_init`으로 초기화한 message는 길이 0이다 — `zlink_msg_size`가 0을 반환한다.
- `zlink_msg_init_size`가 성공하면 `zlink_msg_size`가 지정한 크기를 반환하고, 할당에 실패하면
  `ENOMEM`이다.

**zero-copy와 free callback**

- `zlink_msg_init_data`로 만든 message가 송신되거나 닫힌 후, library가 `data_`와 `hint_`를
  인수로 `ffn_`을 호출한다. `ffn_`이 NULL이면 callback을 호출하지 않는다.
```

Framework처럼 언어별 signature가 다른 스펙은 함수 이름 대신 언어 중립 operation 이름(bind,
relay, `NotifyDisconnected`), `ErrorKind`, callback 이름, wire command 번호를 공개 표면으로 쓴다.

| 이렇게 쓴다 | 흔한 이탈 |
|---|---|
| Session callback이 managed queue를 소비하지 못하는 동안 client가 계속 보내면 client 쪽 send가 receive pipe HWM에 걸려 멈추고, queue가 풀리면 packet이 순서대로 한 번씩만 callback에 도달한다. | Framework 내부 recv loop가 packet을 managed queue에 넣은 뒤에만 session callback을 실행한다. (내부 구조 서술 — 바깥에서 관찰할 수 없다) |
| Actor 둘을 bind한 connection을 끊으면 각 Actor의 current Spot에서 `OnDisconnectActorAsync(...)`가 정확히 한 번 호출된다. | 직렬 실행 원시 타입이 runtime 안에서 하나다. (white-box — 규칙 문단이 "내부 확인 조건"으로 소유한다) |

전체 예:
[Core message 스펙 「8. 구현 및 contract test 검증 요구」](../../../core/doc/spec/core/02-message.ko.md#8-구현-및-contract-test-검증-요구).

내부 구현으로만 확인할 수 있는(화이트박스) 검증은 이 절이 아니라 internals 서술이 소유한다 —
대상 독자가 contract·binding test 작성자가 아니라 Core 유지보수자이기 때문이다.

## 10. 이전 계약을 대체할 때

이 절은 이전 계약 문서를 대체하는 경우에 적용한다. 이전 문서, 구현과 E2E는 누락 검사에
사용할 수 있다. 완성된 정식 스펙은 판단에 필요한 내용을 스스로 담는다.

완성 시점에 걷어낼 항목:

- 폐기할 이전 문서 링크
- 두 문서가 다르면 이전 문서를 따른다는 문구
- 계약 일부를 구현 코드나 초안에서 확인하라는 안내
- 이전 문서와 달라진 작성 이력

대조 중 발견한 새 동작은 별도 리뷰를 거쳐 현재 계약에 포함할지 정한다.

## 11. 완료 점검표

AI는 최종 보고 전에 아래 항목을 직접 확인한다.

### 계약

- [ ] 첫 단락에 문서의 질문, 결과와 책임 범위가 있다.
- [ ] Application, runtime, provider와 remote runtime의 책임을 구분했다.
- [ ] 대상이 있을 때와 없을 때의 동작을 설명했다.
- [ ] 동시 요청이 하나로 수렴하는 조건을 설명했다.
- [ ] 자동 선택, 직접 지정, fallback과 retry의 차이를 설명했다.
- [ ] Send, remote 수락, handler와 reply 완료를 구분했다.
- [ ] Timeout, cancellation, shutdown과 정리 결과를 설명했다.
- [ ] 모든 수치에 적용 범위를 붙였다.
- [ ] 문서 마지막에 검증 요구 절을 두고, 인터페이스 관찰(공개 표면·errno·반환값)로만 썼으며 각 항목이 test 하나로 이어지는가? (§9.3)
- [ ] 관찰 가능한 행동을 검증 절에 한 번만 적고, 다른 절은 그 행동을 다시 서술하지 않고 가리켰는가? (§4.3, §9.3)
- [ ] 검증 절에 white-box 조건이나 "확인 방법" 열이 없고, 내부 확인 조건은 규칙 문단이 소유하는가? (§4.4, §9.3)
- [ ] 입력 자료에 없는 이름·수치·방향·소유 문장을 만들지 않았고, 대장의 각 규칙을 grep으로 실물 확인했는가? (§2.6)
- [ ] 이전 계약에 있던 상태, 수치와 실패 규칙을 모두 옮겼다.

### 용어와 설명

- [ ] 용어집 용어는 각 문서의 첫 설명에서 쉬운 뜻과 링크를 함께 제공했다.
- [ ] 같은 철자는 한 가지 의미로만 연결했다.
- [ ] Public identifier와 업계 용어도 처음에 하는 일을 설명했다.
- [ ] 제품 전용 영어 용어는 §3.4의 조건을 만족하는 것만 썼다.
- [ ] 영어 명사를 이어 붙인 압축 표현을 동작이 드러나는 문장으로 바꿨다.
- [ ] "결정" 같은 라벨 없이 굵은 규칙 + 이유 불릿으로 썼고, 언어별 재량만 표시했는가? (§2.4, §4.4)
- [ ] 원칙 7.3의 어색한 한자어("정본" 등)를 쓰지 않았는가?
- [ ] 한 문단에는 주된 판단 하나만 있다.
- [ ] 간접 구조는 실제 값이나 개수를 사용한 예로 설명했다.
- [ ] 객체, 연결과 상태를 동작 주체 그대로 서술했다.

### 표, diagram과 코드

- [ ] 표의 각 셀에 조건과 결과가 있다.
- [ ] 조건 열만 있고 결과 열이 빠진 표는 없는가? (§7.1)
- [ ] 종류를 나열한 자리에 독자가 아는 구체적인 예와 "언제 쓰는가"가 있는가? (§5.7)
- [ ] 시간 순서는 번호 목록이나 sequence diagram으로 설명했다.
- [ ] Diagram의 화살표와 조건은 한국어로 작성했다.
- [ ] 물리 connection과 논리 target 선택을 별도 diagram으로 구분했다.
- [ ] 세 주체 이상의 순서, node 경계를 넘는 것, 실패 분기를 설명하는 절에 diagram이 있는가? (§7.2)
- [ ] 선언의 option·field 설명이 별도 표가 아니라 인라인 주석에 있는가? (§8.3)
- [ ] 필요한 public interface와 최소 예제를 관련 절에 배치했다.
- [ ] 코드 주석은 목적과 계약을 설명한다.
- [ ] 송신 설정과 수신 context를 같은 흐름에서 확인할 수 있다.

### 검증

- [ ] 상대 링크와 용어집 anchor가 실제 위치를 가리킨다.
- [ ] 제목 아래와 본문 끝에 같은 내비게이션 줄(주제 목차·상위 목차·이전·다음)이 있는가? (§2.2)
- [ ] Markdown 표와 code fence가 올바르다.
- [ ] Mermaid 문법을 확인했다.
- [ ] `git diff --check`가 통과한다.
- [ ] 문서 계약 검증 스크립트가 있다면 통과한다.
