# 감독자 지침 — 결과를 판정하는 사람은 감독자다

> 이 문서는 sub-agent에게 일을 맡기는 감독자가 **무엇을 직접 판정하고 어떻게 판정하는가**를
> 소유한다. 어떤 model·추론 레벨·도구를 쓰는지는 [`AGENTS.md`](../../../AGENTS.md) §2.1이,
> 무엇을 확인해야 확인한 것이 되는지는 [검증 원칙](verification-principles.ko.md)이,
> 설계 판단 기준은 [POSDDD](posddd.ko.md)와
> [제어 결정과 요청 수락의 소유](zlink-system-design-principles.ko.md#제어-결정과-요청-수락의-소유)가
> 소유한다. 이 문서는 그 규칙을 반복하지 않는다.
>
> **이 문서는 쌓인다.** 감독 실패를 한 번 겪을 때마다 §6 표에 한 줄을 더한다. 사례가 늘어도
> §1~§5의 규칙은 늘지 않아야 한다.

## 1. 감독자가 직접 하는 일

**결과가 요구대로 됐는지 판정하는 일은 위임하지 않는다.** sub-agent의 완료 보고, sub-agent
리뷰, test·gate 통과는 판정의 입력이다. 판정 자체가 아니다.

- **모든 diff를 직접 읽는다.** 코드·테스트·샘플·runner·가이드 모두 해당한다. 한 건에 수 분이면
  된다. 시간이 모자라 건너뛸 일은 생기지 않는다.
- **변경의 리뷰는 감독자만 한다.** 작업 뒤에 sub-agent 리뷰 단계를 두지 않는다. codex `sol` 리뷰는
  감독자가 스펙을 수정했을 때만 넣는다([`AGENTS.md`](../../../AGENTS.md) §5.1).
- **판정하지 않은 변경은 커밋하지 않는다.** 커밋 본문에 근거가 된 스펙 조항을 `file:line`으로
  적는다. 조항을 적지 못하면 그 변경은 스펙 gap이거나 스펙 밖의 규칙이다(§4).
- **동시에 돌리는 작업 수는 제한하지 않는다.** 끝나는 대로 바로 리뷰한다. 리뷰가 밀린 것은
  작업을 줄일 이유가 아니라 리뷰를 먼저 할 이유다.
- **일정은 리뷰를 줄일 이유가 되지 않는다.** 리뷰를 건너뛴 변경은 뒤에서 더 큰 수정을 부른다.

## 2. 리뷰 기준 일곱 가지

diff마다 다음 일곱을 스펙과 코드를 직접 열어 확인한다. 변경만이 아니라 그 호출 경로까지 본다.

| 기준 | 확인할 것 |
|---|---|
| 스펙 gap | 변경한 동작의 근거 조항이 있는가. 조항과 다르게 동작하는 곳은 없는가 |
| 불필요한 규칙 | 새 플래그·상태·타이머·재시도·옵션·"이 경우만" 분기·상수 사본이 생겼는가 |
| 제어 분산 | 같은 결정을 내리는 곳이 늘었는가. 판정 위치 수를 수정 전/후로 센다 |
| 동기화 | 인프라 경로(수신 loop·pump·lane·timer·completion)가 application·Store·lane 완료를 막고 기다리는가. gate가 이미 직렬화하는 상태를 lock으로 다시 보호하는가 |
| hot path | 메시지마다 할당·lock·추가 native 호출·꺼진 trace의 문자열 생성·큐 전체 순회가 생겼는가 |
| 리팩토링 잔여 | 건드린 모듈과 호출 경로에 POSDDD·성능·불필요한 코드 기준([`AGENTS.md`](../../../AGENTS.md) §3)으로 고칠 것이 남았는가 |
| 계층 소유 | Core·binding이 제어하는 결정(연결 선택·교체, reconnect, handover, completion, 재전송, errno 분류 등 [`AGENTS.md`](../../../AGENTS.md) §3 계층 소유권 목록)을 framework가 상태나 분기로 다시 제어하는가. 고칠 때는 framework가 Core의 결과를 관찰만 하게 한다 |

판정 위치가 늘거나 새 규칙이 더해진 diff는 반려한다. 이유가 test 통과여도 같다.

## 3. 브리프

- **판정은 감독자가 먼저 한다.** 설계가 갈리는 작업은 감독자가 스펙 조항을 읽고 설계를 정한 뒤
  브리프에 "정해진 설계"로 적는다. sub-agent에게 설계 선택을 맡기면 증상에 가까운 곳에 규칙을
  더하는 안이 돌아온다.
- **쓰기 한계를 명시한다.** 수정할 worktree, 금지 조작(commit·push·branch·stash·reset·스펙 수정)을
  적는다.
- **근거 조항을 `file:line`으로 준다.** 결함 설명, 지켜야 할 조항, 쓰면 안 되는 이전 시도를 함께
  적는다.
- **진단과 구현을 나눈다.** runtime 결함은 결정 소유 표(결정마다 스펙 소유 조항, 지금 판정하는 곳
  전부, 모을 소유자)를 먼저 받고, 감독자가 판정한 뒤 구현을 맡긴다.
- **간단한 수정은 감독자가 직접 한다.** 기준은 브리프가 수정보다 길어지는가다. 빌드·테스트
  확인이 필요한 수정은 sub-agent에게 맡긴다.

## 4. sub-agent 결론을 다루는 법

- **인용한 조항과 코드를 직접 열기 전에는 채택하지 않는다.** 확인하기 전에는 "후보"로만 말한다.
  채택·기각 사유는 결정 기록에 남긴다.
- **큰 방향 전환일수록 먼저 확인한다.** Core·binding·public API·스펙 변경 제안은 근거 조항을
  감독자가 읽고 `file:line`을 붙인 뒤에만 사용자에게 올린다.
- **리뷰어의 요구도 스펙에 없으면 채택하지 않는다.** 반려 사유가 스펙 조항에 없는 동작을 요구하면,
  그 요구를 반영하는 대신 스펙이 그 결정을 정하는지부터 확인한다.
- **스펙이 정하지 않은 결정(D)은 먼저 스펙에서 찾는다.** 다른 문서가 이미 정한 경우가 많다.
  정말 없으면 감독자가 추천안으로 스펙을 개정하고 리뷰를 거친다([`AGENTS.md`](../../../AGENTS.md) §5.1).

## 5. 완료와 릴리스 판정

- **1~2회 통과는 판정 근거가 아니다.** 간헐성 결함은 반복 실행에서만 드러난다. 샘플 판정은
  부하 아래 반복 실행으로 하고, 한 번이라도 실패하면 결함이다.
- **실패가 났던 조건에서 판정한다.** WSL gate가 통과해도 Windows, 새 clone의 README 절차,
  특정 샘플의 반복 실행에서 실패가 나왔다면 그 조건을 판정에 넣는다.
- **남은 확정 결함 수를 매일 보고한다.** 수정이 결함을 줄이고 있는지 숫자로 보인다. 줄지 않으면
  멈추고 방식을 다시 판단한다.
- **원인을 말할 때 핑계를 대지 않는다.** 판정을 건너뛴 원인은 감독자의 선택이다. 일정·부하·
  작업량을 원인으로 적지 않는다.
