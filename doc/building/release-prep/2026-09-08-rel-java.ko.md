# rel-java Maven Central 배포 준비 기록

## 변경 파일

- `bindings/java/build.gradle`
- `bindings/java/codec/zlink-ext-netty/build.gradle`
- `bindings/java/scripts/upload-central-bundle.sh`
- `.github/workflows/bindings-release.yml`의 `release-java` job
- `doc/building/release-prep/2026-09-08-rel-java.ko.md`

## 핵심 변경

- 공개 좌표는 기존과 같이 `systems.zlink:zlink:0.17.3`과
  `systems.zlink:zlink-ext-netty:0.17.3`을 유지한다.
- 두 publication에 sources JAR과 Javadoc JAR을 포함하고, Javadoc의 누락 문서 경고는
  실패로 처리하지 않는다. 루트 sources JAR에서는 배포용 native payload와 Core provenance를
  제외한다.
- 공통 POM에 프로젝트 URL, MPL-2.0 라이선스 URL, 개발자 정보, SCM connection을 추가한다.
- `SIGNING_KEY`와 `SIGNING_PASSPHRASE`가 모두 있을 때만 base64 armored 개인키를 메모리에서
  복호화해 publication을 서명한다. 두 값이 없는 일반 로컬 빌드와 staging은 서명 없이 성공한다.
- `MAVEN_CENTRAL_BUNDLE_DIR`가 지정된 실행에만 `centralStaging` file repository를 추가한다.
  기존 `releaseRepo`의 `MAVEN_REPOSITORY_URL` 및 GitHub Packages fallback은 유지한다.
- `upload-central-bundle.sh`는 두 component를 하나의 Maven repository layout ZIP으로 묶고,
  원본별 MD5/SHA-1을 만든 뒤 Publisher API의 `USER_MANAGED` deployment로 업로드한다. 최종
  Publish는 자동으로 수행하지 않는다.
- Java workflow는 Core source를 다시 컴파일하지 않고 `core/v0.17.3` release package와 exact
  provenance summary를 사용한다. 기존 GitHub Packages 발행 다음에 Central Portal 업로드 단계를
  추가하고 네 시크릿 이름만 연결한다.

## Central 방식 선택

로컬 staging repository를 만든 뒤 Central Portal Publisher API로 bundle ZIP을 업로드하는 방식을
선택했다. Sonatype은 공식 Gradle publishing plugin을 제공하지 않으며, 공식 API는 Maven layout을
따르는 하나의 ZIP에 여러 component를 넣는 방식을 지원한다.

현재 Gradle wrapper는 8.10.2이고 Vanniktech plugin 최신 0.37.0은 Gradle 9.0 이상을 요구한다.
호환되는 과거 plugin을 고정하기보다 기존 `maven-publish`를 유지하고 얇은 업로드 스크립트만 두면
추가 Gradle plugin 의존성과 업그레이드 결합이 없고, 두 publication을 한 deployment로 재현할 수
있다.

조사 근거:

- Sonatype Publisher API: <https://central.sonatype.org/publish/publish-portal-api/>
- Sonatype bundle layout: <https://central.sonatype.org/publish/publish-portal-upload/>
- Vanniktech Central 문서: <https://vanniktech.github.io/gradle-maven-publish-plugin/central/>
- Vanniktech 0.37.0 release: <https://github.com/vanniktech/gradle-maven-publish-plugin/releases/tag/0.37.0>

## 사용자가 직접 해야 할 일

1. GitHub Actions에 `MAVEN_CENTRAL_USERNAME`, `MAVEN_CENTRAL_PASSWORD`, `SIGNING_KEY`,
   `SIGNING_PASSPHRASE`가 설정되어 있는지 확인한다. 다른 Maven Central credential 이름은
   만들지 않는다.
2. 서명 개인키에 대응하는 공개키가 Central이 조회할 수 있는 공개 keyserver에 배포되어 있는지
   확인한다.
3. 감독자가 diff를 검토하고 커밋한 뒤 `bindings-release.yml`을 Java target,
   `publish_registry=true`로 실행한다. 이 job은 GitHub Packages 발행 후 Central Portal에
   `USER_MANAGED` deployment를 만든다.
4. Central Portal에서 deployment validation 결과와 두 좌표를 확인한 뒤 사용자가 직접
   **Publish**를 누른다.

## 미해결 사항

- 실제 서명은 시크릿을 읽지 않는 검증 환경이라 실행하지 않았다.
- Central Portal upload 및 최종 Publish는 금지 조건에 따라 실행하지 않았다. 최초 실제 workflow
  실행에서 서명 검증과 Portal validation 결과를 확인해야 한다.
