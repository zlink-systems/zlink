# Node send/close stress의 Core 0.17.3 실패 조사 기록

## 결론

실패 원인은 Core 0.17.3의 반환값 변경이나 Node binding의 오류 분류가 아니라, test hook이
submit과 close의 겹침을 보장하지 않은 timing 문제다. 분류는 **(c)**다.

기존 hook은 sender가 Core에 진입하기 전에 `attempts`를 증가시키고, closer는
`attempts == total_attempts`만 기다렸다. 0.17.3에서는 여러 thread의 multipart submit이 모두
허용되고 빨리 끝나므로 closer가 실행될 때 40,000건의 Core 호출도 이미 끝났다. 반복 수를
400,000건으로 늘려도 `submitted=400000`, `shutdown=0`으로 같았다.

0.17.0 dev에서 관찰된 `EINVAL`은 close 결과가 아니다. 당시 Core는 미완성 multipart를
socket-wide slot 하나에 보관했고, 다른 thread가 진입하면
`core/src/api/socket/part_helper_api.cpp:175-185`의 owner 검사에서 `EINVAL`을 반환했다.
Core 커밋 `29f4d8b45c6fdc3fd8fab64ec809fedeb306950d`는 PAIR·DEALER·ROUTER의 조립 상태를
thread별 sequence로 바꾸었다. 현재 계약은 `core/doc/spec/core/socket/README.ko.md:49-59`와
`core/doc/spec/core/socket/README.ko.md:947-965`에서 여러 thread의 독립된 multipart submit을
허용하고, close 수락 뒤의 새 API 진입을 `ESHUTDOWN`으로 정한다.

## 수정 전 카운터 비교

두 실행은 수정 전 hook에 `testRunSendCloseStress(4, 10000)`을 사용했다.

| Core | submitted | rejected_einval | shutdown | backpressured | other_submit | received_records | bad_records |
|---|---:|---:|---:|---:|---:|---:|---:|
| 0.17.0 dev (`core/build-dev/lib`) | 26,726 | 12,066 | 0 | 1,208 | 0 | 26,726 | 0 |
| 0.17.3 release prefix | 40,000 | 0 | 0 | 0 | 0 | 40,000 | 0 |

두 실행 모두 `attempts=40000`, `single_attempts=20000`, `multipart_attempts=20000`,
`close_ok=1`, `close_busy=0`, `close_shutdown=0`, `close_other=0`이었다.

반복 수를 늘린 0.17.3 실행은 `attempts=400000`, `submitted=400000`,
`rejected_einval=0`, `shutdown=0`, `backpressured=0`, `other_submit=0`,
`received_records=400000`, `bad_records=0`이었다. 부하 증가만으로는 close 경합이 생기지 않았다.

## 원인 판정 근거

### Core 0.17.3 변경 범위

`core/v0.17.2..core/v0.17.3 -- core/src`에는 다음 커밋만 있다.

- `de730d4ac5ee568e2ce4d345cdf6bfa8b2915d2b`: receive ownership protocol 수정
- `f5d7cccde238de29d3ee9484fac86b678efda48f`: Windows entropy와 context termination 수정

두 커밋은 part submit API, submit result 변환, public handle의 close admission을 바꾸지
않았다. `core/include` 차이도 version 문자열뿐이다. 따라서 0.17.2에서 0.17.3으로 올라가며
close 경합의 submit 결과가 `EINVAL`에서 다른 값으로 바뀐 것은 아니다.

`29f4d8b45c` 이전의 `core/src/api/socket/part_helper_api.cpp:175-185`는 socket-wide
multipart owner와 현재 thread가 다르면 `EINVAL`을 반환했다. 같은 커밋 이후에는 현재
thread의 identity로 sequence를 찾거나 만들며, 현재 코드는
`core/src/api/socket/part_helper_api.cpp:287-343`에서 이 동작을 구현한다. 이 변경은
0.17.2에 포함되어 0.17.3에도 유지된다.

### Node binding 분류

`bindings/node/native/src/addon_message_parts.h:45-66`은 실패한 Core result를 그대로
반환한다. 실패 뒤의 `zlink_multipart_close`는 유효한 message를 닫을 때 errno를 바꾸지 않는다.
`bindings/node/native/src/addon_core.cc`의 stress 분류는 `ESHUTDOWN`을 `shutdown`에,
`EINVAL`을 `rejected_einval`에 각각 기록한다. Binding이 0.17.3 결과를 다른 counter로
잘못 옮기지 않는다.

### 다른 language binding 대조

`bindings/cpp/tests/stress/test_cpp_send_close_stress.cpp`와
`bindings/dotnet/tests/Zlink.Tests/test_socket_concurrency.cs`도 multipart 거절과 shutdown을
서로 다른 결과로 분류한다. 두 테스트는 어느 counter도 양수라고 요구하지 않아 이번처럼
실제 close 경합이 빠져도 통과한다. Node 테스트만 과거 multipart owner 충돌에서 생긴
`EINVAL`을 close 경합의 증거로 잘못 사용했다.

## 변경 내용

- `bindings/node/native/src/addon_core.cc`: 마지막 global attempt 하나를 Core 호출 직전에
  대기시킨다. Closer가 close 결과를 확정하고 release 신호를 보낸 뒤 이 attempt가 진행하므로
  close 수락 뒤의 `ESHUTDOWN` submit이 최소 한 건 발생한다.
- `bindings/node/tests/multipart.test.ts`: 현재 multipart 계약에 따라
  `rejected_einval == 0`을 확인하고, 확정된 close 경합 결과로 `shutdown > 0`을 확인한다.
- `bindings/node/dist-tools/tests/multipart.test.js`: TypeScript test build가 만든 같은 assertion을
  반영한다.

수정 전에는 attempt counter와 Core 호출 사이의 timing을 scheduler에 맡겼다. 수정 후에는
마지막 submit이 close 완료 뒤에 진입한다는 동기화 규칙 하나가 그 순서를 결정한다.
