Kotlin의 실제 위치는 `framework/languages/java/zlink-framework-kotlin`이다. `framework/languages/java/zlink-framework-kotlin/build.gradle.kts:14`와 `framework/languages/java/zlink-framework-kotlin/src/main/kotlin/systems/zlink/framework/kotlin/ZLinkRouteMeshExtensions.kt:13`, `framework/languages/java/zlink-framework-kotlin/src/main/kotlin/systems/zlink/framework/kotlin/ZLinkFrameworkExtensions.kt:98`에서 Java runtime 위임을 확인했다. Kotlin의 독립 mesh/channel/session transport 구현을 확인한 것처럼 표시하지 않았으며, 실행을 통한 언어 parity 검증은 수행하지 않았다.

하위 계약은 다음 한계까지 적용했다. Core READY는 peer ROUTER의 RID admission 완료를 뜻하지 않는다(`core/doc/spec/core/socket/README.ko.md:165`). DISCONNECTED의 게시와 소비는 다르며 monitor record는 queue 포화 시 유실될 수 있다(`core/doc/spec/core/06-monitoring.ko.md:519`). Close/unbind의 endpoint 해제는 반환 전에 끝나지만 disconnect 뒤 physical teardown은 비동기다(`core/doc/spec/core/socket/README.ko.md:623`, `core/doc/spec/core/socket/README.ko.md:853`, `core/doc/spec/core/socket/README.ko.md:873`). 따라서 service identity·owner lease 확인, 정규 service probe, fanout beacon과 binding별 logical disconnect 중복 제거를 일괄 삭제 대상으로 보지 않았다.

제안의 공개 관찰 계약은 해당 소유 문서의 마지막 검증 요구 절에 한 번 두고, 본문은 근거·메커니즘을 설명하도록 구분했다(`doc/principal/documentation/spec-writing-guide.ko.md:367`, `doc/principal/documentation/spec-writing-guide.ko.md:378`, `doc/principal/documentation/spec-writing-guide.ko.md:701`). 내부 소유권·상태 불변 조건은 본문에 두며 white-box 항목을 검증 요구로 옮기지 않는다. A/B/C/D 진단 분류는 구현 변경을 검토하는 finding의 영향 항목에 덧붙였다.

### F-R5-9 ClientServer ready 대기의 호출 deadline 이탈

- 분류: `parity-gap`
- 위치: `framework/doc/framework/common/spec/server/02-channel-transport/02-channel-messaging.ko.md:170`, `framework/doc/framework/common/spec/server/02-channel-transport/02-channel-messaging.ko.md:172`, `framework/doc/framework/common/spec/server/02-channel-transport/02-channel-messaging.ko.md:178`, `framework/doc/framework/common/spec/server/02-channel-transport/02-channel-messaging.ko.md:181`; 경과시간 단일 clock `framework/doc/framework/common/spec/server/02-channel-transport/05-transport-liveness.ko.md:70`. 하위 request admission-time budget `core/doc/spec/core/socket/README.ko.md:1079`. 제안 위치 `framework/doc/framework/common/spec/server/02-channel-transport/02-channel-messaging.ko.md:675`.
- 현재 규칙(인용): “대기 한도는 해당 호출의 request timeout과 5초 중 짧은 쪽”(`framework/doc/framework/common/spec/server/02-channel-transport/02-channel-messaging.ko.md:172`)
- 문제: Node의 ready wait는 개별 호출 timeout을 받지 않고 Channel/host 기본 설정으로 별도 deadline을 만든다. 그 뒤 dealer.request에는 원래 timeout 전부를 다시 준다. Java도 request call builder를 반환하기 전에 Channel 기본 timeout으로 동기 ready wait를 수행하므로 뒤에 지정할 호출별 timeout이 이 대기를 제한할 수 없다. .NET·C++는 ready wait 전부터 원래 operation deadline을 세고 남은 시간만 request에 준다. Node에서 기본 timeout 5초, 호출 timeout 100 ms, ready가 400 ms에 생기는 정적 예시라면 100 ms 요청이 그때까지 대기한 뒤 다시 전체 timeout을 쓰는 경로가 있다. 이는 실행 측정이 아닌 코드상 deadline 경계의 반례다.
- 제안: `framework/doc/framework/common/spec/server/02-channel-transport/02-channel-messaging.ko.md:675` §10 「완료와 재전송」이 deadline의 관찰 계약을 소유하고 §3.2는 대기 이유만 설명한다 — “ClientServer 호출의 ready 대기는 호출 제출 때 정한 원래 deadline과 5초 중 먼저 오는 시점까지만 수행되고 후속 request는 그 원래 deadline의 남은 시간 안에서 완료된다.”
