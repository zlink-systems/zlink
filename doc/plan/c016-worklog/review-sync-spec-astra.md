# review-sync-spec — 동기화 규칙 문서 리뷰

대상은 `core/doc/spec/core/systems/11-synchronization-model.ko.md`와 `.en.md`다. 두 언어판은 주요 규칙과 문제를 함께 공유한다. 아래 `K`와 `E`는 각각 한국어판과 영어판의 행 번호다. 제안 문장은 별도 표시가 없으면 두 언어판에 같은 의미로 적용한다.

이 문서는 **코드가 따라야 하는 규칙**으로 검토했다. 현재 코드에 lock이 있다는 이유만으로 무잠금 목표를 오류로 판정하지 않았다. **성립**은 읽은 코드로 확인한 범위, **예정**은 현재 미성립이지만 계획 §7.7에 대응 항목이 있는 경우, **미포함**은 미성립을 확인했지만 §7.7에 구체적 대응이 없는 경우, **오류**는 잘못된 사실·조건·산식 또는 공개 계약과 충돌하는 규칙이다. 절차 요구는 실행 증거 없이 달성 여부를 판정할 수 없으므로 별도로 표시한다.

검토는 `main` 작업 트리에서 수행했다. 검토 중 확인한 HEAD는 `c0c561ae63bb5aabbbadd44a49dbb9ccacbd6717`, 종료 확인 시 HEAD는 `dfe6ec2829814a4267de1d86cffccdfaeb25df02`였다. 두 커밋 사이의 `core/src/`와 대상 문서에는 diff가 없었다. 기존 작업 및 병행 작업에서 생긴 테스트·진행 파일 변경에는 관여하지 않았다. 빌드·테스트·커밋은 실행하지 않았다. 아래 행 번호는 열람한 작업 트리 기준이며, 지정 코드에서 호출되는 소유자·플랫폼 구현을 확인할 때만 추가 파일을 좁혀 읽었다. 이 보고서 외에는 파일을 생성하거나 수정하지 않았다.

## 2. 다른 스펙과의 정합

현재 구현 설명과 목표 규칙이 다르다는 사실만으로 정식 계약 충돌이라고 판정하지 않았다. 반면 공개 오류 결과·level readiness·회계 경계를 바꾸는 문장은 실제 충돌이다. 다른 스펙의 짧은 요약은 소유 문서와 적용 범위를 밝히면 유지할 수 있다.

## 반드시 고칠 것

- **Turn 획득·해제와 대기 설명:** release store를 다른 bit를 보존하는 RMW로 고치고, CAS 횟수 단정·없는 backoff 참조를 제거한다. 공개 연산 하나와 turn 하나를 동일시하지 않는다(R04, R13–R15, R20–R22).
- **공개 lifecycle 경계:** close를 일반 대기형 직렬화에 포함하지 않는다. 공개 동시성 범위의 소유자는 04가 아니라 Socket 공통 §2와 함수별 계약이다(R03, R16; S01–S04).
- **Wake 원인과 책임:** ypipe sleep, head 재분류, commandless 신호, public poller re-arm을 구분한다. ‘잠듦 전이만 유일한 원인’, ‘mailbox 전체가 전이당 1회’, ‘영구 단일 signaler reader’ 단정을 고친다(R26, R35–R42; S07–S08).
- **Credit의 의미:** written−read를 여유 credit이라고 부르지 않는다. generation·multipart·candidate와 waiter/LWM 조건은 회계 소유 스펙에 위임한다. `_out_active`를 단방향 flag라고 설명하지 않는다(R29–R32; S09).
- **안전한 lock 제거 조건:** context snapshot reader와 공유 수명 상태를 포함한다. Cold reader만 lock을 유지하면 hot writer와 동기화되지 않는다는 조건을 명시한다. 단일 전역 lock 순서가 현재 전체 코드의 사실인 것처럼 쓰지 않는다(R19, R33, R48, R50).
- **C1/C2/C3의 경계:** context socket registry 전체를 C1 예로 쓰지 않는다. 교차 불변식에 참여하는 상태를 atomic 타입이나 pipe 경계만으로 C3로 분류하지 않는다(R08–R12, R43, R63).
- **표준·플랫폼 단정:** `seq_cst`가 ‘동시에 보게 한다’는 표현, recursive mutex+CV가 무조건 UB라는 설명, 모든 backend의 ERRORCHECK 보장을 고친다(R47, R49, R56).
- **다른 규칙의 소유권:** Framework 전체 모델과 같다는 문장과 executor 대체 설명을 한정한다. HWM 관측 시점을 11에서 선허용하지 않는다(S11–S13).
- **문서 구성과 링크:** 내부 확인 조건을 해당 규칙으로 옮기고 마지막 검증 절에는 관찰 결과를 둔다. 공개 plan 링크를 제거하고 Framework 상대 링크의 깊이를 고친다(W11–W14).

## 고치면 좋은 것

- lock 필요성의 판단 질문을 앞세우고 상태 예를 구체적인 동작으로 소개한다. 모든 제목을 억지로 질문형으로 바꿀 필요는 없다(W02–W04).
- 중복 규칙을 §2·§3에 모으고 §4·§5·§7은 적용 기준과 참조로 줄인다(W05).
- 선택표는 조건을 앞에 두고, 주체와 경로 빈도를 같은 비교축에 섞지 않는다. 금지표에는 따를 규칙을 연결한다(W07–W10).
- 대기와 re-arm을 보여 주는 짧은 sequence diagram을 추가한다(W16).
- 구어 비유, ‘모든 경우 cache line 왕복’ 같은 비용 단정, ‘경고 차이 0’의 모호함을 정리한다(R52, R60; W15, W18).
- 상하단 내비게이션에 상위 스펙 목차를 추가하고, 식별 불가능한 ‘알려진 수정’은 회귀 목록의 소유 위치로 연결한다(W12, W17).

## 그대로 둘 것

- **규칙이 목표이고 현재 코드의 차이·진행은 계획 §7.7이 소유한다는 역할 분리.** 공개 spec에 계획 링크를 남기는 문제와 역할 분리 자체는 별개다.
- **하나의 교차 불변식에 하나의 실행 소유자를 둔다는 방향.** 아직 남은 `receive.sync`, route/poller lookup lock과 pipe `_out_sync`를 근거로 목표를 현재 구현에 맞춰 되돌리지 않는다.
- **모든 socket command batch를 같은 turn에서 적용하는 규칙.** 현재 코드에서도 확인되며 socket type·빈도별 예외를 없앤 방향이 맞다(R17).
- **SPSC queue에 별도 상태 mutex를 추가하지 않는 원칙, mailbox producer 발행 직렬화, planned=applied 빠른 반환.** 적용 범위와 backend 조건을 정확히 한정하면 유지할 수 있다(R24, R36, R45).
- **공개 polling·동시성·회계 결과를 보존하고 검증하는 요구.** 내부 event 횟수 불변과 공개 결과 불변을 구별하는 것이 수정 방향이다.
- **두 언어판의 공통 규칙 구성과 실측 진행표를 본문에 두지 않은 점.** 이번 핵심 문제는 번역 불일치보다 양쪽이 공유하는 범위·사실 단정이다.

## 총평

이 문서의 단일 상태 소유와 불필요한 lock 제거 방향은 유지할 가치가 있다.
§7.7에 예정된 구현 차이를 문서 오류로 취급해 목표를 되돌려서는 안 된다.
그러나 turn 해제, wake의 유일성, credit 산식, thread 고정과 lock 순서에는 중요한 단정 오류가 있다.
특히 context snapshot과 공유 수명 상태를 빼고 lock을 제거하도록 읽히는 규칙은 보완이 필요하다.
Close·polling·HWM과 Framework 모델의 소유 경계를 명확히 하고 양 언어판을 함께 고쳐야 한다.
내부 확인 조건·공개 검증·진행 기록을 분리하면 규칙 문서의 역할이 더 분명해진다.
보고서만 생성했으며 빌드·테스트·커밋은 실행하지 않았다.
