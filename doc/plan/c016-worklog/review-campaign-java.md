검토일: 2026-09-05  
범위: 지정된 16개 commit의 diff와 `doc/plan/c016-worklog/*.md` worklog, 현재 Core·binding·Framework spec, C++·Node 대응 구현  
방법: read-only 정적 검토. build·test·gate는 실행하지 않았다.

## 결론

- 순수 0.17.0 계약 적응(A)은 `4d263e66b9`, `4af4f66f31`, `36c310ffef` 세 건이다.
- Java 실행 구조의 잠복 결함 수정(B)은 `af7afd28e7`, `6682ae0db1`, `dc9fe76100`, `424b15684c`, `7b0590183d`, `efad74ef94` 여섯 건이다. 새 Core가 원인을 만든 것이 아니라 public completion owner와 DONTWAIT 즉시 실패가 기존 동기 경계를 더 쉽게 드러냈다.
- test·sample·runner 한정(E)은 `2b1d0c794c`, `ed156f5983`, `ec2ee1ea50`, `9e76d053e5`, `83dfe33fb5`, `cb22cf6ae5` 여섯 건이다. DeliveryDispatch 변경은 Framework 지연을 숨긴 workaround가 아니라, offer가 전송되기도 전에 courier 응답 시간을 소모하던 sample 자체의 순서 오류를 고쳤다. 다만 “수신 후”의 정확한 시점은 아래의 별도 spec gap이다.
- `e65abaf7ac`은 pull-completion 부분만 보면 필요한 적응이지만, 같은 commit이 physical replacement fence를 제거해 두 M6A 계약 test를 깨뜨렸다. commit 단위로 하나만 고르는 이 review에서는 D로 판정한다.

또한 질문에 적힌 “unknown ROUTER RID = `NOT_FOUND/ENOENT`”는 flags를 생략한 요약이다. 현행 Core 계약은 `NONE` request에는 `NOT_FOUND/ENOENT`, `DONTWAIT` request와 DONTWAIT send에는 `NOT_CONNECTED/EHOSTUNREACH`를 정한다(`core/doc/spec/core/socket/README.ko.md:936-950,1018-1022,1054-1055`). 따라서 Java shutdown에서 관찰한 DONTWAIT `NOT_CONNECTED` 자체는 Core나 Java binding의 오분류가 아니다.

## 마지막 세 async/state-lane 수정의 완전성

`424b15684c`, `7b0590183d`, `efad74ef94`는 관찰된 command 36·control·bound-session push 경로의 원인은 제대로 고쳤지만, Java STREAM의 위험한 동기 bridge를 체계적으로 모두 제거하지는 않았다. 모든 `inStateLane().join()`을 없애는 것이 답도 아니다. State ownership spec은 기존 동기 표면이 외부 gate 재획득 없음, async continuation, 반환 전 registration/capture 필요라는 세 조건을 만족하면 blocking compatibility bridge를 허용한다(`01-execution/06-state-ownership-and-lanes.ko.md:212-263`). 남은 실제 위험은 다음 두 곳이다.

1. `ZLinkJavaStreamSocket.replyAsync()`는 여전히 호출 thread에서 `admissionTimeout()`을 먼저 읽는다(`ZLinkJavaStreamSocket.java:285-290`). 이 호출은 `ZLinkJavaSocketBacked.java:11-15`의 `nativeSocket()`을 거쳐 `ZLinkJavaStreamSocket.java:102-117`의 lane `join()`으로 이어진다. 실제 Framework reply 호출자가 `ZLinkStreamSessionContextState.java:404`, `ZLinkStreamSessionCalls.java:330`, `ZLinkBoundActor.java:346,457`에 있으므로 “async entry는 lane queue 전에 반환”이라는 앞선 두 fix의 원칙이 아직 일관되지 않다.
2. `close()`는 state lane에 들어간 채(`ZLinkJavaStreamSocket.java:567-574`) remote unbind future 전체를 최대 500 ms 기다린다(`:581-625`). State lane turn 안에서 장기 외부 operation 완료를 기다리지 말라는 spec(`01-execution/06-state-ownership-and-lanes.ko.md:71-91`)의 직접 위반이다. 이 wait 뒤에 `recv()`·`disconnectPeer()` 같은 짧은 lane 작업도 함께 밀릴 수 있다(`ZLinkJavaStreamSocket.java:143-174`).

따라서 세 commit을 revert할 이유는 없지만, “관찰된 sample만 green”을 완료 조건으로 삼아 lane audit를 닫아서는 안 된다.

## 알려진 M6A 두 실패 판정

두 test는 현행 spec 규칙을 encode하며 campaign 변경과 모순된다.

- `descriptorFenceReplacesEndpointOnlyIntent()`(`ZLinkJavaRawMeshNodeM6ATest.java:555-609`)은 endpoint-only intent가 아직 live일 때 descriptor-backed replacement를 거부하고, physical close를 관찰한 뒤에만 새 lifecycle을 admit해야 한다고 검사한다. 실패한 `assertTrue(live)` helper는 현재 `:1430-1440`이다.
- `observedInprocCloseDoesNotFenceDescriptorReplacement()`(`:613-655`)은 remote inproc close를 `CLOSED`로 관찰하고 transport intent까지 닫힌 뒤 새 descriptor replacement가 admit되는지 검사한다. 실패한 state helper는 `:1386-1400`이다.

이는 `02-channel-transport/06-wire-protocol.ko.md:329-342`와 `03-spot-actor/08-routing.ko.md:156-177`의 “close snapshot 뒤 replacement”를 그대로 검증한다. `af7afd28e7`의 edge-less READY 무시는 이 test와 모순되지 않는다. Core spec상 그 event는 close가 아니라 count snapshot이므로(`core/06-monitoring.ko.md:92-95`) 이를 close로 사용했던 것이 잘못이다. 필요한 것은 진짜 DISCONNECTED/CLOSED wake와 exact old-connection attribution이다.

이 두 실패를 campaign보다 “pre-existing”이라고 부른 worklog 분류는 역사적으로 부정확하다. `e4442b8456`은 두 test를 포함한 M6A 30/30 및 Java 전체 1,207/1,207 green을 기록했고, 그 commit은 `e65abaf7ac`의 ancestor다. 이후 `e65abaf7ac` diff가 monitor callback과 pair fence를 제거했고 결과가 1,205/1,207이 됐다(`decisions.ko.md:316-317,483-494`). 즉 후속 commit들 기준으로는 known-existing failure였지만, 이 campaign 전체 기준으로는 `e65`가 만든 회귀다. Assertion을 완화하거나 “known C”로 계속 제외하면 안 된다.

## 재수정 권고

1. **P0 — Java monitor/replacement fence를 root에서 재설계한다.** `bindings/java`가 monitor readiness를 public poller 또는 동등한 waitable handle로 제공하고, Core/common Framework가 replacement fence에 허용하는 identity를 명시해야 한다. 그 뒤 Java가 DISCONNECTED/CLOSED를 놓치지 않고 old connection만 retire하도록 복원한다. 완료 기준은 위 M6A 두 test를 변경 없이 통과시키고, inproc·TCP에서 늦은 old event가 replacement를 닫지 않음을 검증하는 것이다.
2. **P1 — STREAM async entry와 close를 owner 단위로 마무리한다.** `replyAsync()`의 timeout lookup도 `submitOwnedStreamFrameAsync()` lane turn 안으로 옮긴다. `closeOnLane()`은 lane 안에서 binding snapshot/retirement claim만 만들고, unbind waits는 lane 밖에서 all-settled로 기다린 뒤 lane에서 final cleanup을 확정한다. lane을 붙든 deterministic regression으로 reply 호출이 즉시 stage를 반환하고 close 중 recv owner가 교착하지 않음을 확인한다.
3. **P1 — shutdown unbind의 terminal 집합을 좁힌다.** `isRemoteRouteUnavailable()`은 현재 모든 `SubmitResult.NOT_ADMITTED`도 허용한다(`ZLinkJavaStreamSocket.java:824-835`). Core는 예를 들어 ROUTER가 DEALER RID에 typed request를 보내면 `NOT_ADMITTED/EPROTOTYPE`이라고 정한다(`core/socket/README.ko.md:1018-1022`). 관찰된 정상 race는 `NOT_CONNECTED/EHOSTUNREACH`였다. `NOT_ADMITTED`를 무조건 idempotent로 삼지 말고 result+errno/lifecycle cause를 검사하며 unexpected protocol failure는 `TeardownFailed`로 보존한다.
4. **P2 — STREAM control failure 정책을 언어 간 통일한다.** Java `sendControlAsync()`은 validation·OOM을 포함한 모든 synchronous `RuntimeException`과 모든 async failure를 로그만 남기고 success stage로 바꾼다(`ZLinkStreamRuntime.java:1492-1525`). C++도 catch-all best effort이고 Node는 send 실패 시 해당 session을 transport error로 닫는다. expected route-gone만 best effort인지, unexpected local error도 drain 성공인지 spec을 정한 뒤 Java/C++/Node를 맞춘다.
5. **P2 — DeliveryDispatch latency는 별도 관측만 남긴다.** 2.653 s Tracking request는 현재 명세 위반 증거가 없고 offer deadline의 시작 전이었다. 이를 DONTWAIT 회귀로 재분류하지 않는다. 다만 message-flow로 publish submit, remote admission, handler, reply completion 구간을 나눠 이후 성능 회귀 판단 자료로 보존한다.

## 스펙 gap 후보

1. **Physical replacement identity와 Java binding surface 충돌.** Common Framework spec은 `transportPairId/transportPairGeneration`으로 old pair를 fence하라고 하지만(`02-channel-transport/06-wire-protocol.ko.md:329-342`), Core 0.17은 `connection_id`를 진단·correlation 전용이라고 하고(`core/06-monitoring.ko.md:530-536`), Java binding은 pair/generation을 공개하지 않는다(`bindings/doc/spec/java/README.ko.md:1084-1092`). 어떤 identity와 어떤 event로 replacement gate를 열지 단일 권위 규칙이 필요하다.
2. **Java monitor drain ownership 부재.** Java `Poller`는 Socket/FD/timer만 받고 `SocketMonitor`를 받을 수 없다(`bindings/java/src/main/java/systems/zlink/contracts/eventing/Poller.java:12-34`); monitor는 blocking/default recv와 DONTWAIT recv만 제공한다(`bindings/java/src/main/java/systems/zlink/contracts/eventing/SocketMonitor.java:11-19`). Callback을 제거한 pull model에서 Framework가 event loss 없이 잠들 수 있는 표면이 명시되지 않았다. C++/Node와 동등한 monitor readiness 계약이 필요하다.
3. **DeliveryDispatch의 “received” 시각.** Sample §7.2는 courier가 offer를 받은 뒤 deadline이라고 하지만 current 네 언어는 status publish 뒤, actor send 직전에 시간을 기록한다. One-way admission success는 remote handler receive ACK가 아니다. 계약을 “local actor-send admission 시각”으로 고치거나, 정말 receive 시각이면 explicit ACK/offer-accepted control을 추가해야 한다. 현재 parity test는 전자를 사실상 고정하지만 spec 문구는 후자다.
4. **STREAM control submit failure.** Heartbeat ping/pong 및 session-closing admission 실패가 per-session transport error인지, teardown best effort인지, host termination failure인지 공통 server spec이 정하지 않아 Java/C++/Node가 다르다.
5. **Shutdown unbind terminal mapping.** Session all-settled 규칙은 있지만 Core result/errno 중 무엇이 “이미 사라진 remote route”이고 무엇이 실제 protocol/ownership 실패인지 공통 매핑 표가 없다. 최소한 `NOT_ADMITTED`의 blanket 수용은 금지하고 exact mapping을 spec 또는 공용 mapper가 소유해야 한다.
