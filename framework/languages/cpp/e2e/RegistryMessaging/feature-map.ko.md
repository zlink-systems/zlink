# C++ Location Messaging E2E Feature Map

이 문서는 `framework/doc/framework/common/e2e/config-1-location-messaging.ko.md`의
시나리오를 C++ framework E2E가 어디까지 검증하는지 정리한다. C++ 디렉터리와 일부 namespace는
시나리오 ID 연속성을 위해 아직 `RegistryMessaging` 이름을 유지한다.

| Scenario | 상태 | 근거 |
|----------|------|------|
| `RM-A1` | public contract 구현 gap | 구현 가능한 automatic discovery request 경로는 current exact API로 이관했다. Runner는 두 Provider와 endpoint가 없는 Consumer에 같은 Redis Location Store를 등록한다. Consumer의 첫 의미 request를 한 번만 제출하고 선택된 `api-a` 또는 `api-b` reply와 해당 Provider evidence를 확인한다. Forward actual `logs/20260729-040424-3961146`, reverse `logs/20260729-040454-3963029`, fixed shuffle `logs/20260729-040458-3963605`가 모두 exit code 0으로 통과했다. Retry, skip과 settle sleep은 없다. 공통 RM-A1의 전체 완료 조건인 ready Server 2개 public snapshot은 검증하지 못했다. 현재 C++ profile 경로는 ClientServer인데 exact 문서가 정의한 `client_server_runtime_t`가 source에 구현되어 있지 않다. RouteMesh status나 Location Store provider query로 바꾸면 다른 물리 topology 또는 내부 저장소 상태를 검증하므로 사용하지 않는다. 공통 RM-A1의 automatic RID prefix도 exact 문서의 `set_automatic_routing_id_prefix(...)`가 current C++ source에 없다. 두 public-contract implementation gap을 먼저 해소해야 전체 RM-A1을 완료할 수 있다. |
| `RM-A2` | 구현 | Exact `client().connect(endpoint)`를 ClientServer ready target으로 연결했다. 최초 handshake에서 Server RID와 lifecycle generation을 고정하고, 같은 endpoint의 automatic descriptor가 나타나면 기존 연결을 automatic key로 옮겨 중복 연결을 만들지 않는다. Select-one은 bounded smooth weighted state를 사용한다. Focused test는 `300:100`을 400회에서 정확히 `300:100`으로 선택하고, weight `0`과 draining으로 후보에서 빠진 member를 선택하지 않으며, candidate 제거 뒤 state와 absolute credit가 active total 이내로 줄어드는지 확인한다. Actual `logs/20260729-043646-565086`에서 최초 manual request, topology 변경 중 in-flight request 보존, `api-a`·`api-b` 두 ready target 처리와 provider evidence가 모두 통과했다. |
| `RM-A3` | 구현 | 공통 connection policy를 production automatic planner와 manual handshake에 연결했다. 두 Object Client 모두 RouteMesh Channel Server membership이 없을 때만 `NotRequired`이며, weight `0`을 포함해 어느 한쪽에 Server membership이 있으면 연결이 필요하다. Current public contract로 Provider와 ObjectClient target을 다시 build한 뒤 actual `logs/20260803-101440-667730`에서 Automatic pair와 Manual pair를 각각 80회 조회했다. 두 phase 모두 20초 동안 `NotRequired`, ready peer 0과 failure 0을 유지했다. Manual peer endpoint 앞의 TCP proxy는 각 logical `peer_connections().connect()` intent에 대해 Core가 제공하는 Application/Completion transport lane 2개를 기록했으며, 추가 reconnect는 없었다. 별도 trace run `logs/20260803-101301-665122`의 process stderr file log에서 `hello`와 `admit` control record를 확인했고, physical lane 수를 logical intent 수로 잘못 세지 않도록 runner assertion을 수정했다. Object Client RID의 Node direct 결과는 `request_target_not_found`인 typed `NotFound`였다. Weight `0` Server descriptor가 ready인 상태에서 process를 정지하자 다른 Object Client가 `NotConnected`와 `no_ready_peer`를 표시했고, process 재개 뒤 양쪽 public status가 ready connection 하나를 표시했다. Runner 종료 뒤 process와 test Redis container가 남지 않았다. |
| `RM-A4` | public contract 구현 gap | Public messaging replacement subflow는 완료했다. Persistent Consumer가 v1 request와 evidence를 확인한 뒤 v1 process를 종료하고, 다른 endpoint의 v2를 시작한다. Retry 없이 제출한 첫 request부터 연속 20개가 모두 `api-a-v2` reply와 v2 evidence로 확인됐다. Actual `logs/20260729-044350-867543`이 exit code 0으로 통과했다. 이전 fixture의 `/locations/peers`는 ClientServer replacement를 별도 RouteMesh fixed RID row로 대신 검증하므로 제거했다. Canonical RM-A4 전체 조건인 새 automatic RID suffix, old RID 제외/new RID Ready public status, `Shutdown` terminal과 active-claim conflict 반복은 남아 있다. Exact C++ 문서의 `mesh_node_builder_t::set_automatic_routing_id_prefix(...)`와 `client_server_runtime_t`가 current source에 구현되어 있지 않으므로 fixed RouteMesh RID나 Location Store provider query로 대체하지 않는다. |
| `RM-A6` | public status 구현 gap | Public messaging 격리 subflow는 완료했다. 같은 Redis Location Store를 사용하는 persistent Consumer 하나가 `api`와 `workflow` ClientServer client role을 함께 등록한다. 두 ChannelName request의 reply와 provider evidence가 서로 섞이지 않는지 양방향으로 확인한다. `api-b` scale-in 뒤 workflow와 남은 `api-a` routing이 모두 성공하고, workflow scale-in 뒤에도 `api-a` routing이 성공한다. Actual `logs/20260729-045601-1343518`이 재시도 없이 exit code 0으로 통과했다. Canonical RM-A6이 요구하는 MeshName별 status sequence와 ready target count는 exact C++ 문서의 `client_server_runtime_t`가 current source에 구현되어 있지 않아 남아 있다. RouteMesh status나 Location Store provider query로 대체하지 않는다. |
| `RM-A7` | actual-process 구현 gap | Global authority의 핵심 상태 전이는 focused `test_cpp_framework_m6b_runtime`에 고정했다. 서로 다른 initial Mesh의 같은 Actor ID는 하나의 create attempt에 합류하고, 다른 stable type은 `type_mismatch`로 끝난다. User Spot도 Store가 예약한 같은 global reference에 합류하며 다른 stable type을 거부한다. Commit 뒤 반대 Mesh를 지정한 Actor·Spot create는 기존 Mesh와 object generation을 유지한다. Focused target build와 실행은 exit code 0이다. 이 검증을 actual E2E 완료 증거로 대신 사용하지 않는다. 현재 public Object fixture인 `SpotActorTransfer` ActorNode는 C++ exact interface 변경 뒤 Spot Actor handler context, context 소유권, factory callback, relocation adapter 반환형과 Location option이 맞지 않아 target 자체가 compile되지 않는다. 따라서 두 process의 public `GetOrCreate`·`Find`·direct Actor/Spot request evidence는 아직 없다. Private Store 조회나 이전 helper로 우회하지 않고 fixture를 current public contract로 이관한 뒤 actual을 추가한다. |
| `RM-B1` | 구현 | client 실행 중 `api-b` provider를 추가하고 두 provider로 분산되는지 검증한다. 최신 전체 통과: `logs/20260708-131829-51832`. |
| `RM-B2` | 구현 | 두 provider의 시작 순서를 `E2E_START_ORDER`로 바꿀 수 있다. store consumer에서 16개 request가 진행 중일 때 `api-b`를 종료하고, 각 완료를 정상 reply 또는 정해진 public error로 분류한다. MeshNode descriptor 제거 직후 재시도 없이 보낸 20개 request가 모두 `api-a`에서 처리되는지도 검증한다. |
| `RM-B3` | 전환 필요 | provider A handler-start evidence 뒤 A를 `SIGKILL`하고, 같은 consumer의 in-flight 결과를 유한한 public error로 분류하며 자동 재전송이 없음을 확인해야 한다. crash 전파 구간과 descriptor 제거 뒤의 신규 request는 생존 provider B로 계속 처리되는지 별도로 검증한다. 현재 runner에는 이 전체 경계의 증거가 없다. |
| `RM-C1` | 구현 | request와 send happy path를 함께 검증한다. |
| `RM-C2` | 구현 | P0 미완료 항목 중 기존 exact RouteMesh Node direct API와 public topology snapshot으로 검증할 수 있어 먼저 완료했다. Public topology가 `api-b`를 Ready로 표시하는지 최대 3초 동안 확인한 뒤 targeted request를 한 번만 제출한다. Request는 `api-b`에서만 처리되고 `api-a` evidence에는 남지 않는다. 미등록 RID는 `RequestTargetNotFound`로 분류한다. Actual `logs/20260729-040050-3900121`이 재시도·skip·timeout 확대 없이 통과했고 runner exit code는 0이다. |
| `RM-C3` | 구현 | Consumer가 exact ClientServer `client().connect(endpoint)`로 두 Provider endpoint를 등록한다. 같은 ChannelName request 90건을 retry 없이 한 번씩 제출해 `api-a`·`api-b`가 모두 선택되고 reply 합계가 90인지 확인한다. 실행 전후 두 Provider의 public evidence 증가분도 정확히 90건인지 확인한다. Actual `logs/20260729-051403-2182401`이 exit code 0으로 통과했고 모든 stderr는 비어 있으며 process와 Redis container가 남지 않았다. |
| `RM-C4` | 구현 | store consumer HTTP role이 timeout request를 `TimeoutException`으로 분류하고, late reply가 후속 정상 request를 오염시키지 않는지 검증한다. |
| `RM-C5` | 구현 | store consumer HTTP role이 미등록 packet request를 `HandlerNotFound`로 분류하고, send drop 이후 정상 request 복구를 검증한다. |
| `RM-C7` | 구현 | `server_peer_weight`로 build-time server weight를 다르게 준 provider 두 개를 시작하고, location-store 자동 연결 client에서 high-weight provider가 더 많이 처리되는지 검증한다. 최신 전체 통과: `logs/20260708-131829-51832` (`api-a=59`, `api-b=41`). |
| `RM-C8` | 구현 | RouteMesh SS에는 Framework-level `MaxMessageSize`를 설정하지 않고 1 byte, 4 KiB, 256 KiB, 1 MiB payload의 length·SHA-256 왕복과 후속 정상 request를 검증한다. StreamNode Core STREAM inbound 상한은 별도 runtime·unit contract다. |
| `RM-C9` | 전환 필요 | 현재 runner는 다량 `ProfileMsg` 제출과 backlog 해소 뒤 후속 request 복구만 검증한다. non-blocking submit의 즉시 backpressure 결과와 blocking submit의 bounded admission 결과를 public send call에서 직접 대조해야 한다. |
