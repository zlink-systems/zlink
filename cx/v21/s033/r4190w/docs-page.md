# #4190 30초 warmup 재측정

측정 commit `d3fd955131`. 기존 r4190m과 같은 셀 집합·배치·3회 반복·5초 활성 측정·stream 설정으로 warmup만 30초로 재측정했다. 언어 결과는 48개씩, Kotlin 보조 셀 6개, C 기준 18개다. 전체 result 파일 warmup은 C++ 48/48, .NET 48/48, Java 48/48, Kotlin 6/6, Node 48/48, C 18/18이 모두 30초였고 `errors=0`, `abandoned=0`, `drain_bound_hit=false`였다.

## 조건·warmup 확인

- 배치 B: source CPU 0–7, target CPU 8–15. 측정 그룹은 `/root/jobs/fx/cx/measure.lock` exclusive lock 안에서 실행했고 CPU 0–15 governor performance, 종료 시 powersave 복구했다. 셀별 uptime/load, free memory, `scaling_cur_freq` 스냅샷은 `raw/bench/<언어>/run*/<cell>/conditions-{before,after}.txt`에 있다. 그룹 단위 lock 전후 상태는 `raw/lock-windows/`에 있다.
- C++ warmup 근거: `raw/bench/cpp/run1/zlink-framework-cpp-request-backpressure-4096/results.json:91` (`warmupSeconds: 30.000000`).
- .NET: `raw/bench/dotnet/run1/zlink-dotnet-request-serial-4096/results.json:14` (`warmup: 30`).
- Java: `raw/bench/java/run1/grpc-java-send-saturation-4096/results.json:17` (`warmupSeconds: 30.0`).
- Kotlin: `raw/bench/kotlin/run1/zlink-framework-kotlin-request-serial-1024/results.json:17` (`warmupSeconds: 30.0`).
- Node: `raw/bench/node/run1/zlink-framework-node-send-saturation-4096/results.json:18` (`warmup: 30`).

## A/A와 latency 참고

A/A는 r4190n에서 수행됐으나 per-run p50 샘플은 없어 보고할 수 없다. r4190n의 20개 `aa-clean` 표본에서 single-latency 중앙값 0.006109 ms (범위 0.003244–0.047212 ms), p95 중앙값 0.004688 ms (범위 0.003424–0.150528 ms), p99 중앙값 0.059520 ms (범위 0.016896–1.400832 ms)였다. 이 single-latency 중앙값은 p50이 아니다. 원시 근거: `../r4190n/report.md`, `/root/jobs/fx/cx/v21/s033/f4162/raw/aa-clean-01.log:5-7` 등.

이번 셀 집합은 request-serial, request-backpressure, send-saturation이며 PUBSUB latency 셀은 없다. 따라서 catch-up 미도달로 무효인 PUBSUB latency 셀과 in-flight floor 참고값은 없다. 이번 결과에는 `late_sends_gt_1ms` 계측 필드가 없어 그 카운트를 판별할 수 없다. latency 판정에는 reference 값을 사용하지 않았다.

## 요약

- 모든 언어와 C 기준의 result metadata에 warmup 30초가 기록됐다. Warmup 관련 unsupported 판정은 없다.
- C request-backpressure는 두 크기 모두 3회 judged runs를 제공했다. Main aggregator의 8개 Framework/binding 판정 중 C++ send-saturation 4096B는 C++ binding denominator의 G5 spread 21.9% (10% 한도 초과)로 unsupported 처리됐다. 이는 warmup 문제가 아니다.
- Node 행 중 G6 결과가 `실행 모델 상한 도달`로 표시된 것은 main aggregator 결과 그대로 기록했다.
- 보고서 숫자는 표별 원시 경로 열의 aggregate/result/CPU 파일에서 가져왔다. C++·.NET·Java·Node 집계 JSON은 main aggregator가 생성한 `raw/aggregates/` 산출물이다.
