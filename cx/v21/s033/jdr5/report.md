느린 reply를 고정한 회귀 테스트도 먼저 시험하였다. submit을 latch로 유지하고 첫 BUSY를 관측한 뒤 100ms 동안 close가 반환되지 않아야 한다는 검사를 추가하였다. production 수정 전 `/root/jobs/fx/cx/measure-shared.sh ./gradlew -p framework/languages/java --no-daemon --max-workers=2 :zlink-framework-core:test --tests '*ZLinkJavaRawServicePortContractTest.slowReplyAlreadySubmitting*'`를 저장소 root에서 실행하였다. 기존 구현은 100ms 전에 BUSY 실패를 반환하여 실패하였다. slow-reply-before.log와 slow-reply-before.xml이 이 음성 검증의 근거다. 임시 로깅은 추가하지 않았다. 이 테스트는 dispatch 이전 native lifecycle 경합을 다루므로 application message-flow 대신 기존 JUnit 예외와 stack을 보존하였다.

원인은 수정 전 ZLinkJavaRawServicePort.java:722의 CLOSE_BUSY_MAX_ATTEMPTS 판정이다. closeAttempt를 읽고 통과한 reply는 close thread보다 늦게 Core에 진입할 수 있다. 이미 Core API에 수락된 reply라면 같은 handle의 close는 BUSY이고, close가 먼저 수락되었다면 뒤늦은 reply 제출은 binding에서 TERMINATED로 거부된다. 어느 쪽인지는 Core·binding만 판정한다. Framework의 8회 제한은 이 사실과 무관한 별도 종료 예산이었다.

소유 계층은 다음과 같이 확인하였다. Core socket spec core/doc/spec/core/socket/README.ko.md:58과 :647은 같은 handle의 admitted API가 실행 중이면 EBUSY, close 수락 뒤에는 ESHUTDOWN이라고 정한다. binding spec bindings/doc/spec/README.ko.md:1851은 닫힌 socket의 reply 제출을 SubmitError(TERMINATED)로 정한다. Java binding NativeSocketRuntime.java:615의 closeInternal은 실패 시 native handle을 지우지 않는다. Framework는 close 수락을 예측하는 in-flight 상태를 만들지 않고 이 결과만 사용한다.

교차언어 구현도 대조하였다. C++ framework/src/runtime/backend/raw_route_port.cpp:506과 :527은 reply와 close에 기존 socket mutex를 공유한다. .NET Runtime/Service/ZLinkRawRouterServicePort.cs:170과 :178은 기존 비동기 socket disposal에 위임하고 :248에서 Received.Reply().Submit()을 사용한다. Node packages/framework/src/runtime/foundation/raw-service-mesh-runtime.ts:924는 reply capability에 위임하고 :1655의 close는 host.close() 실패 시 host를 보존한다. Java ZLinkJavaRawServicePort.java:533은 direct binding 제출, :660은 CloseAttempt로 close 소유자를 정한다. Kotlin은 같은 JVM core를 사용한다. 내부 실행 방식은 다르지만 Core·binding의 close 수락과 실패 시 소유권 보존을 상위 계층의 새 상태로 대체할 근거는 없다. 이번 변경은 공통 계약을 바꾸지 않는 기존 결함 수정 B이다.

선택한 정책의 원천은 runtime/host/ZLinkFrameworkRuntime.java:94의 DEFAULT_TERMINATION_DEADLINE 30초다. 기존 ZLinkJavaSocketOptions.java:15의 FRAMEWORK_LINGER도 이 기본 종료 정책을 따르는 30초였다. 별도로 선언한 30초를 없애고 ZLinkJavaSocketOptions.java:18도 같은 기본값을 참조하도록 하였다. ZLinkJavaRawServicePort.java:671은 이 기존 정책으로 close 호출 하나의 monotonic deadline을 계산한다. 생성자나 객체 필드에 timeout을 추가하지 않는다. :680에서 모든 router에 같은 deadline을 전달하고 :727에서 남은 시간을 확인한다. 1ms는 다음 close 호출 사이의 기존 양보 간격이며 전체 대기 한도가 아니다.

실제 host의 absolute deadline을 전달하는 방안과 socket linger 값을 읽는 방안도 비교하였다. ZLinkFrameworkShutdown.java:25와 :30의 자원 정리 단계는 host deadline 뒤에도 수행된다. ZLinkFrameworkRuntime.java:2359의 mesh_nodes_close는 meshNodes::close로 등록되며 host absolute deadline을 port까지 전달하지 않는다. port 단독 close와 runtime 단독 close에도 host가 없다. 또한 ZLinkJavaRawMeshNode.java:1094는 이미 대기 중인 output 폐기를 위해 linger를 0으로 설정한다. 이 옵션은 native API가 handle을 사용 중인지와 관계없으므로 대기 기한으로 읽으면 같은 결함이 유지된다. binding의 공개 Socket.close()에는 admitted API 종료를 기다리는 별도 close mode가 없고 native close는 위의 fail-fast 계약이다. 따라서 기존 기본 종료 정책을 공유하고 Core의 BUSY만 관측하는 방식을 선택하였다. 이 기한은 실제 host의 남은 drain 기한을 전달한 것이 아니라 port 자원 정리 호출의 공통 기한이다.

ZLinkJavaRawServicePort.java:724는 BUSY가 아닌 실패를 즉시 반환한다. :728은 기한 뒤에도 BUSY이면 마지막 ZlinkCloseException 자체를 반환한다. :685의 기존 실패 처리가 closeAttempt를 되돌리고, :681의 소유 목록 제거는 성공한 socket에만 수행된다. 따라서 실패한 socket은 다음 close의 소유 대상으로 남는다. 같은 thread의 재진입과 다른 thread의 close 합류는 기존 CloseAttempt가 담당하며 새 대기 기한을 만들지 않는다.

결정 위치 수는 다음과 같다. 종료 대기 예산을 독립적으로 정하던 곳은 수정 전 port의 8회 제한, socket option의 30초 선언, host의 30초 기본값으로 3곳이었다. 수정 후 예산 원천은 host의 기존 기본값 1곳이다. Core의 close 수락 판정은 1곳에서 1곳으로 유지하였다. Framework의 BUSY 재시도 계속 여부를 판정하는 함수도 1곳에서 1곳으로 유지하였다. 수락 여부와 대기 기한은 서로 다른 결정이므로 합산하지 않았다.

리팩토링 점검에서 종료 예산의 중복 정의 2곳을 제거하였다. 수정 전 ZLinkJavaRawServicePort.java:47의 시도 횟수 상수와 ZLinkJavaSocketOptions.java:15의 별도 Duration 선언이 대상이다. 새 runtime counter, queue, lock, cache, flag, 객체 상태나 예약 timer는 없다. 기존 시도 횟수 변수도 제거하였고 호출 지역변수인 monotonic deadline만 사용한다. 이는 기존 30초 정책을 적용하기 위한 시간 좌표이며 별도의 타이머나 동기화 수단이 아니다.

같은 호출 경로의 operations.close()는 ZLinkJavaRawMeshNode.java:5545와 ZLinkJavaRawServicePort.java:673에 존재한다. mesh의 논리 종료 완료 전에 pending operation을 끝내는 책임과 port 단독 정리의 책임이 달라 이번에 제거하지 않았다. 실제 종료 결정은 동일한 ZLinkServiceOperationRegistry.close()가 소유하며 두 registry나 별도 권위 상태는 없다. socket close가 실패한 뒤 다음 port.close()에서 poller.close()에 다시 도달하는 것도 ZLinkJavaRawServicePort.java:679와 ZLinkJavaSocketReceivePoller.java:215의 기존 닫힘 검사로 처리한다. 실패 socket의 소유 entry를 보존하기 위한 경로이므로 제거하지 않았다. 변경한 reply 제출에는 추가 encode, payload copy나 executor 인계를 넣지 않았다.

테스트는 시도 횟수와 독립적으로 바꾸었다. failedSocketCloseRetainsOwnershipUntilLaterCleanupSucceeds는 실제 기본 기한이 지날 때까지 계속 BUSY를 반환하고 원본 예외·소유 entry 보존을 검사한 뒤 BUSY를 해제하여 다음 close의 정리를 검사한다. meshExplicitCloseReachesRetainedSocketOwner도 첫 close 내내 BUSY를 유지하고 다음 close 전에 해제한다. 재진입 callback은 첫 close와 다음 정리 close에서 각각 한 번만 실행하며 reentrantCalls는 2를 유지한다. 세 번째 close는 native close를 반복하지 않는다. slowReplyAlreadySubmittingLeavesBeforeCloseSucceeds는 100ms 동안 reply를 유지한 후 해제하여 같은 close 호출의 성공과 message 소비를 검사한다. 두 native 경합 테스트의 반복 수는 각각 1000으로 늘렸다.

남은 실패는 위에 기록한 부하 실행의 reply 결과 assertion이다. close의 고정 횟수 제한 결함은 재현과 관련 테스트로 확인하여 수정하였지만, 이 assertion 실패를 전체 통과로 처리하지 않았다. 신규 queue·lock·cache·flag·runtime 상태는 0개이며 추가적인 runtime 변경, spec 변경이나 GitHub 작업은 하지 않았다.
