# C++ 요청·send 스레드 전달 축소 설계 조사 — #3867·#3868

호출→binding 제출은 준비된 remote target·무경합 경로에서 이미 같은 OS thread이므로, 직접 제출을 새 절감분으로 계산하지 않는다.
우선순위는 기존 receive 역할 배치 소유자에서 target handler 전달과 source completion 전달을 회전 단위로 줄이는 것이다. 성공한 경우 각각 최대 1회이며, 역할 통지 비용은 별도로 남는다.
Binding 완료의 terminal 확정은 이미 poller wait를 구동하는 receive 자원에서 한다. Core IO thread에서 직접 완료하는 안은 현재 binding 계약 변경이 필요하므로 BLOCKERS(D)다.
Wake 일괄 처리는 기존 owner queue·Core mailbox의 중복 억제를 재사용해야 한다. 별도 완료 drain queue로 callback들을 직렬화하지 않는다.
스레드 전달 축소만으로 비율 0.6에 도달한다는 근거는 없다. 아래 비용 한도는 제공된 cprof의 추정이며, 이 머신에서는 시간·처리량을 측정하지 않았다.

## 조사 범위와 계수

- 확인한 코드는 detached HEAD `910d1fc41f`다. 작업 시작 시 tracked/untracked 변경이 없었고 저장소 파일을 수정하지 않았다. 브랜치를 지정받지 않았으므로 변경·commit·branch 조작을 하지 않았다.
- 측정은 `/mnt/d/t/jobs/fx/cx/jhandoff2/cprof-report.md:1`의 `ee11390257`, request-backpressure 1024 B 셀만 인용한다. 현재 HEAD와 비교하면 lane·raw mesh·mesh runtime 등에 변경이 있다(`revision-core.log`). 실행 스레드의 기본 배치는 확인했지만, 그 측정값을 현재 HEAD의 재측정 결과로 간주하지 않는다. 이전 `FINAL.md`는 참고만 했다.
- `H`는 한 메시지의 실행 책임이 다른 자원으로 넘어가는 논리적 전달, `Q`는 queue 게시, `W`는 통지 호출이다. OS context switch·futex syscall과 서로 다른 계수다. Mutex 획득·notify 호출이 매번 futex·context switch를 발생시키지는 않는다. Frame별 pipe write와 record별 enqueue도 구분한다.
- 아래는 RouteMesh의 준비된 remote Node RID를 기본 경로로 한다. ChannelName의 selector 진입, 연결 준비 전 대기, HWM pending, local target, Yield·사용자 scheduler는 따로 표시한다. Core IO는 연결별 담당 thread이며, source·target마다 IO thread가 하나라는 뜻이 아니다.
- `/mnt/d/t/jobs/fx/cx/jhandoff2/cprof-report.md`에는 send-saturation의 세부 thread/counter 측정이 없다. Send의 구조는 확인했으나 request의 µs·전환수를 send에 그대로 대입하지 않는다.

**주 경로의 합계:** 동기 handler·준비된 remote Node·무경합·사용자 scheduler 없음인 request는 Framework 외 transport 경계 4개(제출→IO, target IO→receive, reply→IO, source IO→receive)와 Framework의 application 전달 2개(target receive→handler, source receive→completion)로 논리적 H=6이다. 이것은 OS context switch 6회나 매번 발생하는 queue/wake syscall 6회를 뜻하지 않는다. 즉시 send는 target handler까지 H=3이고 source 완료는 이미 확정된 admission이다. Pending send는 WRITABLE을 위한 source IO→receive와 receive→completion을 추가로 갖지만 횟수는 pending 비율·binding 재제출 횟수에 달려 고정할 수 없다. Remote one-way send에 응답 왕복을 더하면 안 된다.

ChannelName의 E2는 selector 소유 turn이 추가될 수 있고(`framework/doc/framework/common/spec/server/01-execution/08-messaging-hot-path.ko.md:97`), 실제 thread 이전 여부는 lane 실행 방식에 달린다. 연결 준비 대기는 `framework/languages/cpp/framework/src/runtime/mesh/raw_mesh_node_owner.cpp:319`, `:362`, `:400`의 별도 cold 경로다. HWM 대기·NO_DATA까지 drain 뒤 재제출은 binding의 책임(`bindings/cpp/src/Runtime/Messaging/completion_owner.cpp:691`)이며 Framework retry를 추가할 근거가 아니다.

### 언어 간 대조의 의미

.NET은 state lane inline claim(`framework/languages/dotnet/src/Zlink.Framework/Runtime/Execution/ZLinkStateLane.cs:90`)과 terminal atomic take 뒤 ThreadPool work item(`framework/languages/dotnet/src/Zlink.Framework/Runtime/Backend/DotNet/ZLinkMeshCompletionTable.cs:192`, `framework/languages/dotnet/src/Zlink.Framework/Runtime/Backend/DotNet/ZLinkCompletionDispatcher.cs:16`)을 사용한다. Java는 caller 자신의 synchronous turn(`framework/languages/java/zlink-framework-core/src/main/java/systems/zlink/framework/runtime/internal/execution/ZLinkStateLane.java:129`)과 platform receive pump(`framework/languages/java/zlink-framework-core/src/main/java/systems/zlink/framework/runtime/binding/ZLinkJavaRawMeshNode.java:5394`), shared completion pool(`framework/languages/java/zlink-framework-core/src/main/java/systems/zlink/framework/runtime/internal/service/ZLinkServiceCompletionDispatcher.java:53`)을 사용한다. Node는 event loop에서 lane FIFO와 Promise/microtask를 사용한다(`framework/languages/node/packages/framework/src/runtime/execution/state-lane.ts:67`, `framework/languages/node/packages/framework/src/runtime/foundation/raw-service-mesh-runtime.ts:790`). **언어별 내부 thread 수가 다르다는 것만으로 spec gap은 아니다.** §08.6이 명시적으로 실행 수단 차이를 허용한다(`framework/doc/framework/common/spec/server/01-execution/08-messaging-hot-path.ko.md:347`). Public 순서·직렬성·독립 진행이 달라질 때는 D로 중단한다.

## 설계안

### 1. target receive 역할 인계 후 현재 자원에서 handler turn 실행 — 조건부 B 후보

회전이 끝나 owner-ready batch를 꺼낸 뒤, 기존 application executor의 **자원 배치 소유자 하나**가 비어 있는 기존 worker에 같은 receive 역할을 독점 배정한다. 성공하면 이전 receive 자원이 기존 owner queue를 통해 새 application turn을 실행한다. 실패하면 현재의 worker 게시를 유지한다. 진입은 `framework/languages/cpp/framework/src/runtime/mesh/mesh_node_host_service.cpp:2283` 이후이고, 배정은 `framework/languages/cpp/framework/src/runtime/dispatch/offload_executor.cpp:172`의 기존 role/worker 배치에 통합한다. Record마다 판정하지 않는다.

- **계수 추정:** batch B개에서 실제로 현재 자원이 실행한 handler 비율을 pT라 하면 application payload H는 메시지당 pT 감소(최대 1). 기존 record owner Q는 유지한다. 사라지는 executor post는 message 수가 아니라 새 owner drain 수다. 다음 receiver를 깨우는 역할 통지는 회전당 최대 1회, 상각 1/B이며 반드시 순비용에 포함한다. 이미 같은 owner의 여러 record가 post 1개를 공유하므로 최대 1/msg 절감으로 단정하지 않는다.
- **문맥 전환·syscall:** 성공해도 배정 worker를 깨우므로 OS switch 순감소는 0일 수 있다. 유리한 경우 message가 수신 cache를 떠나 handler worker에서 다시 로드되는 전달과 task 게시가 줄어든다. 예상 방향은 감소 또는 동일, 보장 감소량은 0이다. target switch 총량 1.3143/msg가 관측 총 예산일 뿐 제거 가능한 몫은 미측정이다. 시간 절감 상한을 target handoff/wake 전체 6.106 µs/msg보다 크게 잡지 않으며, 그 전체도 Core lock을 포함하므로 실제 절감액이 아니다(`/mnt/d/t/jobs/fx/cx/jhandoff2/cprof-report.md:179`).
- **제출 CPU:** source caller의 직접 제거 작업 0, 기본 추정은 기존 profile 23.405 µs/msg 유지다. IO batching·경합의 간접 개선은 미측정이며 ≤6 µs를 주장할 수 없다.
- **계약·위험:** 기존 permit은 handler 첫 instruction 직전 반환하고, owner FIFO와 Spot/Actor gate를 유지한다. Node handler는 gate로 새 직렬화하지 않는다. 수신 역할을 넘긴 뒤 원래 wait/drain stack과 lane scope가 끝나야 한다. Socket·poller·cursor·permit·shutdown은 role 수명에 남는다. 오래 막힌 handler가 있어도 새 receiver가 관리·completion을 진행해야 한다. Typed decode는 새 application turn 안에 둔다. Ambient flow·corr·job·wait-owner는 기존 진입 경로로 복원한다.
- **규범·분류:** §08.4.4가 이미 허용하므로 spec 변경 불필요. 다만 현재 `_roles` queue와 `_idle_workers`만으로 '지금 비어 있는 자원의 독점 배정'을 증명해야 한다. 단순 `start_role()` enqueue나 idle 숫자 관찰만으로 성공이라 할 수 없다. 기존 배치 소유자를 이동·통합하지 않고 새 예약 flag/판정자를 더해야 한다면 이번 제약 아래 구현 BLOCKERS다. B 확정 전에는 코드 변경하지 않는다.
- **언어 일관성:** .NET의 기존 execution pool, Java의 pump/application executor 배치 소유자에서도 같은 계약은 성립한다. Java 현재 전용 pump를 넘기려면 기존 배치 구조 통합이 필요해 단순 C++ 코드 이식이 아니다. Node는 넘겨받을 자원이 없으므로 §08:313의 기존 microtask 경로를 유지한다. 공통 계약 시험으로 관측 결과를 맞춘다.

### 2. source receive 역할 인계 후 dispatcher의 새 turn을 같은 자원에서 실행 — 조건부 B 후보

방안 1과 같은 역할 배치를 source에도 적용한다. C1 terminal take와 등록된 dispatcher 자리는 유지한다. binding poller wait/drain이 끝난 회전 경계에서 역할 인계가 성공하면, 이전 receiver가 dispatcher turn을 실행하고 typed decode·caller continuation을 기존 경로로 재개한다. `dispatch_completion`에 즉시 실행 조건 하나를 덧붙이는 수정은 안 된다. 현재 `framework/languages/cpp/framework/src/runtime/dispatch/provider_task_context.cpp:181`의 inline 판정과 역할 배치 소유권을 하나로 모으는 설계여야 한다.

- **계수 추정:** 해당 source completion의 역할 인계 성공 비율 pC에 대해 H는 메시지당 pC 감소(최대 1). Dispatcher의 등록·대기 자리는 유지하며 게시를 로컬의 다음 turn에서 소비한다. 역할 통지는 1/B 추가다. request는 최대 적용, send는 BACKPRESSURED 뒤 완료되는 비율 f만 적용되어 최대 f·pC/msg 감소다. 즉시 admitted send의 현재 0회 완료 전달은 다시 줄일 수 없다.
- **문맥 전환·syscall:** completion worker post 감소 후보는 성공당 1회이지만 새 receiver 통지와 경쟁 비용을 차감해야 한다. 보장되는 switch·futex 감소량은 0이며 source 2.4606 switches/9.3719 futex 전부를 절감분으로 보지 않는다. 8 completion worker의 25.984 µs/msg는 실제 typed 처리·할당도 포함하므로 삭제되는 CPU가 아니다. 같은 일을 이전 receiver에서 수행하는 비용 이동이다.
- **제출 CPU:** 직접 제거 작업 0, 기본 추정 23.405 µs/msg 유지. 방안 1과 합쳐 H 최대 2 감소여도 submitter 20여 µs를 6 µs로 만드는 계산은 성립하지 않는다.
- **계약·위험:** 완료 callback은 C1 잠금·확정 stack·lane scope를 벗어난 새 turn에서만 시작한다(`framework/doc/framework/common/spec/server/01-execution/01-submit-and-completion.ko.md:508`). Callback 하나가 막혀도 다음 completion의 확정·관리와 무관 callback의 dispatch가 그 반환에 의존하면 안 된다. 이미 수락한 callback의 shutdown drain, cancellation과 reply의 단일 terminal 경쟁, public 완료 뒤 physical 결과의 codec/정리, ambient 복원, 사용자 scheduler 및 Yield gate 재획득을 그대로 둔다. 같은 자원에서 B개 callback을 한 drain으로 직렬 실행하는 것은 §08:306 위반이다.
- **규범·분류:** 기존 §08.4.4 범위라 spec 변경 불필요. 독점 배정과 독립 callback 진행을 기존 자원·수명으로 증명할 수 있을 때만 B. 새로운 completion queue·worker·flag를 더하는 대안은 제외한다.
- **언어 일관성:** .NET ThreadPool callback과 Java commonPool callback에도 역할 인계 계약은 적용 가능하나 runtime 소유 pool 정책을 대체하면 안 된다. Node는 microtask의 새 turn을 유지하며 OS hop 절감은 0이다. 비동기 callback의 재진입·순서·독립 진행 시험을 네 언어 공통 조건으로 한다.

### 3. 기존 ready-owner·worker·Core wake의 중복 통지만 축소 — B 후보, 실측 위치 확인 우선

새 batch queue를 만들지 않고 현재 owner/drain 상태와 worker queue의 기존 잠금 구간이 결정한 '실제로 깨울 필요가 있는가'를 재사용한다. `framework/languages/cpp/framework/src/runtime/mesh/service_mailbox.cpp:497`는 이미 ready batch를 꺼내고 `core/src/runtime/core/mailbox.cpp:343`도 `_scheduled` 하나로 Asio post를 합친다. 따라서 이 두 최적화를 새 성과로 계산하지 않는다. 남은 후보는 offload executor의 enqueue마다 `notify_one()` 하는 경계(`framework/languages/cpp/framework/src/runtime/dispatch/offload_executor.cpp:96`, `:105`, `:107`)와 실제 wait 전후의 redundant wake이며, 잠든 worker가 없는 경우·이미 충분히 깨운 경우가 **기존 상태로 증명되는 곳만** 다룬다. Core 측 수정은 Core가 소유하고 Framework에서 send를 모아 재제출하지 않는다.

- **계수 추정:** H 감소 0, record Q 감소 0. 기존 상태로 묶을 수 있는 독립 wake n회를 batch B개의 1회로 줄인 경우 W 절감은 (n−1)/B다. 현재 실제 n은 미확인이다. Core mailbox는 이미 조건부 게시이므로 'Core syscall 7배→1배'로 계산할 수 없다. Multiworker의 독립 callback 진행에 필요한 wake는 없애지 않는다.
- **문맥 전환·syscall:** 실제 futex wake 호출을 없앤 수만큼 최대 동수의 syscall 절감을 기대할 수 있지만 `notify_one()`가 user space에서 끝났다면 syscall 절감은 0이다. sendto/recvfrom 감소는 IO batch가 실제 커질 때만 가능하며 카운터로 확인해야 한다. Source read+write는 2.0102/msg, binding 0.0465/msg지만 차이 전부가 wake 비용이라는 근거는 없다(`/mnt/d/t/jobs/fx/cx/jhandoff2/cprof-report.md:205`).
- **제출 CPU 수치:** profile의 handoff/wake 1.473 µs/msg **전체를** 지운다는 비현실적인 낙관 가정에서도 23.405−1.473=21.932 µs/msg다. Ratio040으로 같은 stage 비율을 환산하면 26.138−1.645=24.493 µs/msg이고 B=220467.251을 고정한 submit CPU capacity의 F/B 상한은 약 0.185다. 측정 당시 간접 allocator·IO 효과가 없다는 가정이며 예측 처리량이 아니다. 현실적인 기본 추정은 23.405 부근 유지이고, 실행 후 µs의 보장 상한은 이 자료로 산출할 수 없다.
- **계약·위험:** 첫 enqueue의 wake 누락, park와 enqueue 경쟁, shutdown 깨우기, 둘 이상 독립 callback 실행을 특히 검사한다. Deadline 방문·NO_DATA drain·HWM admission을 늦추거나 sleep/timer로 batch를 기다리는 방식은 제외한다. 기존 상태보다 두 번째 `wake_pending` flag나 queue가 필요하면 이 안을 채택하지 않는다.
- **규범·언어:** §07.6.5·§08 I2/W5와 일치해 spec 변경 불필요. .NET ThreadPool·Java commonPool의 내부 wake는 해당 runtime 소유라 Framework가 같은 정책을 복제하지 않는다. Framework가 소유한 ready-owner 통지까지만 최적화하고, Node에서는 turn/microtask 게시 수를 따로 계수한다.

### 제외안: Core IO에서 완료 후 재개만 전달

기본 binding 알림은 **Core IO callback이 아니라 caller가 구동하는 poller wait의 drain**이다(`bindings/doc/spec/async-execution-model.ko.md:67`–`:75`). 현 public 경로를 유지하면서 Framework만 바꿔 Core IO에서 terminal을 처리하는 것은 불가능하다. Core/binding에 새 push completion 소유 경로를 요구하면 그 조항과 poller 수명·drain 소유를 변경해야 하므로 A/스펙 gap(D), 구현 BLOCKERS다. 또한 typed payload decoding을 그 thread의 infrastructure stack으로 옮기면 `framework/doc/framework/common/spec/server/01-execution/02-handler-turn-and-execution-gate.ko.md:483`과 충돌한다. 그런 변경 없이 내부 wire 분류를 알림 자원에서 하는 것은 이미 현재 경로이며 H 절감 0이다.

Reply를 다른 응답 dispatch thread로 보냈다가 source 완료를 합치는 안도 채택하지 않는다. Target reply는 이미 handler turn에서 직접 제출하며 §08 W4가 그렇게 강제한다. Source도 알림→registry take 사이에 host mailbox를 거치지 않는다. 없는 전달을 삭제 대상으로 세거나 독립 callback을 한 drain으로 합치는 설계는 제외한다.

## 추천 순서와 횟수 검증

**추천 조합은 3의 확인된 중복 wake 제거 → 1의 target 역할 인계 → 같은 배치 소유자를 재사용한 2의 source 역할 인계다.** 1·2는 최대 payload H=2/request를 줄이지만 역할 인계의 새 통지가 남는다. 안정적인 native batching 개선이 확인되지 않으면 시간 목표 달성으로 해석하지 않는다. 절감 수가 0인 호출→binding 직접 진행은 현재 동작을 고정하는 회귀 조건으로만 둔다.

1. **기준 계수 고정:** 시간 측정 없이 같은 payload와 N개 성공 메시지에 대해 E1/E4/E5·I2/I4/W3/W4의 thread ID, Q push, worker post, W 통지·실제 futex 호출, allocation/free, handler 시작/완료, binding submit 수를 계수한다. 진단 off 비용은 남기지 않는다. 기존 검증 자산은 `framework/languages/cpp/tests/Zlink.Framework.UnitTests/test_cpp_framework_request_native_counts.cpp:398`, `test_cpp_framework_receive_dispatch_cost.cpp`, `test_cpp_framework_completion_allocations.cpp:46`와 native/allocation counter다. 아직 이 설계 조사에서 새 계측을 구현하거나 실행하지 않았다.
2. **양방향 회귀:** 준비된 무경합 target에서는 caller/E4 thread 동일·추가 Framework 제출 Q=0, request terminal take=1, physical decode=1, binding 최초 submit=1을 고정한다. 경합·FIFO 선행 작업에서는 순서 위반이 없는지도 확인한다. 의도적인 추가 post·중복 wake를 넣은 시험 double이 해당 계수 assertion에서 실패해야 한다. Callback을 barrier로 잡아 둔 동안 unrelated completion·관리 진행을 확인하고, 단순 재실행 성공을 결함 해소 근거로 쓰지 않는다.
3. **방안 3:** 이미 active인 drain에 enqueue한 경우와 실제 parked worker를 깨워야 하는 경우를 나누어 W·futex 변화를 고정한다. Cold enqueue/park 경쟁/여러 idle worker/shutdown에서 누락·독립 진행을 확인한다. 기존 Core `_scheduled` 억제는 수정 전부터 존재하므로 0 개선일 가능성을 그대로 보고한다. 한 callback을 막은 부정 사례에서도 다음 callback이 그 해제를 기다리지 않는지 검사한다.
4. **방안 1·2:** 성공/실패 역할 인계 수, socket당 active wait+drain 자원 high-water=1, 전체 자원 high-water 불증가, target/source payload H 전후 1→0(성공분), 역할 W와 executor Q의 순증감을 보고한다. Busy pool이면 기존 경로가 진행되어야 한다. Request normal/error/timeout/cancel/shutdown 및 late physical reply, send immediate/BACKPRESSURED를 분리하고, held gate·Yield·ambient flow/corr·명시 scheduler도 확인한다. 같은 자원 재개는 이전 확정 stack/lane scope 종료 뒤인지 관찰한다. 기존 receive-role 회귀 시험 `framework/languages/cpp/tests/Zlink.Framework.UnitTests/test_cpp_framework_receive_role_completion.cpp:48` 등을 보강한다.
5. **구현 job의 완료 검증:** 수정 전 실패 또는 전후 횟수 차이를 먼저 고정한 뒤 새·수정 시험 100회는 스크립트로 실행한다. `nice -n 10`, 빌드·시험 병렬 최대 2로 C++ Debug `ctest -L '^(unit|contract)$'` 전체 1회와 `scripts/format/format.sh --check cpp`를 수행한다. 네 언어 공통 contract fixture로 새 turn·gate·permit·cancel/shutdown·독립 진행을 대조하고, 다른 언어 구현도 변경하면 해당 언어 전체 suite와 format을 수행한다. 이번 산출물은 저장소 밖 읽기 전용 조사이므로 runtime·docs 생성/검사 시험은 실행 대상이 아니다.

**0.6까지 남는 비용:** cprof profile 기준 binding submitter 3.746/0.6≈6.243 µs/msg를 단순 목표로 삼아도 현재 23.405에서 17.162 µs/msg를 줄여야 한다. 이 계산은 profile 두 실행의 단순 CPU 비교이며 throughput 예측이 아니다. 같은 critical thread의 allocation 7.559와 handoff/wake 1.473을 둘 다 전부 없애도 14.373 µs/msg가 남는다. 실제로는 필수 allocation·동기화가 있어 더 남는다.
