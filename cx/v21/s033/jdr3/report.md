Java Framework의 ZLinkJavaRawServicePort는 라우터 close가 CloseResult.BUSY를 반환하면 한 CloseAttempt 안에서 최대 8회 호출한다. 여덟 번째 호출도 BUSY이면 그 예외를 호출자에게 전달하고 closeAttempt를 초기화하며, 라우터를 receivePollers에서 제거하지 않는다. 다음 close 호출은 같은 라우터 닫기를 다시 시도한다. 구현은 framework/languages/java/zlink-framework-core/src/main/java/systems/zlink/framework/runtime/binding/ZLinkJavaRawServicePort.java:46, 654-690, 712-724에 있다.

ZLinkFrameworkRuntime.shutdown(Duration)는 기본 종료 기한 30초와 호출자 지정 deadline을 갖고 ZLinkFrameworkShutdown에 넘긴다. 기본값과 API는 framework/languages/java/zlink-framework-core/src/main/java/systems/zlink/framework/runtime/host/ZLinkFrameworkRuntime.java:94, 1706-1715에 있고, terminationDeadline을 설정해 close stage에 전달하는 지점은 같은 파일 1729-1736, 2288-2306, 2337-2345에 있다. 하지만 ZLinkJavaRawServicePort.close 및 CloseAttempt(같은 파일 654-710)와 ZLinkJavaRawMeshNode.close(ZLinkJavaRawMeshNode.java:5362-5432)는 이 값을 받지 않는다. 따라서 standalone close를 포함한 공통 port close 경로에 적용 가능한 기존 deadline은 없다. 별도 deadline, timer, flag 또는 state를 추가하지 않고 정수 상수 CLOSE_BUSY_MAX_ATTEMPTS=8을 두었다. 여덟 번의 즉시 close 호출은 짧은 in-flight 호출이 정리될 기회를 주면서 시도 횟수를 유한하게 제한한다. Thread.onSpinWait은 최대 일곱 번만 실행되어 park나 추가 타이머를 만들지 않는다.

failedSocketCloseRetainsOwnershipUntilLaterCleanupSucceeds의 이름과 첫 close에서 같은 ZlinkCloseException을 받는 assertion, 후속 close로 정리되는 assertion을 복원했다. BUSY가 여덟 호출 동안 계속되는 proxy를 사용하며, 첫 close가 실패한 뒤 다음 close가 성공하고 반복 close가 추가 호출을 만들지 않는지 확인한다. 시도 횟수 assertion은 원래 값 2에서 9로 바꿨다. 이전 assertion의 값 2를 유지하면 BUSY가 한 번 난 뒤 즉시 해소되는 경우만 시험하게 되어, 이번 테스트가 검증해야 할 한도 초과를 확인할 수 없다. meshExplicitCloseReachesRetainedSocketOwner도 원래 실패 예외 identity와 재진입 callback 1회 기대를 복원했다. 해당 테스트는 한 번의 logical close 동안 8회의 물리 close가 발생하므로 시도 횟수 1은 유지할 수 없어 8로 바꿨고, 후속 close는 9번째 시도에서 성공한다.

busySocketCloseSucceedsWhenBusyClearsWithinTheCurrentCloseAttempt 테스트를 추가했다. 첫 두 호출은 BUSY이고 세 번째 호출은 성공하여 같은 close attempt가 성공하는지 확인한다. 이전 변경에서 추가한 동시 reply 및 port/runtime close race 테스트와 테스트 import 정리는 유지했다. close race 테스트는 최초 close가 BUSY 한도를 넘으면 이를 결과로 확인한 뒤 reply worker가 끝난 후 같은 owner의 close를 다시 호출해 정리 성공을 확인하도록 수정했다.

재시도 판정자는 ZLinkJavaRawServicePort의 기존 CloseAttempt이며 새 queue, lock, cache, flag, timer 또는 객체 상태는 추가하지 않았다. 상수 하나를 추가한 이유는 port close에 전달되는 기존 deadline이 없어 BUSY 무한 반복을 유한한 시도 횟수로 제한하기 위해서다. close 결과와 소유권 규칙은 기존 그대로 유지된다. Core가 BUSY를 반환하는 결정은 Core close 계약의 소유이며, Java Framework는 반환된 BUSY만 같은 close attempt에서 최대 8회 재시도한다. Java 외 binding의 close 경로는 BUSY를 그대로 전달한다는 직전 조사 결과와 일치하며, PM 결정에 따라 Java Framework 경계에서만 제한 재시도를 적용한다. 이 변경은 승인된 계약 적응(A)이다.
