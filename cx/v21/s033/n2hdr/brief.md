Its conclusion: the big difference is header **copies** — outbound: Node copies the prepared JSON template into a new JS Buffer (`channel-envelope.ts` preparedChannelHeader, `Buffer.allocUnsafe` + `prepared.bytes.copy`) and the binding then copies that Buffer into a native Message (`bindings/node/native/src/addon_core.cc:211-222,904-924`); .NET writes prefix + dynamic fields straight into the final native Message (`ZLinkChannelReplyWriter.cs:41-60`, `ZLinkEnvelopeCodec.cs:1195-1236`). Inbound: once the target reads the header, the binding receive mode switches to managed buffers and copies the header native→JS (`bindings/node/src/zlink/runtime/messaging/message_materializer.ts:92-98`, `bindings/node/native/src/addon_message_values.h:248-265`, `addon_core.cc:509-525,2138-2150`); .NET reads the header from the native span with zero copies (`ZLinkEnvelopeCodec.cs:377-378`).
- The same "write the final frame into native storage" pattern is already implemented for the service wire in PR #4415 (branch origin/perf/4353-node-service-wire, commits afd3a0cea4 and ec6aa8ea5c): `ServiceWireOwnedFrame` in `framework/languages/node/packages/framework/src/runtime/foundation/service-wire-m6a-codec.ts` (allocate via public `Message.allocate`, write, hand the Message to the binding, close on synchronous submit failure) and `submitNativeParts` in `runtime/backend/node/node-raw-binding-port.ts`. Reuse that ownership type; do not create a second one.
