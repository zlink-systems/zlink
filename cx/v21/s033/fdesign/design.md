# C++ Framework request/send hot path — structural design proposal (#3867, #3868)

Independent proposal. Evidence: stage profile on main `ee11390257` (`/root/jobs/fx/cx/v21/s033/cprof/report.md` and its raw `source.samples.json` / `*.threads.csv` / `counts-summary.json`), the allocation work report (`/root/jobs/fx/cx/v21/s033/sfix/report.md`), and the source tree `/root/worktree/zlink-3867a` (#3884 + #3888 applied). Paths below: `C/` = `framework/languages/cpp/framework/src/runtime/`, `P/` = `framework/languages/cpp/framework/include/zlink/framework/contracts/`, `B/` = `bindings/cpp/src/Runtime/`, `S/` = `framework/doc/framework/common/spec/server/01-execution/`. All µs are **CPU µs per completed message** from the profile (request-backpressure 1024, 41.3k msg/s capture window) unless marked *inferred*. Where I infer rather than read, the sentence says so.

Headline: the C++ Framework is within the spec's hop limits (0 Framework transitions on submit, 1 on completion, 1 on target ingress, 0 on reply) — the gap is not extra hops, it is (a) the per-message work and wakes inside each hop, and (b) **two serial resources that are both already saturated**: the source submitter thread (0.967 cores) and the target's single-worker owner drain (0.940 cores). Fixing the submitter alone moves nothing; the design has to cut three serial threads at once.

Every serial thread on the Framework path must drop below the target spacing for the ratio to move.

## 2. Where the CPU goes and which serial resource limits throughput

### 2.1 Budget arithmetic

- Target: 0.6 × 220,467 = **132,280 msg/s → 7.56 µs/msg on every single-threaded stage**, and 8 CPUs/process → **60.5 CPU µs/msg per process**.
- Equivalent in profile scale (ratio040 submit CPU 26.14 vs profile 23.40, scale 1.117): the ratio formula ratio ≈ 3.746 / F_max, where F_max is the slowest Framework serial thread's µs/msg; 0.6 needs **F_max ≤ 6.24 µs** on every serial thread.
- Per-process totals today: source 103.1 / target 74.5 vs budget 60.5. Of that, Core IO threads are 34.7 (source) and 34.4 (target) — see 2.3.

The ordering conclusion: **Part A alone buys nothing beyond #3888** because the target's owner drain (0.940 cores) and the source receive role (0.758) sit right behind the submitter. The three parts must land together (or C first) for any of them to show.

### 2.3 Core IO threads — Core-owned, rate-adaptive (*inferred*)

Source IO/0 spends 83% in `tcp_sendmsg` with 0.883 sendto/msg; the binding at 270k has 0.117 sendto/msg and 2.5 µs/msg on the same thread. Core's engine writes whatever accumulated in the pipe while the previous `sendto` ran, so batch size grows with offered rate: at 41k msg/s one message per write; the binding's IO/1 at 270k is at 0.898 cores with ≈5.5 messages per write. A cost model c_write ≈ 12 µs per loopback `sendto` (it includes the receiver's softirq path) + ≈1.5 µs per message predicts the IO writer running at ≈0.8–1.0 cores anywhere between 40k and 270k, with per-message cost falling as rate rises. So the IO threads are not a Framework lever and will not block 132k (the binding pushes 270k through them), but they will be near one core and should be watched in the confirming measurement (§4.4). Nothing in this design changes Core.

### 2.4 Per-process CPU at the estimated ceiling

At 0.42 (92.6k msg/s) the budget is 86 µs/msg per process; estimated source ≈ 9 + 6 + 3 (workers) + ≈15 (IO) ≈ 33, target ≈ 4.5 + 5.5 + ≈16 ≈ 26. The CPU budget is not binding; the serial threads are.

## 3. Recommended design: "one entry, one turn, one wake" on three serial threads

One design with three parts (A source submit, B source completion, C target ingress + drain). It adds no new state, lane, queue type or flag beyond replacing the dispatcher queue; it removes result-object layers, duplicate protectors and per-item wakes. Decision-location count (places that decide where/when a completion runs, which port to use, when to wake): before 9 → after 6 (see 3.6).

### 3.1 Part A — Submit path: one pending entry carries the final typed sink (S1: 23.4 → ≈9)

What changes (all on the caller thread, inside the existing single `_lane.run_sync` turn — E1–E4 unchanged in shape):

1. **One sink object, no layered results.** `register_operation` stores a type-erased `completion_sink_t` { pointer to the public `request_task_t<T>` shared state (which already carries the admitted phase), the decode chain as plain function pointers (service-wire reply parts → envelope header → body view → `serializer_t<T>::deserialize`) } instead of `std::function<void(terminal, result<message_t>)>`. Removed per request: `request_admission_completion` wrapper (`raw_mesh_node_owner.cpp:224`), `finish` lambdas (`:1580`, `raw_route_port.cpp:359`), `observe_request_completion` coroutine frame (`raw_binding_adapter.hpp:147`), `submit_node_request_reply` lambda + `compose_node_request_submission` (`mesh_node_runtime.cpp:4399`), `request_receiver_t<node_reply_t>` + `make_shared<projection_t>` + `request_decoder_t` string copies (`channel_runtime.cpp:1847–1903`), `await_request_admission`/`project_task_terminal<bool>` (`raw_mesh_node_owner.cpp:437`). This is what `S/01 §9` already demands: "내부 계층 사이의 변환만을 위한 별도 비동기 결과와 관찰 연결을 두지 않는다" and `§10.1` "Typed caller 수신자는 이 entry의 dispatcher 자리에 등록한다".
2. **E1 writes the wire once.** `serializer_t<T>::serialize` writes into the final native frame (`ByteSizeLong` → one `zlink::message_t` of envelope header + body) instead of protobuf → `encoded_payload_t` vector → `message_parts_t` → W writer copy. `S/08 §3` E1: "중간 byte 배열을 거쳐 ... 복사하는 것은 위반" — today the body is written twice. `format_utc_deadline` (`client_call_codec.cpp:31`, gmtime_r + strftime, 0.37 µs) becomes a fixed-width integer writer producing the same `%Y-%m-%dT%H:%M:%SZ` bytes; `next_correlation_id` stays within SSO. Channel id / packet name are borrowed from `route_client_state_t`/call for the duration of the synchronous submit rather than copied three times.
3. **One protector per state.** The `_lifecycle_mutex` read of `_port` inside the lane turn (`raw_mesh_node_owner.cpp:1554`, also `:3367`, `:3594`, `:4257`, `reply`) is removed: the lane already serializes `_port` (`S/06 §4` "C2가 이긴다 — 컴포넌트를 부분적으로만 lane으로 옮기고 나머지를 별도 lock으로 남기면 … 위반"). Port close moves onto the lane (it is already a lifecycle turn).
4. **Registry node = chain item.** `pending_t` holds the completion item by value; `take` uses `std::multimap::extract` so the node leaves the table without freeing and becomes the chain node (`operation_completion_chain_t` already exists at `operation_registry.cpp:230`). One allocation at register, zero at take/post.
5. `route_send_call_t::_submission` (`channel.hpp:683`, `make_shared<submit_once_t>`) and `route_request_call_t`'s equivalent become inline flags.

Allocation target on S1: ≈10/msg (frame, header frame, registry node, binding entry + owner map node, public task state, bench slot/registration ≈2, bench payload ≈2) vs 24.3 now and 12.4 for the binding driver.

Estimate (profile scale): E1 1.2 (protobuf 0.4 + envelope 0.5 + service-wire header 0.3) · E2 0.3 · lane 0.3 · E3 0.6 · E4 1.6 (binding entry + Core, equal to the binding's 1.3 + `_socket_mutex`) · result object + admitted 0.4 · flow/ambient 0.2 · alloc 0.5 · driver + payload build + completion observation 1.7 → **≈7.8**; with 30% slack **≈9–10.5**.

### 3.2 Part B — Source completion: take at the notification, post the rotation's chain once (S4: 18.35 → ≈6; S5: 26 → ≈3)

1. **Direct sink call.** The binding's `async_result_t` completion lands in one `raw_route_port_t` member (`on_reply(entry*, result)`), which decodes the 29-byte reply header (correlation → `call_id_t`), performs the **C1 atomic take** and appends the extracted node to a **rotation-local chain** held by the thread running `poll`. No coroutine, no std::function chain, no post yet. Keeps `S/08 §3` E5 ("완료 알림을 받은 자리에서 … 원자적 꺼내기", "host mailbox·dispatch thread를 추가로 거치지 않는다") and `S/01 §10.1` C1.
2. **Chain post after the wait returns.** When `raw_route_port_t::poll` returns from `_poller->wait` (i.e., after the binding's `drain_impl` loop finished and all binding locks are released), the chain is handed to the completion dispatcher in **one call**: `post_chain(head, tail, n)` = one queue lock, n items linked intrusively, **one `notify_one`**; a woken worker that dequeues and still sees items wakes the next idle worker (cascade). Every callback stays an independent dispatcher item, so `S/08 §4.4` "서로 무관한 완료 callback을 한 callback의 반환에 의존하는 drain으로 합치지 않는다" and `S/01 §11` (blocked callback holds one worker; one exception does not block the next; posting cannot fail — the nodes are pre-allocated at registration, strictly better than today's allocating `asio::post`) hold.
3. **Dispatcher queue.** `completion_dispatcher_t` (`provider_task_context.cpp:53`) replaces `boost::asio::io_context` with an intrusive MPMC queue + condvar; worker count rule unchanged (`max(2, CPUs)`); `completion_turn_scope_t`, `close()` (drain accepted items, then join) and `dispatch_completion`'s inline-reuse rule unchanged. Java already posts chains (`ZLinkServiceCompletionDispatcher.postChain(first,last)`), .NET relies on `ThreadPool.UnsafeQueueUserWorkItem` wake throttling (`ZLinkCompletionDispatcher.cs:13`); this gives C++ the same amortization.
4. **One poll per rotation.** `begin_receive_turn(waited)` reuses the readiness the rotation already waited for; the re-check after a non-empty rotation becomes a `poll(0)` only when the previous rotation drained to NO_DATA with pending supply (removes the second `zlink_poller_wait` that shows as 51.7% inclusive on S4). `wait_for_activity`'s mailbox `pending_messages` ×2 + `has_application_dispatch` become one lock.
5. **Typed decode on the worker, once.** The dispatcher turn runs sink.decode (service-wire views → envelope header → protobuf parse) and completes the public state; no `decode_operation_record`/`decode_application_part_views`/`request_decoder_t` re-wrapping.

Estimate S4 per message: Core per completion (`zlink_completion_recv` + `lock_public_api_sync` + `process_completion_records`) ≈2.0 · per-wake part (epoll_wait, signaler read, `get_events`, one `zlink_completion_recv` NO_DATA) ≈4 µs / N completions per wake · binding entry capture/settle 0.5 · header decode + take + chain append 0.6 · chain post share 0.3 → **≈5–6 at N≈2–3**. S5 per message: dequeue (amortized wake) 0.5 · decode + protobuf parse 0.8 · complete typed state + deliver 0.5 · bench notify 0.4 → **≈2.5–3** (spread over workers).

### 3.3 Part C — Target: one rotation builds one claim batch; the drain runs records as plain calls (T2: 17 → ≈4.5; T3: 22.8 → ≈5.5)

1. **Rotation (I0–I4) without per-record lane entries.** `public_host_runtime.cpp:7398 _local_dispatch_completion_lane.run_sync` per pumped record becomes a once-per-rotation check guarded by an atomic count; `_lifecycle_mutex` reads go (3.1.3); `service_mailbox_record_t` borrows the admitted peer's routing id and owner key (the topology entry already owns them for the connection lifetime) instead of allocating a `std::string` + vector per record; `dispatch_ready` stays a coroutine only on the management branches that actually suspend (`retry_terminal_relays`, `dispatch_user_spot_operations`) — the record loop is a plain function. I0–I4 order, permit handling (`supply.take_budget`, `begin/take_application_receive_turn`) and the once-per-rotation ready-owner notify are unchanged.
2. **Drain (W1–W5) without per-record objects.** In `dispatch_application` (`mesh_node_host_service.cpp:3664`): the terminal owner lives by value in the claim batch entry (no `make_shared` per record); `mesh_record_dispatcher_t` is built once per drain; the stateful branch (`dispatch_mesh_record`) is skipped by record kind before being called; `dispatcher.dispatch` returns a ready value when the handler completed synchronously (today it returns a per-record `task_t` — `S/08 §4.3` "record마다 별도 dispatch task … 를 만들지 않고"), allocating a continuation only when the handler suspends. The envelope header is decoded once and passed down (verify there is exactly one `decode_header` per record; the profile shows both `decode_mesh_record_header` 7.9% and `envelope_codec_t::decode_header` 7.3% on the worker). Service scope per dispatch stays (`S/08 §4.3` DI rule).
3. **Reply (W4) without a lane round trip.** `raw_mesh_node_owner_t::reply` currently does `_lane.run_sync` + `_lifecycle_mutex` to fetch `_port` per reply; the claim batch carries the port reference for its lifetime (the receive turn that enqueued the record holds it), so the reply is header frame + payload frame + `raw_route_port_t::reply` → `zlink_reply`. The payload frame uses the same single-write serializer as 3.1.2.
4. Owner exclusivity (`begin_application_drain`) is **kept**: one worker drains one owner at a time, as I read `S/08 §4.3` W1/W5 and `S/04 §3` "준비된 owner 집합" (one owner, one entry, the worker takes the owner's next record within the time budget). This is why T3 remains a single-threaded stage in the single-source benchmark and why its per-record cost, not worker count, sets its ceiling.

Estimate T3 per record: claim take 0.3 · header decode 0.3 · scope + filters + handler invoke 0.7 · protobuf parse 0.4 · echo + metrics 0.1 · serialize 0.4 · two reply frames 0.4 · `zlink_reply` 1.0 (binding: 0.90) · `_socket_mutex` 0.1 · permit/terminal release 0.3 · batch bookkeeping 0.3 · residual alloc 0.3 → **≈4.6; with slack ≈5.5 (5–7)**. T2 per record: Core recv 1.3 (binding: 1.28) · per-wake share 0.3 · header decode 0.2 · peer lookup 0.2 · record build 0.3 · enqueue 0.5 · rotation share 0.5 → **≈3.3; with slack ≈4.5**.

### 3.4 Spec clauses — kept, and the ones that would have to change

Kept, and how:

| Clause | How the design keeps it |
|---|---|
| `S/08 §3` E1–E4 in one owner turn, ≤2 transitions, registration before submit, same-turn `admitted` for `result == OK` | unchanged: caller still executes the lane turn via `run_sync`; the sink is registered before `port->request`; admitted completes inline on OK |
| `S/08 §3` E1 single wire write | 3.1.2 removes the intermediate byte array the current path still has |
| `S/08 §3` E5 / `S/01 §10.1` C1 take at the notification site, no owner round trip, no host mailbox before the dispatcher | 3.2.1 takes on the receive-role thread inside the binding completion callback; 3.2.2 posts straight to the dispatcher |
| `S/01 §11` callback outside the lock, new execution turn, dispatcher never fails, blocked callback leaves another worker, exceptions independent | items stay independent dispatcher work; pre-allocated nodes; worker count unchanged; `completion_turn_scope_t` unchanged |
| `S/08 §4.4` receive-role holder runs no application turn without hand-off; callbacks not merged into a dependent drain | the receive-role thread only takes and posts; hand-off is **not** introduced (see 3.5 ALT-2) |
| `S/08 §4.1` I0–I4, ≤1 transition after I4, once-per-rotation management; `S/04 §3` permit order | unchanged |
| `S/08 §4.3` W1–W5: scope per dispatch, reply in the same turn, no per-record dispatch task, one owner per worker | 3.3.2 removes the per-record task the current code creates; exclusivity kept |
| `S/06 §4` one mechanism per component (C2 wins); `§5` lane FIFO/non-reentrant/반환 전 완료 보장 | 3.1.3 removes the second protector; registration still completes before `.async()` returns |
| `S/01 §9` one final receiver, codec conversion in one place | 3.1.1 is the implementation of this clause |
| Cross-language observable contract (wire bytes, admitted/reply phases, terminal classification, completion on a process-shared dispatcher in a new turn) | unchanged; .NET ThreadPool / Java FJP / Node event loop already have the amortized-wake shape |

Would have to change (not part of this design; stated so it is not bent):

- **To lift T3 above one core for a single gate-less owner** (needed for 0.6 on either cell, see §3.7): `S/08 §4.3` W1/W5 and `S/04 §3` would need an explicit clause allowing N workers to pop records of one gate-less Node/ChannelName owner from a shared head (FIFO *start* order preserved, handlers run concurrently). Today's text puts one owner in the ready set once and has one worker take "the owner's next record"; I do not read it as allowing concurrent drains, so this is a D-class item, four languages at once.
- **`S/08 §7(c)`** states 0.90 as the pass line while the project target in this task is 0.6 and the bench spec's request-backpressure line is 0.80; this design does not reach any of them (see 3.7) — the clause is not bent, but the gap should be recorded against it.

### 3.5 Alternatives considered (brief)

- **ALT-1 Pipeline E2–E4 onto a posted lane turn** (caller does E1 + enqueue; lane drainer registers + submits). `S/08 §3` allows the transition and `§9` even budgets the wait, but (a) `S/06 §5` 반환 전 완료 보장 requires registration before the caller observes the return, and (b) the backpressure pattern waits for request N's `admitted` before submitting N+1 (`bench_cpp_client.cpp:915`), so the admission would cross threads per message — a wake per message instead of none. Rejected.
- **ALT-2 §4.4 receive-role hand-off** (drained thread re-queues the role and runs completion items itself). Allowed, and it removes the one remaining wake per rotation on S4, but the independence clause means it may only act as an ordinary dispatcher worker, not run the chain sequentially. Worth measuring **after** Part B if S4's `futex_wake` share is still visible; adds one decision location, so not in the baseline.
- **ALT-3 Fewer completion workers / inline typed completion on the receive-role thread.** Violates `S/01 §11` (blocked callback) and `S/08 §4.4`. Rejected.
- **ALT-4 Shard the registry / per-caller registries** to cut `_mutex` contention between S1 register and S4 take. The contention is real (1.67 futex/msg on S1) but is a sub-µs item once the chain post and single take per completion land; revisit with data.

### 3.6 Rule count

| Decision | Before | After |
|---|---|---|
| Who converts a physical reply to the typed result | 4 places (raw port `finish`, `observe_request`, `submit_node_request_reply` lambda, `request_decoder_t`) | 1 (sink.decode in the dispatcher turn) |
| Where `_port` is read on the hot path | lane **and** `_lifecycle_mutex` (5 sites) | lane only |
| When a dispatcher worker is woken | per posted item (asio) | per posted chain + cascade (one rule) |
| How many polls per rotation | 2 (wait + `begin_receive_turn`) | 1 |
| Reply port acquisition | lane turn + mutex per reply | batch-held reference |
| Owner drain exclusivity, permit order, E1–E4 order, C1 take, dispatcher independence | unchanged | unchanged |

New state/queue/lock added: the dispatcher's intrusive queue + condvar (replaces asio `io_context` + its op allocations). Removed: `_lifecycle_mutex` hot-path reads, `observe_request_completion` coroutine type, `projection_t`, `request_decoder_t`, `request_admission_completion`, `submit_once_t` shared state.

### 3.7 Risks

- **Ordering.** Completion callbacks of different requests were never ordered (8-worker pool); the chain post keeps per-chain FIFO within the queue and does not add ordering. Caller-side FIFO of submits through the lane is unchanged.
- **Reentrancy.** The sink call runs inside the binding's `drain_impl` loop (as today's coroutine resume does) but **outside** the owner mutex (released at `completion_owner.cpp:750`) and the entry mutex (released before `request_result->complete`); it only takes the registry lock for the extract. The chain post happens after `_poller->wait` returns, outside every binding lock. The typed decode and public completion run on the dispatcher turn only. A callback that re-enters the runtime (new request from a completion) hits the lane via `run_sync` from a dispatcher worker — same as today.
- **Deadline / admission.** The deadline stays the entry's value; expiry still goes through `operation_registry_state_t::expire` on the lane and competes via the same C1 take; a timed-out entry extracted by the management visit must not also be in a rotation chain — guaranteed by the single extract. The admitted phase: inline on `ZLINK_SUBMIT_OK`; on `BACKPRESSURED` the WRITABLE completion arrives through the same binding callback and completes the admitted phase from the receive-role thread **without** touching the pending entry (it is not a terminal) — keep that branch explicit and tested.
- **Shutdown.** `completion_dispatcher_t::close()` must still run every accepted item (`S/01 §11`); the registry's `fail_target`/close path produces a chain and posts it the same way; a rotation chain held on the receive-role thread when the port closes must be posted, not dropped — put the post in the `poll` epilogue that runs on every exit path.
- **Completion turn.** `completion_turn_scope_t` and `can_reuse_completion_turn` are unchanged; the hand-off variant (ALT-2) is explicitly out of scope so no receive-role thread ever runs an application callback.
- **Owner exclusivity stays** — T3's ceiling is the per-record cost; if measurement shows T3 above S1 after Part C, the only lever left is the spec change in 3.4.
- **Core IO near one core** (§2.3) — not a Framework defect; report if the confirming run shows IO ≥ 0.95 cores before S1/T3 saturate.
- **Bench-side cost** (driver 0.9 + payload build + validation ≈ 1.7 µs on S1) is part of the measured ratio and outside the Framework; the binding driver pays ≈1.3 for the same.

### 3.8 Estimated ceilings (arithmetic shown)

**request-backpressure 1024.** ratio ≈ 3.746 / max(S1, S4, T2, T3). After A+B+C: max = S1 ≈ 9 (7.8–10.5) → **≈0.42 (0.36–0.48)**. For 0.6, every serial thread must be ≤ 6.24 µs: S1 would need the Framework's own E1–E4 + result object to cost ≤ 2.5 µs on top of binding submit + bench work (≈3.7), which I do not consider reachable with the wire envelope's string fields and the single-entry registration; T3 at ≈5.5 would fit but with no margin and only after Part C. **Honest answer: ≈0.42, not 0.6.**

**send-saturation 1024.** ratio ≈ 1.84 / max(S1_send, T2, T3_send) (*inferred*: the binding's 1.84 µs/msg is its one submitter thread). After A (send part) + C: S1_send ≈ 3.3 (E1 1.0 · E2 0.3 · lane 0.3 · binding send 0.8 · mutex 0.1 · ready task 0.1 · flow 0.1 · driver 0.6; 2.9–3.8), T2 ≈ 3.3–4.5, T3_send ≈ 3.4–4.5 (T3 minus W4 and the parse-serialize pair: claim 0.3 · decode 0.3 · scope/handler 0.7 · protobuf parse 0.4 · permit/terminal 0.4 · bookkeeping 0.6 · alloc 0.6) → max ≈ 3.4–4.5 → **≈0.48 (0.41–0.55)**. 0.6 needs ≤ 3.07 µs on all three; T3_send and T2 both sit at or above it, so 0.6 again needs the owner multi-drain spec change or a target-side cost below what Core recv (≈1.3) plus mandatory classification leaves.

### 4.4 Cheapest measurement that confirms or refutes the ceiling before implementing

1. **Two minutes, no build — per-thread CPU of the send-saturation cell** with the existing `cprof/collect.py` schedstat snapshot (no `perf record`), both implementations, under `measure.lock`. It answers which thread limits the send cell today (S1_send vs T2 vs T3) and gives the binding's limiting thread µs/msg, which fixes the denominator in the ratio formula of §3.8. If T3 is already ≥ 0.9 cores on send, the send ceiling is set by Part C, not Part A.
2. **One unit-tier build — a submit floor probe**: a `framework-unit` executable that calls `route_client_t::request_to_node<BenchPayload>(…).async<T>()` against a stub `raw_route_port_t` whose `request` returns `ZLINK_SUBMIT_OK` and completes nothing (no Core), looping 1e6 times and reporting ns/call and malloc/call. Today it should read ≈ 23.4 − 0.9 (driver) − ≈2.5 (binding/Core) ≈ 20 µs; the design predicts ≤ 5. If the floor after Part A is > 6.5 µs the 0.42 ceiling is refuted downward; if the stub probe alone (before any change) shows that encode + envelope + registration is > 4 µs, the ≈9 estimate is too optimistic and the honest ceiling is ≤ 0.35.
3. **Reuse of the existing profile** for T3: 22.76 µs/record with the two workers never concurrent is already in `target.threads.csv`; after Step 1 the same snapshot (no perf) confirms ≤ 7.5.

Measurements run one at a time under `measure.lock`, Framework and binding cells back to back, 30 s warm-up, as the sfix A/B did; interim checks only on the changed language per the current rule.
