# Thin C++ request path — 0.33.0 / #1639

Read-only design study, 2026-11-06. Source: `/root/worktree/zlink-3867s`, HEAD `e86f55886a08f4870913bf781b4f515c3239283f` (`perf/3867-cpp-submit-path`). This study did not edit or build in the worktree, perform GitHub operations, or invoke additional agents/models. This report is design evidence; it does not authorize implementation.

## Answer and interpretation

**The current implementation does not reach 0.6. The current specification does not establish that 0.6 is impossible.** It requires logical ownership, admission semantics, canonical wire bytes and execution boundaries; it does not require today's number of heap objects, generic result projections, callable owners, string copies or per-item Asio posts. Those representations can be reduced behind the existing API. Conversely, deleting the operation registry, owner lane, admission stage or infrastructure/application separation would change explicit contracts.

A numeric minimum CPU time cannot be derived from a specification that contains no per-operation CPU lower bound. Below, measured residuals are distinguished from conditional savings estimates. A residual obtained by deleting profiled scopes while freezing everything else is not a minimum imposed by the spec, and no unimplemented design is reported as a measured 6 µs path.

The existing binding also expressly forbids a request callback terminal. Thus the earlier callback-based proposal is not an optimization available under all current contracts. A thin path can retain one public binding await bridge and remove other representation layers; a new callback terminal requires a binding contract revision.

## 2. “No clause” representations and removable layers

**The removal target is repeated representation and ownership, not the public API/registry/lane/binding responsibilities.** The following µs ranges are engineering allowances for a future implementation, constrained by the measured enclosing scopes. They are not causal savings measurements, confidence intervals, or a promise that all work in a scope disappears. Actual savings can be zero or negative. The scopes and changes overlap; **do not add the rows** or add them to #3884/#3888/e86 savings.

Decision counts below count locations owning the named decision. They do not count objects, allocations, function calls or phases as extra authorities. A pure forwarding representation owns zero decisions (0→0). Admission, public reply and physical completion are different facts; compact storage must preserve all of them. ### Minimum submitter CPU allowed by the current spec

**There is no specified numeric minimum. A measured minimum for a redesigned path is unavailable in this design-only study.** The meaningful hardware budget is `1e6 / (0.6 × binding throughput)` on every serial resource, not an architectural constant of 6 µs. The paired measurement table gives that budget for this machine and revision.

The required caller work is final-receiver preparation + selected payload/envelope encode + one operation-owner turn + logical registration/index insertion + one binding async request start + return of isolated result views. A public binding await consumer must also exist; it can be the physical producer of that final receiver instead of a chain of result adapters. Reply decode, independent callback delivery and target handler work need not run on the submitter, although caller-side handle destruction and benchmark validation remain in its measured CPU.

The following numerical tests separate what can be inferred from what cannot:

| Numerical test, CPU µs/message | Request | Send |
|---|---:|---:|
| Measured final profile caller | 20.627 | 5.101 |
| Measured new unprofiled caller | 18.658 | 4.844 |
| 0.6 serial budget using paired profile binding capture | 6.733 | 2.690 |
| 0.6 serial budget using new unprofiled binding phase | 6.710 | 2.828 |
| Delete all caller allocation/free CPU, every other cost frozen | 15.557 | 4.240 |
| Delete all allocation + handoff/synchronization + task + bookkeeping CPU | 8.444 | 2.825 |
| Above residual normalized to unprofiled caller by unchanged-stage-fraction assumption only | 7.638 | 2.683 |

**The last deletion test is deliberately stronger than a legal representation optimization**: it deletes required allocation/registration/coordination as well. It still leaves **8.444 µs/request** and **2.825 µs/send** on the sampled caller. Their frozen-caller capacity ratios are only **0.478 / 0.571** against the matching binding capture. Other serialized resources can lower these bounds further. This rejects a 0.6 claim from deleting only those measured categories; it does not make the residual a semantic or hardware lower bound.

The required codec and native calls can change their implementation and amortization. For example, the same binding request API encloses 1.364 µs on the raw caller versus 5.162 under Framework, with different cadence/concurrency and wire records. This is evidence that current function cost is not fixed by the API, not proof that the raw cost transfers unchanged into Framework. Removing intermediate native message wrappers also changes work charged to “binding/Core.” The normalized row assumes the sampled mix is unchanged without perf; that assumption was not measured and is included only as sensitivity arithmetic. No exact minimum for a fully thin conforming submitter has been measured.

Calling 9–10 µs a “spec floor” because an earlier design estimated that value is not justified. Likewise, the raw caller's ~3.5 µs is neither a lower bound nor an additive fixed cost for the Framework caller: the raw caller also drains completions/decodes replies, which Framework performs on other resources. Frozen-scope deletion models are useful for rejecting a limited optimization claim; they are not proofs that every conforming implementation must retain those costs.

## 4. Can the two 1K cells reach 0.6 under the current spec?

**Contract admissibility: yes, a substantially thinner implementation is allowed. Measured/forecast attainment: not established for either cell, and not supported by a submit-wrapper or handoff-only change.** There is no defensible proof here that a conforming implementation cannot reach 0.6, so there is no justified list of clauses that *must* be relaxed to hit it. There is also no measured thin implementation that justifies promising 0.6. Those are different conclusions.

The new unprofiled figures give a caller requirement of **6.710 µs/request** and **2.828 µs/send** at 0.6. The caller currently uses **18.658 / 4.844 µs**. This is approximately **64.0% / 41.6%** caller reduction, before giving other serial resources any headroom. The earlier three-run reference requires 6.752 / 2.701 µs; the conclusion is not dependent on choosing the easier of the two cohorts.

The new unprofiled target application drain consumes **18.663 µs/request / 5.805 µs/send**, or about **0.935 / 0.966 cores** in its captured windows. The source caller uses about **0.935 / 0.806 cores**. Thus request is constrained at both ends; in the send capture the owner-wide target drain is nearer saturation than the caller. The final profiles also show source receive 14.823 µs/request, target receive 14.586 / 4.320 µs, and Core I/O demands above the same serial budget. **A source-only thin API cannot establish 0.6 for either end-to-end cell.**

With the current measured native/codec work frozen, the answer is **no**: even the intentionally excessive deletion model in §3 does not give 0.6. With cheaper representations, cheaper required actions and changed *natural* batching, current contracts leave the answer **open**. Reaching 0.6 would require those effects to be measured, not assumed. No clause specifies that each native API call must consume today’s CPU, and no current data establishes the best achievable version of those calls.

The selected design direction is to retain the existing public API and its domain ownership while eliminating representation-only work: a final typed receiver prepared before submission, one compact request lifetime representation with isolated observable phases, existing operation-owner registration and one native submit, one binding await producer, one C1 take, then codec-owned conversions into that receiver in a dispatcher turn. The owner queue, permit system and scoped handler pipeline remain on the target. Replace the existing representation in its owning module; do not add a “fast request” API, alternate protocol, second registry, private binding access or benchmark-specific runtime.

This is materially different from applying another local lock/string/coroutine cut. It removes repeated intermediate ownership and adaptation, but it still pays all the actions in §3. Keeping the public API does not require keeping every current public-template implementation detail. Keeping the registry contract does not require keeping its current node/item allocation shape. Keeping the binding layer does require consuming its deployed public result contract.

### What the earlier studies establish, and what they do not

- `cprof` and `cadvice` establish the absence of a routine caller→submit-worker hop and identify expensive allocation/bookkeeping/native work. Their pre-cut stage budgets cannot be subtracted again from e86f55886a.
- `coreio` disproves “extra physical parts / different native Core” as the primary explanation. Its measurements show smaller TCP batches, not proof that a faster submitter alone restores binding-level I/O CPU. K3's automatic convergence and fdesign's adaptive-I/O forecast remain unmeasured hypotheses.
- `fdesign`/`kdesign` suggest representation collapse, native writer and batched independent delivery. Their 0.4–0.5 ceilings are design estimates, not spec-imposed lower bounds. The proposed callback terminal contradicts the current binding policy; the extracted-map-node lifetime shortcut was already rejected in `csubmit`. Current ready fast paths/writer cannot be counted again.
- `zdesign`/`cadvice` correctly preserve receive-role ownership and independent callbacks. Resource placement can reduce off-caller work; it cannot by itself delete the caller's measured service demand.
- `cdrain` shows that satisfying gate-less multiworker concurrency by more fanout can increase endpoint CPU and lower throughput: send application CPU 5.559→24.846 µs/message; request 18.920→49.860; its PM p99 about 0.502→7.585 ms. Those are a different branch/cohort, not new measurements of this HEAD or a fixed target cost. They prevent assuming that more worker concurrency or fewer exclusion rules necessarily saves CPU.

The decisive future measurement is the full thin representation using the **same** public interface, codec, wire, admission, payload and logical concurrency, with per-resource CPU and native batching measured again. It must bring every serial resource below the paired budget and each endpoint below its eight-CPU budget. A lower caller number alone, an isolated queue benchmark, fewer allocations, or a contract-relaxed raw benchmark does not establish the two requested 0.6 ratios.
