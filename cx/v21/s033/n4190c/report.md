## 2. 기존 다중 client 지원과 다른 언어의 용량

- Node runner에는 다중 client process/worker thread 옵션이 없다. `--submit-concurrency 8`은 규격상 stream 수이며 Node driver의 Promise loop를 늘릴 뿐, event loop 수를 늘리지 않는다: [run_local.sh](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/node/run_local.sh:76), [README §10.3](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/README.ko.md:605).
- aggregator는 셀 간 client metric을 합산하지 않는다. 각 결과 metric의 run 중앙값을 내고, 선언 ceiling은 run 값의 최댓값을 쓰며, G6는 metric 값과 ceiling의 0.95배를 비교한다: [analysis.py](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/tools/benchagg/analysis.py:158), [analysis.py](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/tools/benchagg/analysis.py:186), [analysis.py](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/tools/benchagg/analysis.py:205), [model.py](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/tools/benchagg/model.py:229).
- 규격의 stream 용량은 직렬 1, 역압·send 8이다: [README §10.3](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/README.ko.md:605). C++는 `submit_thread_cores`를 측정하고 ceiling을 stream 수로 선언한다: [bench_cpp_client.cpp](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/cpp/client/bench_cpp_client.cpp:928), [같은 파일](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/cpp/client/bench_cpp_client.cpp:943). Java는 `jvm_thread_cores`와 `submitParallelism`을 선언한다: [BenchDrivers.java](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/java/client/src/main/java/systems/zlink/bench/withgrpc/client/BenchDrivers.java:155), [같은 파일](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/java/client/src/main/java/systems/zlink/bench/withgrpc/client/BenchDrivers.java:157). .NET은 pattern별 stream을 직렬 1, 역압·send 8로 정의한다: [Program.cs](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/dotnet/Client/Program.cs:956), [같은 파일](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/dotnet/Client/Program.cs:959), [같은 파일](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/dotnet/Client/Program.cs:965), [같은 파일](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/dotnet/Client/Program.cs:970). 따라서 `submit_thread_cores=8`은 C++ 지표명일 뿐이며 .NET·Java는 각자의 지표명을 쓴다: [README §5.1](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/README.ko.md:280).
- 규격은 Node가 모든 stream을 event loop 하나에서 돌린다고 명시한다: [README §10.3](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/README.ko.md:613), [같은 절](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/README.ko.md:617). 그래서 현재의 1 상한은 코드·규격과 일치하며, 동시성 패턴의 다른 언어 대비 실행 용량이 작은 것이 근본 원인이다: [README §5.1](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/README.ko.md:271).

## 3. 변경 제안 (구현하지 않음)

- 동시성 패턴에서 다른 언어와 같은 용량을 주는 최소 설계는 stream마다 Node `worker_threads` worker/event loop를 두는 것이다. worker 수는 규격대로 직렬 1, 역압·send 8로 하고, 이 구성을 `zlink-node`와 `zlink-framework-node`에 공통 적용한다. 직렬은 규격상 stream이 하나이므로 8개 client로 늘리면 직렬 측정 의미가 달라진다: [README §10.3](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/README.ko.md:605), [같은 절](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/README.ko.md:617).
- 예상 변경 경로는 규격 소유 문서 `framework/bench/grpc/README.ko.md` §5.1·§10.3(여러 Node event loop의 capacity 선언을 허용), 공통 runner `framework/bench/grpc/node/run_local.sh`(worker 수 전달), `client/main.js`(worker orchestration), 신규 worker 진입 파일(각 worker의 transport·stream 실행), `client/bench-core.js`(worker별 ELU·결과 결합)이다. 현재 규격은 Node event loop 하나를 전제하므로 코드만 먼저 바꾸면 규격과 어긋난다: [README §10.3](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/README.ko.md:617).
- 각 셀 결과를 쓰기 전에 `event_loop_utilization = worker ELU 합`, `client_parallelism_ceiling = worker 수`로 기록하면 aggregator 변경 없이 G6가 합산된 사용량과 용량을 비교할 수 있다. 이 값은 하나의 셀 metric으로 제출해야 하며, 현재 aggregator는 별도 client 결과를 합하지 않고 run 중앙값만 낸다: [bench-core.js](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/node/client/bench-core.js:289), [analysis.py](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/tools/benchagg/analysis.py:186), [analysis.py](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/tools/benchagg/analysis.py:205).
- 직렬 바인딩 행의 ELU 1.00은 stream 하나의 event loop가 실제로 포화된 값이다. 이 경우는 용량을 맞춰도 사라지지 않으며, G6에서 제외되는 것이 현행 규격의 의도다: [README §10.3](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/README.ko.md:607), [README §5.1](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/README.ko.md:271).
- 주어진 요약의 “모든 Node 셀이 1.00 포화”는 raw aggregate와 정확히 일치하지 않는다. 8개 비교 판정은 모두 unsupported지만, 예를 들어 Framework 직렬 1024 ELU는 0.5018이며 saturated가 아니다; 판정이 막히는 여러 비교는 binding row 포화 때문이다: [node.json](/root/jobs/fx/cx/v21/s033/r4190m/raw/aggregates/node.json:1039), [같은 파일](/root/jobs/fx/cx/v21/s033/r4190m/raw/aggregates/node.json:1046), [Framework 직렬 row](/root/jobs/fx/cx/v21/s033/r4190m/raw/aggregates/node.json:110), [해당 metric](/root/jobs/fx/cx/v21/s033/r4190m/raw/aggregates/node.json:125), [해당 saturation 판정](/root/jobs/fx/cx/v21/s033/r4190m/raw/aggregates/node.json:139).

## 4. 서버(target) 포화 여부

- 결과에는 target의 `server_cpu_percent`가 있지만 target event loop utilization은 기록하지 않는다. target stats가 CPU seconds와 메모리를 내보내고, ELU 필드는 없다: [bench-server-metrics.js](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/node/shared/bench-server-metrics.js:48), [같은 파일](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/node/shared/bench-server-metrics.js:67). source 결과의 `event_loop_utilization`은 client metric이다: [bench-core.js](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/node/client/bench-core.js:286), [같은 파일](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/node/client/bench-core.js:291).
- 16 논리 CPU 환경에서 target CPU는 aggregate 표상 직렬 3.8–8.1%, 역압 6.2–12.4%, send 7.7–11.1%다. raw 결과의 `logicalCores`는 16이다: [results.json](/root/jobs/fx/cx/v21/s033/r4190m/raw/bench/node/run1/zlink-node-request-serial-1024/results.json:11). 따라서 host 전체 CPU 포화 증거는 없다: [node.md](/root/jobs/fx/cx/v21/s033/r4190m/raw/aggregates/node.md:9), [직렬 raw 표](/root/jobs/fx/cx/v21/s033/r4190m/raw/aggregates/node.md:14), [역압 raw 표](/root/jobs/fx/cx/v21/s033/r4190m/raw/aggregates/node.md:21), [같은 표](/root/jobs/fx/cx/v21/s033/r4190m/raw/aggregates/node.md:25), [send 표](/root/jobs/fx/cx/v21/s033/r4190m/raw/aggregates/node.md:33), [같은 표](/root/jobs/fx/cx/v21/s033/r4190m/raw/aggregates/node.md:38).
- target ELU가 없어 target의 단일 JS event loop가 포화되지 않았다고 단정할 수는 없다. raw만으로 말할 수 있는 결론은 서버 프로세스 CPU의 host-wide 포화는 보이지 않는다는 것이다: [target stats schema](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/node/shared/bench-server-metrics.js:48), [같은 파일](/root/worktree/zlink-v21-s033/r4190m/framework/bench/grpc/node/shared/bench-server-metrics.js:68).
