For send, executor + mailbox + permit synchronization adds **10.274 µs/msg** of the **19.698 µs/msg** increase. Most executor synchronization samples are mutex acquisition/unlock paths; its condition-variable path is only 0.085 µs/msg on branch. A representative wake chain is `_raw_spin_unlock_irqrestore → try_to_wake_up → wake_up_q → futex_wake → __lll_lock_wake → pthread_mutex_unlock → offload_executor_t::worker_loop`. This is a contended mutex handoff, not evidence that `wake_one_locked` is notifying an idle condition variable on every record.

For request, all three synchronization owners add **7.603 µs/msg** of the **19.427 µs/msg** increase. The branch executor condition-variable path itself is 2.397 µs/msg; permit synchronization also grows by 2.642 µs/msg. The request profile therefore has a different mix from the sustained send backlog.

The branch executes `selected->take()` while holding the executor mutex, and completes active-work bookkeeping under that mutex after each record. The take enters the mailbox mutex and constructs a single-record claim, its pointer/byte vectors and settlement array there. Every detached record is then a last-credit settlement and takes the mailbox lock again. Main performs scheduler selection and mailbox claiming around a drain/batch, amortizing those operations. This accounts for the measured lock and take/settle groups. The remaining measured increase is in codec, dispatch/DI/terminal, permit and executor bookkeeping; these groups include allocation, destruction, typed invocation and reply preparation. CPU sampling does not identify how much of their increase is instruction work versus stalls or reduced clock rate.

In the branch p99 request, **3.164 ms precedes Spot owner enqueue and 4.357 ms follows handler exit**. Those intervals hold 7.521 ms of the 7.759 ms total. Executor queue wait is 0.210 ms, and the gate transition is under 0.001 ms. Short stages include probe overhead; they should not be interpreted as isolated atomic-instruction timings.

An additional branch request (ID 210) totals **7.465268 ms**, close to the reported 7.54 ms. It spends **3.340357 ms** from local infrastructure enqueue to activation dispatch, **0.069788 ms** in the application executor queue, **0.000712 ms** in gate transition, **0.000381 ms** in the handler, and **3.217441 ms** after handler exit. Scheduler trace independently shows TID 237749 runnable from `1902869.404687` to `1902869.408006` (**3.319 ms**) before the activation-dispatch marker. Completion TID 237735 is runnable from `1902869.408897` to `1902869.412016` (**3.119 ms**). Those non-overlapping intervals explain **6.438 ms** of this request. They are scheduler CPU-allocation delays, not evidence of a host-permit or execution-gate wait.

The first PM tracing pass also includes request 240, whose 8.072 ms total has 3.506 ms between gate publication and acquisition; its Spot worker is runnable for 3.489 ms before getting CPU. Thus a tail can appear in the executor-queue stage too. Across the measured examples, the common observed cause is runnable scheduling delay on the target affinity set; the location of that delay within a request varies.

Under condition B the application pool can own nine workers: one receive role and eight application workers. The separate infrastructure executor is sized from the same eight-CPU process affinity, and continuation/HTTP/Core threads share that mask. Pool independence does not provide CPU isolation. The trace establishes the runnable waits above; it does not establish a universal scheduler latency bound or a specification violation.
